# W6-10 — 승인 경계

> [30-6-w6-interrupt-resume.md](30-6-w6-interrupt-resume.md) §10의 상세 문서.

W6은 전환 10단계 중 **승인이 가장 많이 필요한 단계**다. 무엇을 자동으로 할 수 있고 무엇을 물어야
하는지가 별도 절로 분리된 이유다.

## 1. 승인 항목 전체

| 항목 | 승인 필요 | 시점 | 근거 |
| --- | --- | --- | --- |
| 공개 A2A 계약 변경(방향) | **이미 승인됨** | 2026-09-23 D1=B | 사용자 결정 |
| **계약안 C1~C5 구체안** | **필요** | 착수 전(W6-T1) | 방향만 승인됐고 구체안은 미정 |
| `workmate-ui` 수정 | 불필요 | — | 전환 범위 안(계획서 §7.2) |
| 어댑터(`tools/`) 수정 | 불필요 | — | 우리 저장소 |
| **오케스트레이터 저장소 수정** | **필요** | 필요 판정 시 | `AGENTS.md` 금지 |
| **Route allowlist 변경** | **필요** | C3가 b안이 될 때 | `AGENTS.md` |
| **02번 문서 개정** | **필요** | 완료 시 | `AGENTS.md` |
| **UI 육안 검수** | **필요** | 완료 시 | `AGENTS.md` 자동 승인 예외 |

## 2. 착수 전 승인 — 계약안 C1~C5

### 2.1 왜 착수 전인가

D1=B는 **방향** 결정이었다. "interrupt 기반으로 공개 계약까지 개편한다"까지만 정해졌고, 구체안은
W6에서 설계한다.

구현 후에 반려되면 되돌릴 범위가 크다.

| 반려 시 되돌릴 것 | 규모 |
| --- | --- |
| `app/graph/skills/assistant_router.py` | interrupt 노드 |
| `app/a2a/runtime.py`·`app/internal_chat.py` | 세 경로 |
| `AssistantDrawer.tsx` | 폴링 분기·확인 UI |
| `tools/m51_legacy_adapter.py` | 번역 |
| `02-a2a-interface.md` | 개정 |
| 스냅샷 2건 | 갱신 |

### 2.2 승인 요청 형식

W6-T1에서 다음을 제시한다.

```
[계약안 C1~C5]
C1 Task 상태:      INPUT_REQUIRED로 노출
C2 payload 위치:   Task.status.message
C3 resume 형태:    기존 message:send에 resume 표식 (Route allowlist 무변경)
                   ※ a2a-sdk가 허용하지 않으면 새 Route 필요 → 추가 승인
C4 취소:           CANCELED 전이
C5 멱등성:         원 message_id Key 유지

[영향]
agent / UI / 어댑터 / 02번 문서

[오케스트레이터]
어댑터 흡수 가능: 예 / 아니오
아니오인 경우: 수정 필요 범위와 승인 요청
```

### 2.3 승인 없이 진행 가능한 범위

W6-T1의 **조사**는 승인 없이 할 수 있다.

| 가능 | 불가 |
| --- | --- |
| a2a-sdk가 a안을 허용하는지 확인 | 계약 변경 구현 |
| 어댑터 코드 읽기 | 어댑터 수정 |
| 오케스트레이터가 `pending_action`을 어떻게 쓰는지 **읽기** | 오케스트레이터 수정 |
| 설계안 작성 | UI 수정 |

**읽기는 항상 허용된다.** `AGENTS.md`의 금지는 수정에 대한 것이다.

## 3. 오케스트레이터 저장소

### 3.1 규칙 원문

`AGENTS.md`:

> 오케스트레이터(`AI-agent_game_platform`) 저장소는 사용자가 그때그때 명시적으로 허용한 경우에만
> 수정한다. 버그를 발견해도(예: `a2a_client.py`의 응답 파싱 문제) 그 자리에서 직접 고치지 않고 먼저
> 사용자에게 보고해 승인을 받는다 — 이전 작업에서 이미 있던 문제를 발견 즉시 임의로 수정한 사례가
> 있었다. **이 규칙은 로컬 실행 확인·디버깅처럼 되돌리기 쉬운 상황에도 예외 없이 적용된다.**

강조 부분이 중요하다. "잠깐 고쳐서 확인만 하고 되돌리겠다"도 금지다.

### 3.2 판정 절차

```
W6-T1
  ├─ 오케스트레이터가 pending_action을 어떻게 쓰는지 조사 (읽기)
  ├─ 어댑터가 새 프로토콜을 옛 모양으로 번역할 수 있는가?
  │    ├─ 예  → 오케스트레이터 무수정. 승인 불필요
  │    └─ 아니오 → 아래로
  └─ 사용자에게 보고
       ├─ 수정 범위 제시
       ├─ 승인 → 오케스트레이터 수정
       └─ 미승인 → 축소안 검토 (§3.4)
```

### 3.3 흡수 가능성을 높이는 설계

C1~C5의 권장안은 **어댑터 흡수를 염두에 둔 것**이다.

| 계약 | 권장안 | 흡수 관점 |
| --- | --- | --- |
| C1 | `INPUT_REQUIRED` | 어댑터가 이 상태를 감지해 옛 `pending_action` 응답으로 번역 가능 |
| C2 | `status.message` | 번역할 payload를 꺼낼 위치가 명확 |
| C3 | `message:send` 표식 | **Route가 그대로라 어댑터 경로가 유지된다** |

C3가 b안(새 Route)이 되면 어댑터가 새 Route를 호출해야 하고, 오케스트레이터가 어댑터를 호출하는
방식도 영향받을 수 있다.

### 3.4 축소안 (D1의 C안)

오케스트레이터 수정이 불가능하면 범위를 줄인다.

| 경로 | 축소안 |
| --- | --- |
| A2A(오케스트레이터) | **기존 계약 유지** — `pending_action` 방식 |
| 내부 UI(Drawer) | `interrupt` 기반으로 개편 |

이는 D1의 C안이며, 2026-09-23 결정에서 사용자가 B안을 택했으므로 **축소는 사용자 확인 후에만** 한다.

## 4. Route allowlist 변경

### 4.1 규칙

`AGENTS.md`:

> 공식 SDK가 제공하는 Route를 전부 공개하지 않는다. 승인된 MVP Route allowlist만 등록하고 제외
> Route의 `404` 또는 `405` Contract Test를 유지한다.

allowlist 확대는 공개 표면 확대이므로 승인 대상이다.

### 4.2 언제 필요해지나

C3가 b안(새 Route `tasks/{id}:resume`)이 될 때다. a2a-sdk 1.1.2가 a안을 허용하지 않으면 불가피하다.

**W6-T1에서 SDK 동작을 먼저 확인**하는 이유다. 확인 결과에 따라 승인 요청 내용이 달라진다.

## 5. UI 육안 검수

### 5.1 규칙

`AGENTS.md`:

> 외부 OAuth·실제 Provider 호출, 공개 Schema·데이터 모델 변경, **UI 육안 검수**, 모델 평가, 원격
> Push처럼 별도 권한이나 사람의 판단이 필요한 작업은 모든 테스트가 PASS여도 자동 진행하지 않고
> 사용자 승인을 기다린다.

### 5.2 검수 항목

[W6-V7](30-6-7-verification.md)의 6케이스다.

```
[ ] V7-1 확인 UI가 표시되는가
[ ] V7-2 확인 후 실행되고 결과가 표시되는가
[ ] V7-3 거부 시 취소 안내가 표시되는가 (오류로 보이지 않는가)
[ ] V7-4 확인 대기 중 5분 타임아웃 오류가 나지 않는가
[ ] V7-5 확인 후 오래 걸리는 Skill의 결과가 오는가
[ ] V7-6 확인 대기 중 새 메시지 입력 시 동작
[ ] V7-7 **확인 대기 중 서버 재시작 → resume이 멈춘 지점부터 이어지는가**
```

**V7-7은 기능 검수가 아니라 구조 증명이다.** 재요청 방식으로는 통과할 수 없는 유일한 케이스이며,
전환이 실제로 Checkpointer 위에서 동작함을 사용자가 직접 확인하는 자리다.

### 5.3 검수 절차

기존 [13-manual-verification-guide.md](13-manual-verification-guide.md) 형식을 따른다. 그 문서에
W6 항목을 추가하고, 사용자가 절차대로 수행해 PASS/FAIL을 판정한다.

## 7. 승인 요청 타이밍 정리

```
W6-T1 (착수 전)
  └─ 승인 요청 #1: 계약안 C1~C5 + 02번 문서 개정안 + (필요 시) 오케스트레이터 수정 + Route 변경
       ↓ 승인
  구현 (W6-T2~T9)
       ↓
W6-T10 (완료 시)
  └─ 승인 요청 #2: UI 육안 검수 결과 + 전체 완료 승인
```

**`AGENTS.md`의 "Push 승인 질문도 실제 Push 조건에 도달했을 때 한 번만 한다"와 같은 원칙이다.**
승인 요청을 잘게 쪼개지 않고 두 번으로 묶는다.

## 8. 승인 대기 중 할 수 있는 것

승인 #1을 기다리는 동안 멈춰 있을 필요는 없다.

| 가능 | 이유 |
| --- | --- |
| 기존 코드 조사 | 읽기는 허용 |
| 테스트 설계 | 계약이 확정되면 바로 쓸 수 있다 |
| W3-V11-4 재확인(외부 상태 불변) | 계약과 무관한 불변식 |
| 스냅샷 변경 전 대조(25+2 확인) | 현재 상태 기록 |

**단 W6-T2(interrupt 도입) 이후는 계약 확정이 전제다.**
