## W6-K1 — interrupt 이전 외부 상태 변경

**설명** `validate_skill_and_arguments` 같은 노드가 검증 과정에서 DB를 쓴다.

**왜 치명적인가** **확인 절차 자체가 무의미해진다.** 사용자가 "아니오"를 눌러도 이미 Task가 삭제된
뒤다. 그런데 **기능은 정상으로 보인다** — 확인 UI가 뜨고 취소도 동작하는 것처럼 보인다.

**발생 경로**

| 경로 | 예 |
| --- | --- |
| 검증 중 상태 갱신 | "이 Task가 존재하는지 확인"하면서 조회 시각을 기록 |
| 컨텍스트 해소 | "그 회의"를 찾으면서 조회 이력 저장 |
| 사전 준비 | 삭제 전에 백업을 만드는 식의 선제 동작 |

**완화**
- 노드별 허용 동작표([30-6-5](30-6-5-design.md) §3.1)를 설계 검토 항목으로
- **W6-V2를 가장 먼저 수행**([30-6-7](30-6-7-verification.md) §3)
- 확인 대상 4종 각각에 대해 DB 직접 조회
- W6-V2-6: `validate_skill_and_arguments`의 Repository 쓰기 호출 계측

**대응 계획** 쓰기가 발견되면 그 동작을 `call_selected_subgraph` 이후로 옮긴다. 검증에 꼭 필요한
쓰기라면 설계를 재검토한다.

---

## W6-K2 — resume 시 LLM 재호출

**설명** 재개할 때 Router LLM을 다시 불러 `skill_id`를 새로 결정한다.

**왜 치명적인가** LLM은 결정적이지 않다. 사용자는 "Task 삭제"를 확인했는데 **"Task 수정"이 실행**될
수 있다. 사용자가 승인하지 않은 동작이 실행되는 것이다.

**현재 코드는 이미 이를 막는다**
([assistant_router.py:794-803](../workmate-agent/app/workflows/assistant_router.py#L794)).
`confirmed_skill_id`가 있으면 `route()`를 건너뛴다. W6에서 이 보호를 잃지 않아야 한다.

**완화**
- Checkpoint의 검증된 `skill_id`·`arguments`만 사용
- **W6-V4에서 LLM 호출 계측** — Router 0회
- W6-V4-2·V4-3: 실행되는 값이 확인 시점과 동일한지
- W6-V4-4: `phrase_answer`의 호출은 정상(구분)

**대응 계획** 재호출이 발견되면 resume 경로가 `route_with_llm` 노드를 지나고 있는 것이다. Graph
구조를 재검토한다.

## W6-K3 — UI가 `INPUT_REQUIRED`를 모름

**설명** 폴링 루프에 분기를 추가하지 않아 5분간 헛돌다 타임아웃한다.

**확률이 높은 이유** 현재 코드가 그렇게 돼 있고, agent만 고치고 UI를 잊기 쉽다.

```js
// AssistantDrawer.tsx:151-163
if (state === "TASK_STATE_COMPLETED") { ... }
if (TERMINAL_FAILURE_STATES.has(state)) { ... }   // FAILED, CANCELED, REJECTED
// INPUT_REQUIRED는 어디에도 안 걸린다 → 1.5초 후 재폴링 → 5분 후 타임아웃
```

**증상** 사용자에게는 "시간 내에 끝나지 않았습니다"로 보인다. 확인을 요청한 것인데 오류처럼 보인다.

**완화**
- W6-T6을 W6-T4와 **같은 커밋 범위**로 묶는다
- **W6-V7-4 육안 검수** — 확인 대기 중 타임아웃이 나지 않는지
- `CANCELED`도 `TERMINAL_FAILURE_STATES`에서 분리(W6-D4)

**대응 계획** UI 수정 없이 agent만 배포하면 확인 기능이 완전히 망가진다. 두 변경을 분리 배포하지
않는다.

---

## W6-K4 — 오케스트레이터 호환성

**설명** 새 프로토콜을 오케스트레이터가 읽지 못해 팀 통합 경로가 끊긴다.

**제약** `AGENTS.md`상 오케스트레이터 저장소를 임의로 수정할 수 없다.

**완화**
- **W6-T1에서 어댑터 흡수 가능성을 먼저 판정**
- C1~C5의 권장안이 흡수를 염두에 둔 설계([30-6-10](30-6-10-approval.md) §3.3)
- 특히 C3-a안(Route 무변경)이 어댑터 경로를 유지한다
- 흡수 불가 시 승인 요청 또는 축소안

**대응 계획** [30-6-10](30-6-10-approval.md) §3.4의 축소안 — A2A는 기존 계약 유지, 내부 UI만 개편.
단 이는 D1=B의 축소이므로 사용자 확인이 필요하다.

## W6-K5 — 계약 변경 미반영

**설명** 구현은 바뀌었는데 02번 문서가 옛 계약을 설명한다.

**영향** 다음 작업자나 오케스트레이터 담당자가 잘못된 전제로 작업한다. 전환의 목적 중 하나가 "문서와
구현의 일치"인데 그것이 깨진다.

**완화**
- W6-T8을 완료 조건(E-3)에 포함
- W6-V9에서 문서 ↔ 구현 대조
- 02번 개정안을 W6-T1의 승인 요청에 포함(먼저 쓰고 나중에 구현)

## W6-K6 — 세 경로의 표면화 불일치

**설명** A2A·UI 동기·UI 비동기에서 `INPUT_REQUIRED`가 다르게 나온다.

**발생 경로** 세 경로의 구조가 다르다.

| 경로 | 응답 방식 | `INPUT_REQUIRED`를 어떻게 전달하나 |
| --- | --- | --- |
| A2A | 이벤트 큐 | 상태 이벤트 |
| UI 동기 | 즉시 응답 | 응답 바디의 `state` |
| UI 비동기 | 폴링 | Task 조회 결과 |

**특히 UI 동기 경로가 애매하다.** 확인이 필요한 Skill은 `assistant_ask`이고 이는 `_ASYNC_SKILLS`에
있어 비동기로 실행된다. 즉 동기 경로에서는 `INPUT_REQUIRED`가 안 나올 수도 있다.

**완화**
- W6-T3에서 세 경로 각각의 동작을 명시
- 동기 경로에서 발생 가능한지 먼저 판정 — 불가능하면 처리하지 않아도 된다
- W6-V1을 경로별로 수행

---

## W6-K7 — 스냅샷 3건 이상 변경

**설명** 의도한 2건 외에 다른 케이스도 바뀐다.

**의미** W6이 확인 흐름 외의 것을 건드렸다는 뜻이다.

**있을 수 있는 원인**

| 원인 | 예 |
| --- | --- |
| Assistant Subgraph 구조 변경의 파급 | `phrase_answer` 동작이 달라짐 |
| Task 상태 전이 변경 | 다른 Skill의 `state` 필드 |
| 멱등성 처리 변경 | 재실행 동작 |

**완화**
- **W6-V10-1에서 변경 전 대조**를 먼저 한다(25+2 확인)
- 3건 이상이면 **갱신하지 않고 원인 조사**
- 기록 모드를 성급히 쓰지 않는다

**대응 계획** 원인을 찾아 수정한다. "이것도 개선이니까"로 갱신하면 W9에서 설명할 수 없는 차이가 된다.

---

## W6-K8 — 멱등성 Key 충돌

**설명** resume 요청의 payload가 원 요청과 달라 해시가 바뀌고,
[`record_message()`](../workmate-agent/app/a2a/persistence.py#L234)가 `ValueError`를 낸다.

```python
if row:
    if row[0] != digest:
        raise ValueError("message_id was reused with a different payload")
```

**완화**
- C5 결정: 원 `message_id` Key 유지
- W6-D3: 멱등성 기록은 **최종 완료 시 한 번만**
- 선례: [`_save_task_status()`](../workmate-agent/app/internal_chat.py#L276)가 이미 이 방식을 쓴다
- W6-V5-4에서 확인

---

## W6-K9 — SDK가 C3-a안을 허용하지 않음

**설명** a2a-sdk 1.1.2의 `message:send`가 resume 표식을 실어 보내는 방식을 지원하지 않는다.

**영향** C3가 b안(새 Route)이 되고, **Route allowlist 변경 승인**이 추가로 필요해진다.

**완화**
- **W6-T1에서 가장 먼저 확인**
- 확인 결과를 승인 요청에 포함
- b안이 되면 allowlist 변경도 같은 승인에 포함시켜 승인 왕복을 줄인다

---

## W6-K10 — 확인 대기 Task가 영원히 남음

**설명** 사용자가 확인도 거부도 하지 않으면 Task가 `INPUT_REQUIRED`로 무한히 남는다.

**영향** 크지 않다. Checkpoint와 Task 행이 쌓이는 정도.

**완화**
- 현재도 같은 상황이다 — 확인 버튼을 안 누르면 아무 일도 안 일어난다
- 만료 정책은 이번 범위가 아니다. 필요하면 후속 백로그
- W6-V7-6(확인 대기 중 새 메시지)에서 UI 동작만 정한다

## 3. "기능은 되는데 위험한" 유형

W6에는 **겉보기에 정상인데 실제로는 깨진** 상태가 셋 있다. 전용 검증 없이는 발견되지 않는다.

| 위험 | 겉보기 | 실제 | 검증 |
| --- | --- | --- | --- |
| W6-K1 | 확인 UI가 뜨고 취소도 됨 | 이미 실행됨 | W6-V2 |
| W6-K2 | 확인 후 뭔가 실행됨 | 다른 Skill | W6-V4 |
| W6-K8 | 대부분 동작 | 특정 조건에서 resume 실패 | W6-V5-4 |

**W6-V2와 W6-V4를 건너뛰면 W6은 "된 것처럼 보이지만 안전하지 않은" 상태로 완료된다.**
