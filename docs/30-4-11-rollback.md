# W4-11 — 롤백·중단·재개 기준

> [30-4-w4-root-graph.md](30-4-w4-root-graph.md) §11의 상세 문서.

## 1. 롤백 비용

W4까지는 **운영 경로가 기존 `WorkflowRegistry`**다. Root Graph는 테스트에서만 실행되므로 롤백해도
사용자에게 보이는 동작이 변하지 않는다.

| 산출물 | 롤백 방법 | 비용 |
| --- | --- | --- |
| `app/graph/nodes/*`, `root.py` | 커밋 revert | 낮음 |
| `tests/test_graph_root.py` | 동일 | 낮음 |
| Checkpointer 테이블 | 테스트 DB 재생성 | 낮음 |

### 1.1 주의 — Checkpointer 테이블

W4-T6에서 Checkpointer를 결합하면 첫 실행 시 자체 테이블이 생성된다. W4를 revert해도 테이블은 남는다.
테스트 DB에서는 무해하지만, 재시도 시 스키마 버전이 어긋날 수 있으므로 컨테이너를 재생성하는 편이
안전하다.

## 2. 부분 롤백

노드 단위로 되돌릴 수 있다. 다만 의존이 있다.

| 롤백 단위 | 영향 | 남는 것 |
| --- | --- | --- |
| `validate_contract`만 | Schema 검증 없이 동작(현재와 같음) | 나머지 유효 |
| `idempotency_check`·`restore_result` | 멱등성 미구현(현재와 같음) | 나머지 유효 |
| `route_skill` | **Root Graph 전체 무효** | — |
| Subgraph 합성 | 동상 | — |

`route_skill`과 합성이 Root Graph의 뼈대다. 나머지 노드는 독립적으로 뺄 수 있다.

### 2.1 부분 롤백의 실용적 의미

W4에서 시간이 부족하면 이 순서로 확보한다.

```
1. route_skill + 합성 + Checkpointer   (Graph가 동작하는 최소)
2. initialize_state + build_artifact    (결과가 나오는 최소)
3. persist_result                       (Task Store 연동)
4. idempotency_check + restore_result   (W4-D1 동작 변경)
5. validate_contract                    (새 검증)
```

단 4·5를 빼고 W5로 가면 그 기능이 영영 안 들어올 수 있으므로, 뺀다면 **후속 백로그로 명시**한다.

## 3. 중단 기준

### 3.1 즉시 중단 — 사용자 판단 필요

| 조건 | 사유 | 처리 |
| --- | --- | --- |
| **W4-V5-1에서 스냅샷 케이스가 Schema 위반** | 현재 존재하는 계약 위반 발견 | 위반 내용을 보고. 구현 수정은 별도 판단 |
| **W4-D1 멱등성 변경이 기존 테스트를 광범위하게 깨뜨림** | 예상 밖 파급 | 범위와 원인을 보고 |
| Task Store 구조 변경이 필요해짐 | 범위 이탈(96번 §10) | 보고 |
| Schema 파일을 배포 환경에서 못 찾고 해결 불가 | W4-R10 미충족 | 보고 |

### 3.2 자동 재작업 — 사용자 질문 없이 진행

| 조건 | 처리 |
| --- | --- |
| 공통 노드가 값을 덮어씀(W4-V6 차이) | 노드 수정 후 재대조 |
| path map 누락 | 추가 후 재검증 |
| 순환 import | 주입 구조로 수정 |
| Checkpointer 결합 오류 | 수정 |
| 식별자 유실 | 수정 |

다음은 해결 방법으로 인정하지 않는다.

| 금지 | 이유 |
| --- | --- |
| **Schema를 완화해 검증 통과** | `AGENTS.md` 기대값 완화 금지 |
| 스냅샷 기대값 수정 | 동상 |
| 멱등성 구현을 포기하고 A안(현행 유지)으로 전환 | W4-D1은 확정된 설계 결정. 바꾸려면 사용자 판단 |
| `validate_contract`를 조용히 비활성화 | W4-V5-4 위반 |

### 3.3 조건부 진행

| 조건 | 처리 |
| --- | --- |
| W4-V5(Schema)만 FAIL, 나머지 PASS | Schema 검증을 후속 백로그로 미루고 W5 진행 **가능**. 단 명시 기록 |
| **W4-V3(멱등성) FAIL** | **W5 진행 금지.** 공개 계약이 깨진 채 진입점을 바꿀 수 없다 |
| W4-V7(Checkpoint) FAIL | W6 진행 불가. W5는 가능하나 권장하지 않음 |

**W4-V3만 무조건 차단 조건인 이유:** 다른 항목은 Graph 내부 문제라 W5에서 고칠 수 있지만, 멱등성은
진입점을 바꾸는 순간 외부에 노출된다. 중복 실행이 실제 부작용(Task 중복 생성 등)을 낳는다.

## 4. 재개 조건

| 중단 사유 | 재개 조건 |
| --- | --- |
| Schema 위반 발견 | 위반 처리 방침 확정(구현 수정 / 예외 기록) |
| 멱등성 파급 | 영향 범위 파악 후 방침 확정 |
| Task Store 구조 | 범위 확대 승인 또는 대안 확정 |
| Schema 파일 접근 | 배포 경로 해결 |

재개 시 [30-4-3](30-4-3-entry-criteria.md)의 선행 조건을 다시 확인한다. 특히 W4-E2(스냅샷 PASS)는
중단 기간 중 W3을 손댔다면 다시 검증한다.

## 5. 에스컬레이션 경로

```
W4-V6 (Root 경유 스냅샷) FAIL
  │
  ├─ 공통 노드가 값을 덮어씀
  │    → 노드 수정 후 재대조 (자동 재작업)
  │
  ├─ validate_contract가 거부
  │    → W4-V5-1 사전 검증 결과와 대조
  │    → 사전 검증도 실패했던 케이스면 → 중단, 보고
  │
  └─ 멱등성 경로를 탐
       → 케이스 격리 확인 (자동 재작업)

W4-V3 (멱등성) FAIL
  → W5 진행 금지
  → 원인이 구현이면 수정
  → 원인이 설계(W4-D1)면 중단, 보고
```

## 8. W4 특유의 주의

### 8.1 "운영 경로는 아직 옛 코드"라는 안전망

W4에서 무슨 일이 생겨도 사용자는 영향을 받지 않는다. 이 여유가 W5 이후에는 없다.

따라서 **W4에서 발견한 문제는 W4에서 해결한다.** "W5에서 어차피 손볼 거니까"로 미루면, W5에서는
운영 경로가 바뀐 상태라 원인 분리가 어려워진다.

### 8.2 동작 변경 3건의 취급

W4-D1·D3·D5는 의도적 변경이다. 롤백을 고민할 때 "이것도 되돌릴까"가 아니라 **"이 변경을 기록했는가"**를
먼저 본다.

| 상황 | 처리 |
| --- | --- |
| 변경이 문제를 일으킴 | 원인 분석. 설계 결정 자체를 되돌리려면 사용자 판단 |
| 변경은 잘 동작하는데 기록이 없음 | **기록이 먼저다.** W9에서 "설명 불가 차이"가 된다 |

### 8.3 스냅샷으로 못 잡는 변경이 늘고 있다

| 단계 | 스냅샷 밖 변경 | 전용 검증 |
| --- | --- | --- |
| W3 | 숨은 부작용(우선순위 Snapshot 저장) | W3-V11 |
| **W4** | **멱등성·`runtime_bootstrap`·진행 중 중복** | **W4-V3, V2-3** |
| W6 | 확인 프로토콜(의도적) | W6-V1~V6 |

이 목록이 W9의 "의도적 변경" 절을 구성한다. 단계마다 빠짐없이 등록한다.
