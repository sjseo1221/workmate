# W6-12 — 롤백·중단·재개 기준

> [30-6-w6-interrupt-resume.md](30-6-w6-interrupt-resume.md) §12의 상세 문서.

## 1. 롤백 비용 — 전환에서 가장 높다

W6은 **agent·UI·어댑터·문서가 함께 바뀌는 유일한 단계**다.

| 단계 | 바뀌는 저장소 | 롤백 비용 |
| --- | --- | --- |
| W1~W4 | workmate-agent(테스트만) | 낮음 |
| W5 | workmate-agent(운영 경로) | 중간 |
| **W6** | **workmate-agent + workmate-ui + docs** | **높음** |
| W7 | workmate-agent + DB | 높음(비가역 포함) |

### 1.1 부분 롤백이 위험한 이유

agent만 되돌리면 UI가 `INPUT_REQUIRED`를 기대하는데 오지 않는다. UI만 되돌리면 agent가 `INPUT_REQUIRED`를
보내는데 UI가 모른다 — **5분 타임아웃**(W6-K3).

**agent 변경과 UI 변경을 인접 커밋으로 두고 함께 revert한다**([30-6-6](30-6-6-wbs.md) §2 W6-T10).

## 2. 롤백 단위

| 롤백 단위 | 영향 | 비고 |
| --- | --- | --- |
| **W6 전체** | 확인 흐름이 `pending_action` 방식으로 복귀 | 권장 |
| agent만 | UI가 오지 않는 상태를 기다림 | **금지** |
| UI만 | 확인이 타임아웃으로 보임 | **금지** |
| 어댑터만 | 오케스트레이터 경로만 옛 방식 | 상황에 따라 가능 |
| 문서만 | 구현과 불일치 | 의미 없음 |

### 2.1 W6 전체 롤백 절차

```
1. UI 커밋 revert
2. 어댑터 커밋 revert
3. agent 커밋 revert (interrupt·INPUT_REQUIRED·resume·취소)
4. 스냅샷 2건 복원 (git에서 이전 버전)
5. 02번 문서 revert
6. app/workflows/의 확인 흐름이 다시 살아나는지 확인
```

6번이 중요하다. W6 롤백의 착지점은 **W5 완료 상태**이고, 그때 확인 흐름은 Graph의
`build_pending_action_reply` 노드가 담당한다(W3에서 만든 것).

## 3. 중단 기준

### 3.1 즉시 중단 — 사용자 판단 필요

| 조건 | 사유 | 처리 |
| --- | --- | --- |
| **계약안 C1~C5 미승인** | 선행 조건 W6-E3 | W6-T1에서 대기 |
| **어댑터 흡수 불가 + 오케스트레이터 수정 미승인** | `AGENTS.md` 금지 | 축소안 검토 후 사용자 확인 |
| **Route allowlist 변경이 필요한데 미승인** | 동상 | 동상 |
| **W6-V2(외부 상태 불변) FAIL이고 해결 불가** | 확인 절차 무의미 | 설계 재검토 후 보고 |
| W6-V7(육안 검수) FAIL | 사용자 지적 | 수정 후 재검수 |
| 스냅샷 3건 이상 변경 | 의도하지 않은 변경 | 원인 조사 후 보고 |

### 3.2 자동 재작업 — 사용자 질문 없이 진행

**단, 계약안이 승인된 범위 안에서만.**

| 조건 | 처리 |
| --- | --- |
| interrupt가 잘못된 조건에서 발동 | 판정 로직 수정 |
| resume이 앞 노드부터 재실행 | Graph 구조 수정 |
| LLM 재호출 발생 | 경로 수정 |
| 멱등성 Key 충돌 | 기록 시점 조정(W6-D3) |
| UI 분기 누락 | 추가 |
| 세 경로 표면화 불일치 | 통일 |

다음은 해결 방법으로 인정하지 않는다.

| 금지 | 이유 |
| --- | --- |
| **확인 판정 규칙 4종 변경** | W6-R10. 범위 밖 |
| **외부 상태 변경을 "어차피 확인할 거니까"로 허용** | W6-R4 불변식 |
| resume 시 LLM 재호출 허용 | W6-R5 |
| 스냅샷 3건 이상을 그냥 갱신 | 설명 불가 차이가 된다 |
| 승인 없이 오케스트레이터 수정 | `AGENTS.md` 금지 |
| UI만 먼저 배포 / agent만 먼저 배포 | §1.1 |

### 3.3 조건부 진행

| 조건 | 처리 |
| --- | --- |
| W6-V8(어댑터) FAIL이고 흡수 불가 | A2A 경로는 축소안, 내부 UI는 진행 — **사용자 확인 후** |
| W6-V7 일부 케이스 FAIL | 지적 사항 수정 후 재검수. 전체 중단은 아님 |
| W6-K10(대기 Task 만료) | 범위 밖. 후속 백로그로 기록하고 진행 |

## 5. 에스컬레이션 경로

```
W6-T1 (계약안)
  ├─ SDK가 C3-a안 미지원 → b안 + Route 변경 승인 요청
  ├─ 어댑터 흡수 불가 → 오케스트레이터 수정 승인 요청
  └─ 둘 다 → 승인 요청 한 번에 묶는다

W6-V2 (외부 상태 불변) FAIL
  ├─ 쓰기 노드 식별 → call_selected_subgraph 이후로 이동 (자동 재작업)
  └─ 검증에 쓰기가 꼭 필요 → 설계 재검토 → 중단, 보고

W6-V7 (육안 검수) FAIL
  ├─ UI 버그 → 수정 후 재검수 (자동 재작업)
  └─ UX 설계 이견 → 사용자와 협의

스냅샷 3건 이상 변경
  → 갱신 금지
  → 원인 조사
  → 의도한 것이면 사용자 보고 후 갱신
  → 회귀면 수정
```

## 6. 중단 시 기록 의무

```
## 9. 최종 판단
- 승인 여부: 보류
- 자동 진행 판정: 중단 / 보류 — 사용자 승인 대기
- 자동 진행 보류 사유: (구체적으로)
- 승인 대기 항목: 계약안 C1~C5 / 오케스트레이터 수정 / Route 변경 / 육안 검수
- 판정을 막은 검증: W6-Vx
- 구현 상태: agent / UI / 어댑터 / 문서 각각의 진행도
- 롤백 여부: (되돌렸는지, 부분인지)
- 시도한 해결 방법: (후보별 결과)
- 필요한 조치·승인: (내용)
- 재개 조건: (조건)
- 다음 구현 백로그: W6-Tx
```

**"승인 대기 항목"과 "구현 상태"가 W6 고유다.** 여러 저장소에 걸친 작업이므로 어디까지 됐는지를
명시해야 한다.

## 8. W6 특유의 주의

### 8.1 승인이 롤백보다 싸다

W6은 롤백 비용이 가장 높은 단계다. 그래서 **착수 전 승인**(W6-E3)이 선행 조건으로 들어가 있다.

```
승인 후 구현:  설계안 작성 → 승인 → 구현
승인 없이 구현: 구현 → 반려 → agent + UI + 어댑터 + 문서 롤백
```

두 번째 경로가 훨씬 비싸다. **"일단 만들어 보고 물어보자"를 하지 않는다.**

### 8.2 "기능은 되는데 위험한" 상태를 경계한다

[30-6-11](30-6-11-risks.md) §3의 세 유형은 전부 겉보기에 정상이다.

| 유형 | 겉보기 |
| --- | --- |
| 외부 상태 변경(K1) | 확인 UI가 뜨고 취소도 됨 |
| LLM 재호출(K2) | 확인 후 뭔가 실행됨 |
| 멱등성 충돌(K8) | 대부분 동작 |

**육안 검수(W6-V7)로는 이 셋을 잡을 수 없다.** W6-V2·V4·V5-4가 필요한 이유다.

### 8.3 W7 전의 마지막 롤백 기회

W7에서 `app/workflows/`를 삭제하면 W6 롤백의 착지점이 사라진다.

```
W6 완료 → (검증 기간) → W7 삭제
              ↑
        여기가 마지막 롤백 기회
```

**W6 완료 후 바로 W7로 가지 않고, 검증이 충분한지 확인한다.** 특히 육안 검수와 오케스트레이터
통합 확인.
