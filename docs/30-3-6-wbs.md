## 2. 작업 상세

### W3-T0 — 노드 분해 설계 확정

**내용**

1. [30-3-5](30-3-5-design.md) §2의 노드 분해안을 실제 코드와 재대조
2. 설계 결정 W3-D1~D5 확정
3. Skill별 부작용 노드 목록 확정([30-3-5](30-3-5-design.md) §3.4) — W8의 재시도 제외 대상이 된다
4. 실패 파급 규칙표 확정([30-3-5](30-3-5-design.md) §7)

**왜 별도 작업인가** 11개를 만들면서 설계를 즉흥적으로 정하면 Skill마다 분해 기준이 달라진다.
일관성 없는 Subgraph는 W4 합성과 W8 정책 적용에서 예외를 만든다.

**난이도** 중간 / **예상 비중** 전체의 10%

### W3-T1 — `rank_priorities`

**내용** [30-3-5](30-3-5-design.md) §2.1의 8노드 구조 구현.

**주의**
- `load_previous_snapshot`을 `save_snapshot`보다 **먼저** 실행한다. 순서가 바뀌면 `changes`가 항상
  `unchanged`가 된다
- `calculated_at`은 비결정 값이다. W1 스냅샷의 정규화 대상인지 확인
- 점수는 [`rank_tasks()`](../workmate-agent/app/domain/priority.py) 호출만(W3-R4)
- `data=` 채우기 — 비우면 프론트가 `null`만 읽는다

**검증** 스냅샷 `rank_priorities.*` + W3-V3(user_id) + W3-V7(LLM 경계)

**난이도** 낮음 — 첫 Skill이므로 패턴을 세우는 의미가 크다

---

### W3-T2 — 보조 Skill 5종

**내용** `get_meeting_analysis`·`review_action_items`·`review_proposal`·`manage_tasks`·`read_email`을
3노드 구조(`validate_input → call_domain_api → build_result`)로 구현.

**주의**
- 이 5개는 UI REST 함수를 호출하는 **얇은 래퍼**다. 억지로 쪼개지 않는다(W3-D4)
- 호출 대상 모듈(`action_item_api`·`proposal_api`·`task_api`)은 **범위 밖** — 수정하지 않는다
- `manage_tasks`만 4분기 조건부 Edge
- `ValueError` → 422 매핑이 유지되도록 예외를 삼키지 않는다

**난이도** 낮음 / **예상 비중** 5개 합쳐 전체의 10%

---

### W3-T3 — `daily_briefing`

**내용** [30-3-5](30-3-5-design.md) §2.3의 팬아웃 구조 구현.

**주의**
- **3중 실패 정책을 그대로 보존**한다 — Gmail 실패는 경고, 본문 보강 실패는 조용히 무시, LLM 관련성
  판정 실패는 전부 통과
- `rank_priorities` Subgraph를 호출해 **부작용을 유지**한다(W3-D1)
- 메일 본문 보강의 내부 병렬(`asyncio.gather(..., return_exceptions=True)`)을 유지
- `summary` 문자열은 고정 템플릿. LLM 아님
- W2의 `warnings` Reducer가 **여기서 처음 실제로 쓰인다** — 병렬 노드 동시 경고 검증(W3-V6)

**검증** 스냅샷 + W3-V5(부분 실패) + W3-V6(병렬) + **W3-V11(숨은 부작용)**

**난이도** 높음 / **예상 비중** 전체의 15%

---

### W3-T4 — `weekly_report`

**내용** [30-3-5](30-3-5-design.md) §2.4 구현.

**주의**
- 현재 등록 형태가 다르다 — 빌더가 아니라 **핸들러 함수 자체**가 등록된다
  ([runtime.py:368](../workmate-agent/app/a2a/runtime.py#L368)). W4 합성 시 혼동 주의
- 재시도 정책이 `assistant_router`와 **다르다** — 2회, 429·5xx 포함
  ([30-2-5](30-2-5-design.md) §5.2). 통일하지 않는다
- 분류와 `source_refs`는 Domain 소유. LLM은 문장만(W3-R4)
- `blocked` Task는 `delayed`가 아니라 `unresolved_issues`
- [30-3-3](30-3-3-entry-criteria.md) W3-E3(W2-V6) 충족 후 착수

**난이도** 높음 / **예상 비중** 전체의 12%

---

### W3-T5 — `search_meetings`

**내용** [30-3-5](30-3-5-design.md) §2.5 구현.

**주의**
- 근거 부족은 **정상 종료**다. 예외로 만들지 않는다
- 회의 날짜 누락은 **전체 실패**(`ValueError`)
- warning 분류가 `grounded` 여부로 갈린다 — `INSUFFICIENT_EVIDENCE`(재시도 불가) vs
  `LLM_PROVIDER_UNAVAILABLE`(재시도 가능). 2026-09-23 커밋 `8043c1e`에서 확정된 동작
- 테스트 Postgres + pgvector 필요

**난이도** 중간 / **예상 비중** 전체의 10%

---

### W3-T6 — `analyze_meeting`

**내용** [30-3-5](30-3-5-design.md) §2.6 구현.

**주의**
- **순서가 계약이다** — 근거 검증(`verify_evidence`)을 통과하지 못하면 저장하지 않는다
- 색인 실패가 이미 저장된 분석을 롤백하지 않는다(실패 격리)
- 부작용 노드 4개(`save_final_transcript`·`save_analysis`·`heal_meeting_title`·`index_chunks`)를
  W8 재시도 제외 목록에 기록
- Fake STT·Fake R2 Fixture 사용

**난이도** 높음 / **예상 비중** 전체의 13%

### W3-T7 — `assistant_ask`

**내용** [30-3-5](30-3-5-design.md) §2.7 구현. **확인 흐름은 현재 방식 그대로**(W3-R11).

**분할 착수 권장** 937줄을 한 번에 옮기지 않는다.

```
T7-a  load_conversation_context + resolve_context_references
T7-b  route_with_llm (구조화 출력)
T7-c  validate_skill_and_arguments + requires_confirmation 판정
T7-d  build_pending_action_reply (W6 교체 대상 노드)
T7-e  call_selected_skill (주입 핸들 사용) + offer_followup
T7-f  phrase_answer + build_assistant_reply
```

**주의**
- `confirmed_skill_id` 재요청 경로는 `route_with_llm`을 건너뛴다
- 확인 판정 규칙 4종을 그대로 옮긴다
- Skill 호출은 주입 핸들로만(W3-D2). 직접 import 금지
- `requires_confirmation?`과 `call_selected_skill` 사이 경계를 반드시 나눈다(W3-D5)

**난이도** 매우 높음 / **예상 비중** 전체의 25%

### W3-T8 — 스냅샷 대조

**내용** Skill 완료 즉시 해당 케이스 대조.

```
uv run python -m unittest tests.contracts.test_contract_snapshots -k <skill_id> -v
```

**차이 발견 시 판정 순서**

```
1. 이식 오류인가?           → 구현 수정
2. 스냅샷 정규화 누락인가?   → W1 정규화 보완 (이유 기록)
3. 의도적 변경인가?         → W3 범위에서는 원칙적으로 없어야 한다.
                             있다면 근거를 증빙에 기록하고 사용자에게 보고
```

**금지** 스냅샷 기대값을 새 구현에 맞춰 고치는 것(`AGENTS.md`: 기대값 완화 금지).

## 3. 작업 의존 그래프

```
W3-T0 (설계 확정)
  ↓
W3-T1 (rank_priorities)
  ├→ W3-T2 (보조 5종) ──────────┐
  └→ W3-T3 (daily_briefing)     │   ※ T1의 Subgraph를 호출
       ↓                         │
     W3-T4 (weekly_report)       │
       ↓                         │
     W3-T5 (search_meetings)     │
       ↓                         │
     W3-T6 (analyze_meeting)     │
       ↓                         │
     W3-T7 (assistant_ask) ←─────┘   ※ 나머지 10개 필요
       ↓
     W3-T9 (증빙)
```

**병렬 가능성** W3-T2(보조 5종)는 W3-T1 직후 T3~T6과 병렬로 진행할 수 있다. 나머지는 난이도 순서상
직렬이 안전하다 — 앞 Skill에서 세운 패턴을 뒤에서 재사용한다.
