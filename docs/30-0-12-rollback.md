# W0-12 — 롤백·중단 기준

> [30-0-w0-baseline.md](30-0-w0-baseline.md) §12의 상세 문서.

## 1. 롤백 대상이 없다

W0는 **코드를 수정하지 않는다.** 따라서 롤백할 것이 원칙적으로 없다.

| 산출물 | 롤백 |
| --- | --- |
| 테스트 실행 결과 | 해당 없음(측정) |
| 증빙 문서 | revert 가능 |
| 환경 복구 | 되돌릴 이유 없음 |
| **미커밋 변경 커밋 2건** | **revert 가능하지만 하지 않는다**(§2) |
| 테스트 DB 컨테이너 | `docker rm` |

## 2. 커밋 2건을 되돌리지 않는 이유

W0에서 `274c204`·`8043c1e` 두 커밋을 만들었다. 이것을 revert하면

| 결과 | 설명 |
| --- | --- |
| 미커밋 상태로 복귀 | 원래 문제로 돌아간다 |
| 기준 Commit 불명확 | W0-R3 미충족 |
| **W1 스냅샷 기준이 달라짐** | 이미 스냅샷을 떴다면 전부 무효 |

**사용자 결정으로 만든 커밋이고, 기준선의 일부다.** 되돌리려면 사용자 판단이 필요하다.

### 2.1 만약 되돌려야 한다면

```
1. 사용자 확인
2. git revert 274c204 8043c1e  (또는 reset)
3. 기준 Commit을 6a87c80으로 재정의
4. 기준선 재측정
5. **W1 스냅샷이 있다면 전부 재작성**
```

5번이 비싸다. W1 이후에는 사실상 불가능하다.

## 3. 중단 기준

### 3.1 전환 자체를 착수하지 않는 경우

**W0-V1(전체 테스트)이 FAIL이면 전환을 시작하지 않는다.**

| 이유 | 설명 |
| --- | --- |
| 비교 기준이 없다 | 깨진 상태를 기준선으로 쓸 수 없다 |
| 원인 분리 불가 | 전환 후 실패가 "원래 그랬는지 전환 때문인지" 모른다 |
| 회귀 판정 불가 | W1 스냅샷도 깨진 동작을 기록하게 된다 |

**실제로는 발생하지 않았다** — 440건 전부 통과했다.

### 3.2 사용자 판단이 필요했던 경우 (실제 발생)

| 상황 | 처리 |
| --- | --- |
| 미커밋 변경 발견 | 질문 → "로컬 커밋으로 고정" |
| SKIP 12건 | 질문 → "지금 구성해서 기준선에 포함" |

**둘 다 중단이 아니라 질문이었다.** 검증은 PASS였고, 작업 범위의 결정이 필요했을 뿐이다.

### 3.3 자동 재작업으로 처리한 경우 (실제 발생)

| 상황 | 처리 |
| --- | --- |
| venv 깨짐 | 자동 복구 |
| `uv venv`가 `--clear` 요구 | 플래그 추가 |
| 파이프가 exit code를 가림 | 명령 수정 후 재실행 |

**`AGENTS.md`의 자동 재시도 범위** — "명령의 작업 디렉터리·환경 변수 전달·일시적인 실행 환경처럼
결과 계약을 바꾸지 않는 수정".

### 3.4 인정하지 않는 해결 방법

W0에서는 발생하지 않았지만, 원칙으로 기록한다.

| 금지 | 이유 |
| --- | --- |
| **실패하는 테스트를 건너뛰게 설정** | `AGENTS.md` 금지. 기준선 왜곡 |
| 코드를 고쳐서 통과시킴 | 측정 단계의 원칙 위반 |
| 의존성 버전을 바꿔서 해결 | 기준선이 다른 환경의 것이 됨 |
| SKIP을 PASS로 간주 | 불완전한 기준선 |
| 발견한 문제를 고침 | 기준선 왜곡 |

## 4. 재개 조건

W0는 완료됐으므로 재개 대상이 아니다. 다만 **기준선을 다시 측정해야 할 상황**이 있다.

| 상황 | 조치 |
| --- | --- |
| 오랜 기간 후 전환 재개 | 재측정하고 차이를 기록 |
| 환경이 크게 바뀜 | 동상 |
| **기준 Commit이 바뀜** | 재측정 + **W1 스냅샷 재작성** |
| 기준선 결과가 의심스러움 | 재측정 |

### 4.1 재측정 절차

```
1. 새 run_id 생성 (YYYYMMDD-HHMMSS)
2. 기존 증빙은 그대로 두고 새 result.md 작성
3. 차이가 있으면 원인 기록
4. evidence/langgraph/README.md의 최신 승인 실행 갱신
5. 이후 단계에 영향 여부 판단
```

**기존 증빙을 덮어쓰지 않는다**(`AGENTS.md`).

## 5. 테스트 DB 정리

전환이 끝난 뒤 테스트 컨테이너를 정리할 수 있다.

```bash
docker rm -f workmate-test-pg
```

**단 전환 기간 중에는 유지한다.** 모든 단계가 이 DB를 쓴다.

### 5.1 재생성이 필요한 경우

| 상황 | 이유 |
| --- | --- |
| W2·W4에서 Checkpointer 테이블 스키마가 꼬임 | 깨끗한 상태에서 다시 |
| W7 Migration 검증 | 001~006 적용 → 007 적용 순서 확인 |
| 테스트 간 상태 오염 | 격리 실패 시 |

```bash
docker rm -f workmate-test-pg
docker run -d --name workmate-test-pg \
  -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=workmate_test \
  -p 55432:5432 pgvector/pgvector:pg16
```

## 6. W0가 남긴 롤백 착지점

W0 자체는 롤백 대상이 없지만, **이후 단계의 롤백 착지점을 만들었다.**

| 착지점 | 역할 |
| --- | --- |
| 기준 Commit `8043c1e` | 전환 전체를 되돌릴 지점 |
| 기준선 440 passed | 되돌린 뒤 확인할 기준 |
| 환경 정의 | 재현 방법 |

### 6.1 전환 전체 롤백

가장 극단적인 경우다.

```
1. feat/lg-rewrite 브랜치를 버린다 (또는 merge 후 revert)
2. 기준 Commit 8043c1e 상태 확인
3. 기준선 재실행 → 440 passed 확인
```

**W7 이후에는 Migration이 적용돼 있어 DB만 다르다.** 코드는 완전히 복원된다.

## 7. W0 특유의 주의

### 7.1 "측정만 하는 단계"가 아니었다

W0는 코드를 안 고친다는 점에서 안전하지만, **결정을 두 번 했다.**

| 결정 | 영향 |
| --- | --- |
| 미커밋 변경 커밋 | 기준 Commit 확정 |
| Postgres 구성 | 기준선의 범위 |

**이 결정들이 전환 전체의 전제가 된다.** 가볍게 넘기지 않는다.

### 7.2 기준선은 한 번만 만든다

빅뱅 전환에서 기준선을 여러 번 갱신하면 "무엇과 비교하는지"가 흐려진다.

```
점진 전환: 단계마다 기준선 갱신
빅뱅 전환: 하나의 기준선을 끝까지
```

따라서 W0에서 **완전한 기준선**을 만드는 것이 중요했다. SKIP 12건을 방치하지 않은 이유다.

### 7.3 발견은 기록하되 고치지 않는다

W0에서 세 가지를 발견했고 전부 기록만 했다. 고쳤다면

| 발견 | 고쳤다면 |
| --- | --- |
| W0-F1 (`save_checkpoint` 미사용) | 그 자리에서 제거 → 기준선이 달라짐 |
| W0-F2 (`external_sync` 호출자 부재) | 삭제 → 증빙 링크 파손 |

**측정 단계의 원칙이 이 둘을 막았다.**
