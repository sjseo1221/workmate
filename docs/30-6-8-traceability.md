## 6. 단계 간 준비 추적

W6이 가능한 것은 앞 단계들이 준비해 둔 덕분이다.

| 준비 | 단계 | W6에서의 쓰임 |
| --- | --- | --- |
| Checkpointer 생성 | [W2-R7](30-2-4-requirements.md) | `interrupt`의 저장소 |
| `build_pending_action_reply` 독립 노드 | [W3-D5](30-3-5-design.md) §6 | **교체 대상 한 노드** |
| 확인 흐름 동결(변경 금지) | [W3-R11](30-3-4-requirements.md) | 스냅샷 대조 가능성 유지 |
| Checkpointer Graph 결합 | [W4-R8](30-4-4-requirements.md) | `interrupt` 성립 |
| 운영 경로가 Graph | [W5-R1~R3](30-5-4-requirements.md) | 실제 요청이 `interrupt`를 탄다 |
| 오류 매핑 유지 | [W5-R6](30-5-4-requirements.md) | `INPUT_REQUIRED`도 같은 경로 |
| 비동기 폴링 구조 | [W5-R3](30-5-4-requirements.md) | UI 분기를 추가할 지점 |

**W3-D5가 특히 효율적이었다.** 노드 경계를 미리 나눠 둔 덕에 W6의 코드 변경이 한 노드 교체로
제한된다.

## 8. 의도적 변경 누적 추적

W9의 "의도적 변경" 목록이 단계마다 쌓인다. W6에서 최종 형태가 된다.

| 단계 | 변경 | 스냅샷 검출 | 전용 검증 |
| --- | --- | --- | --- |
| W3 | 숨은 부작용 유지(변경 아님, 보존 결정) | ✗ | W3-V11 |
| W4 | 멱등성 실제 구현(W4-D1) | ✗ | W4-V3 |
| W4 | `runtime_bootstrap` 미등록 처리(W4-D3) | ✗ | W4-V2-3 |
| W4 | 진행 중 중복 정책 정의(W4-D5) | ✗ | W4-V3-6 |
| W5 | 멱등성이 외부에 노출 | ✗ | W5-V1-4 |
| **W6** | **확인 프로토콜 개편(C1~C5)** | **✓ 2건** | W6-V1~V6 |
| W6 | UI REST 멱등성 비대칭 유지(W5-D3) | ✗ | 기록만 |

**W6만 스냅샷으로 검출된다.** 나머지는 전부 전용 검증이 필요했다. 이것이 스냅샷의 한계를 보여준다.

## 9. 매트릭스 유지 규칙

1. 계약 항목(C1~C5)이 변경되면 §2 매트릭스의 영향 범위를 다시 그린다. 특히 Route 영향.
2. **§8의 의도적 변경 목록은 W9의 입력이다.** 빠짐없이 등록한다.
3. 검증이 FAIL이면 §4에서 "기능은 되는데 위험한" 유형인지 먼저 본다.
4. 식별자는 재사용하지 않는다.
