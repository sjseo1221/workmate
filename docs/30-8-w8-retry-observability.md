> **W8의 특징 셋.**
> (1) **재시도 정책이 하나가 아니다.** `assistant_router`는 3회·네트워크만, `weekly_report`는
> 2회·429·5xx 포함. **통일하지 않고 각각 보존**한다 — 통일은 동작 변경이다.
> (2) **부작용 노드에 재시도를 붙이면 안 된다.** Task 중복 생성·승인 중복 처리를 낳는다. W3에서
> 만든 부작용 노드 목록이 제외 대상이며, 이 단계의 핵심 산출물은 코드가 아니라 **재시도 적용표**다.
> (3) **위험의 다수가 "과도한 안정화"에서 온다** — 모든 노드에 재시도, 여러 계층에서 재시도, 정책
> 통일. 적절한 곳에만 붙이는 것이 요점이고, **계측이 유일한 검증 수단**이다.

## 2. 목적과 범위

### 2.1 목적

노드 단위 실패 격리와 재시도 정책을 Graph의 기능으로 정리하고, 실행을 들여다볼 수 있게 만든다.
W2에서 정의한 재시도 정책을 **전 노드에 일관되게 적용**하는 것이 핵심이다.

### 2.2 범위 내

- 노드 `RetryPolicy` 적용과 재시도 경계 정리
- Provider 실패 분류(재시도 가능/불가, 부분 결과/전체 실패)
- 노드 단위 실행 로그

### 2.3 범위 외

- 스트리밍(`astream`) 전환 — D5=A로 전환 후 별건
- LangSmith 등 외부 트레이싱 — API Key 필요, 별도 승인
- 새 Provider 추가

## 5. 설계

### 5.1 재시도 경계 (3계층)

96번 §8이 정의하는 계층을 혼동하지 않는 것이 요점이다.

| 계층 | 주체 | 재시도 대상 | 멱등성 근거 |
| --- | --- | --- | --- |
| HTTP 요청 전체 | Orchestrator | 요청 실패 | 같은 `message_id` |
| 노드 | LangGraph `RetryPolicy` | 노드 내 Provider 호출 | 노드 재실행이 안전해야 함 |
| Provider Client | 없음 | — | 클라이언트 내부 재시도는 두지 않는다 |

**노드 재시도의 전제:** 재시도 대상 노드는 부작용이 없거나 멱등해야 한다. 외부 상태를 바꾸는 노드
(Task 생성, Action Item 승인)에는 `RetryPolicy`를 붙이지 않는다.

### 5.2 오류 분류

```python
def _is_network_error(exc: BaseException) -> bool:
    """재시도 가능한 네트워크 계층 오류인지 판정한다.

    HTTP 응답을 받은 오류(4xx/5xx)는 재시도해도 같은 결과이므로 제외한다 —
    2026-08-19 Windows 환경 DNS 간헐 실패 대응에서 확정한 구분이다.
    """
```

| 부류 | 예 | 처리 |
| --- | --- | --- |
| 네트워크 | DNS 실패, 연결 끊김, Timeout, 응답 파싱 실패 | 재시도(최대 3회) |
| HTTP 4xx | 400, 401, 403, 404 | 즉시 실패. 401/403은 `AUTH_REQUIRED` 후보 |
| HTTP 5xx | 500, 502, 503 | 즉시 실패 |
| 인증 | Provider 재인증 필요 | `AUTH_REQUIRED` |
| 취소 | 취소 감지 | `CANCELED` |

> HTTP 429(rate limit)는 현재 구현이 재시도하지 않는다. 이번 전환에서 동작을 바꾸지 않는다 —
> 변경하려면 별도 백로그로 분리한다.

### 5.3 실패 파급 규칙 (W8-R4)

| Skill | 핵심 소스 실패 | 보조 소스 실패 |
| --- | --- | --- |
| `daily_briefing` | Task 저장소 → 전체 실패 | Gmail·Calendar → `warnings` 후 부분 결과 |
| `weekly_report` | Task·근거 조회 → 전체 실패 | LLM → 근거 기반 부분 결과 |
| `analyze_meeting` | STT·분석 → 전체 실패 | 색인(embedding/pgvector) → 재시도 가능 `warnings` |
| `search_meetings` | 검색 → 전체 실패 | reranker → RRF 결과 + `warnings` |

이 규칙은 새로 만드는 것이 아니라 현재 구현의 동작을 명문화한 것이다. W1 스냅샷의 부분 실패 케이스가
수용 기준이 된다.

### 5.4 관측

```python
# 노드 실행 로그 항목
{"node": "fetch_gmail", "thread_id": "...", "elapsed_ms": 412,
 "status": "warning", "warning_code": "GMAIL_UNAVAILABLE", "retry_count": 1}
```

- `user_id`는 로그에 남기되 메일 본문·토큰·Presigned URL은 남기지 않는다(W8-R7).
- LangSmith 도입은 범위 밖이다. 표준 로깅으로 충분한 수준까지만 한다.

## 9. 완료 정의 (Exit criteria)

1. W8-V1~V10 전부 PASS.
2. **W8-V2(HTTP 4xx/5xx 비재시도)가 PASS** — 계획서 §9-6 완료 조건이자 D3=B의 최대 위험 해소 증거.
3. 재시도가 노드 계층에만 존재하고 Provider Client·노드 내부에 중복 루프가 없다.

## 10. 위험과 완화

| 위험 | 영향 | 완화 |
| --- | --- | --- |
| 라이브러리 기본 재시도가 남아 이중 재시도 | 장애 시 지연이 곱으로 증가 | W2에서 `max_retries=0`, W8-V3로 계측 |
| 부작용 노드에 재시도가 붙어 중복 실행 | Task 중복 생성, 승인 중복 | W8-T2 적용표 + W8-V7 |
| 부분 실패가 전체 실패로 승격 | 사용 가능한 결과를 버림 | W8-V4, W1 스냅샷 부분 실패 케이스 |
| 로그에 메일 본문·토큰 유출 | 보안 사고 | W8-V8 전수 검사 |

## 11. 롤백·중단 기준

- W8은 정책·로깅 변경이라 revert 비용이 낮다.
- **중단 기준:** W8-V2가 PASS하지 않으면 W9(완료 선언)로 진행하지 않는다. 이 항목은 완료 기준에
  명시된 필수 조건이다.
