## W2-K1 — 의존성 충돌

**설명** `langchain-openai`·`langgraph-checkpoint-postgres`의 전이 의존성이 기존 고정 버전
(`a2a-sdk==1.1.2`, `fastapi==0.116.1`, `psycopg[binary]==3.2.10`, `jsonschema==4.26.0`)과 충돌하거나,
해결 과정에서 기존 버전을 밀어 올린다.

**징후** `uv add` 실패, 또는 `uv.lock` diff에 기존 고정 패키지의 버전 변경이 나타남.

**영향** 전환 전체가 막힌다. 기존 버전이 밀려 올라간 경우 A2A 계약이 조용히 깨질 수 있다.

**완화**
- W2-T1을 **가장 먼저** 수행해 조기 판정
- `uv.lock` diff에서 기존 고정 버전 불변을 명시적으로 확인
- 밀려 올라갔다면 `AGENTS.md`에 따라 M0.1 Contract Test 재실행

**대응 계획(발생 시)** 해결 불가하면 사실을 보고하고 D3 재검토를 요청한다. **임의로 A안(urllib 유지)
으로 되돌리지 않는다** — 확정 결정의 변경은 사용자 권한이다.

**트리거** `uv add` 실패 또는 기존 고정 버전 변경 검출

## W2-K2 — 라이브러리 기본 재시도 잔존

**설명** `ChatOpenAI`의 기본 재시도를 끄지 못하거나, 껐다고 생각했지만 실제로는 동작해서
HTTP 4xx/5xx까지 재시도한다.

**영향** 2026-08-19에 고친 회귀가 재발한다. 장애 시 지연이 정책상 3회 × 라이브러리 재시도만큼
곱으로 증가한다.

**왜 발생하기 쉬운가** `max_retries=0`을 설정해도 내부 HTTP 클라이언트(`httpx`)나 OpenAI SDK 계층에
별도 재시도가 있을 수 있다. 설정값만 보고 "껐다"고 판단하면 놓친다.

**완화**
- `max_retries=0` 명시
- **W2-V7-10에서 실제 HTTP 호출 횟수를 계측**한다. 설정 확인이 아니라 호출 계측이 유일한 검증 수단이다
- W8에서 전 노드 적용 시 재확인

**대응 계획** 라이브러리 수준에서 끌 수 없으면 HTTP 계층을 직접 주입(커스텀 `http_client`)해서 끈다.

## W2-K3 — 구조화 출력 동작 차이

**설명** `with_structured_output()`이 현재의 `response_format: json_schema` strict와 다르게 동작한다.
LangChain은 모델·Provider에 따라 function calling / json_mode / json_schema 중 하나를 선택하는데,
어느 것이 선택되는지에 따라 응답 구조나 실패 방식이 달라진다.

**영향** Router가 `skill_id`·`arguments`를 결정하는 경로가 깨지면 `assistant_ask` 전체가 실패한다.
조용히 다른 구조를 반환하면 W3에서야 드러난다.

**완화**
- W2-V6 동등성 테스트를 **W3 착수 전에** 통과시킨다
- `method`를 명시적으로 지정해 자동 선택에 맡기지 않는다
- strict 유지 여부를 확인하고, 유지되지 않으면 사후 스키마 검증을 대체 수단으로 구현

**대응 계획** 동등성을 확보하지 못하면 해당 호출 지점만 기존 방식을 유지하는 혼합 구성을 검토하고,
그 사실을 증빙에 기록한다. 범위를 넘는 판단이면 사용자에게 보고한다.

---

## W2-K4 — Checkpointer·Task Store 책임 혼재

**설명** Checkpointer가 Task 상태를 쓰거나, Task Store가 노드 State를 담는다.

**영향** 장애 복구 시 어느 저장소가 진실인지 판정할 수 없다. 96번 §10 경계가 무너진다.

**왜 발생하기 쉬운가** 둘 다 `thread_id`/`task_id`를 다루고, 둘 다 "상태를 저장"하므로 편의상 한쪽에
몰아넣고 싶어진다. 특히 W6의 `interrupt` payload를 어디에 둘지에서 혼동이 생긴다.

**완화**
- 96번 §10 경계표를 W2-T6 설계 검토 항목으로 고정
- **W2-V4-5·V4-6에서 교차 쓰기가 없음을 테스트로 확인** — 설계 검토만으로는 부족하다

**대응 계획** 경계 침범이 발견되면 W2에서 바로잡는다. W4·W6까지 끌고 가면 되돌리기 어려워진다.

## W2-K5 — Windows Event Loop 충돌

**설명** 비동기 Checkpointer(`AsyncSqliteSaver`·`AsyncPostgresSaver`)가
[main.py](../workmate-agent/app/main.py)의 Selector Event Loop 정책·IPv4 강제 설정과 충돌한다.

**배경** 현재 코드는 Windows 환경에서 Selector Event Loop를 강제하고 `_ipv4_only_getaddrinfo`로
IPv4를 강제한다. 둘 다 실사용 중 발견된 문제의 대응이다.

**영향** 로컬 개발 환경에서 Graph 실행이 불가하거나 간헐 실패한다.

**완화**
- 기존 설정을 유지한 채 W2-T7에서 실제 저장·복원을 확인
- SQLite·Postgres 양쪽 모두 확인(드라이버가 다르므로 한쪽만으로는 부족)

**대응 계획** 충돌하면 Checkpointer 연결 생성 시점·수명을 조정한다. 기존 Event Loop 설정은 **바꾸지
않는다** — 그쪽이 더 오래된 실사용 대응이다.

## W2-K6 — 재시도 정책 불일치 간과

**설명** 현재 재시도 정책이 두 종류라는 사실([30-2-5](30-2-5-design.md) §5.2)을 놓치고 하나로
통일한다.

| 지점 | 시도 | 재시도 대상 |
| --- | --- | --- |
| `assistant_router` | 3 | 네트워크만, HTTP 오류 제외 |
| `weekly_report` | 2 | `LLMProviderError` — timeout·429·5xx·Schema 포함 |

**영향** `weekly_report`의 동작이 바뀌어 W1 스냅샷의 부분 실패 케이스가 깨진다. 그 차이는 "의도한
변경"으로 설명해야 하는데, 의도한 적이 없으므로 회귀다.

**완화**
- `llm.py`에 RetryPolicy를 **두 종류** 정의
- W2-V7을 정책별로 나눠 검증(V7-1~V7-7 / V7-8~V7-9)
- 상위 계획서 §9-6 서술을 정밀화([30-2-9](30-2-9-exit-criteria.md) §2.5)

**대응 계획** 정책 통일이 바람직하더라도 이번 범위가 아니다. W9에서 후속 백로그로 기록한다.

## W2-K7 — State에 Secret 영속화

**설명** State에 담긴 값이 Checkpointer를 통해 DB에 저장된다. 지금까지 메모리에만 있던 Token·메일
본문·Presigned URL이 디스크에 남는다.

**왜 W2에서 새로 생기는가** 기존 구조에는 노드 간 공유 State가 없었다. Workflow 함수의 지역 변수는
함수가 끝나면 사라졌다. W2 이후에는 State에 넣는 순간 영속화 대상이 된다.

**영향** 보안 사고. `AGENTS.md` 금지 사항 위반.

**완화**
- W2-V9-1·V9-2에서 State 직렬화 결과와 Checkpoint 저장 내용을 모두 검사
- 큰 개인정보(메일 본문·녹취 원문)는 State에 싣지 않고 식별자로 참조하는 설계 규칙을 W3에 전달

**대응 계획** 발견 시 해당 필드를 State에서 제거하고, 필요하면 조회 함수로 대체한다.

---

## W2-K8 — State 스키마 미확정으로 W3 재작업

**설명** State 필드나 Reducer 규칙이 W3 중간에 바뀌어, 이미 만든 Skill Subgraph를 다시 손봐야 한다.

**영향** 최악의 경우 Skill 11개를 모두 수정한다. W3은 전환에서 가장 큰 단계이므로 손실이 크다.

**완화**
- State는 96번 §3을 **그대로** 구현하고 이번에 임의 추가·삭제하지 않는다
- W3 착수 전 W2-V1~V3을 통과시켜 기반을 고정
- W3에서 State 변경이 필요해지면 **한 Skill에서 먼저 검증**한 뒤 확산

**대응 계획** 불가피한 변경이면 이미 만든 Subgraph의 수정 범위를 먼저 산정하고, 변경 사유와 범위를
증빙에 기록한다.
