# W3-11 — 롤백·중단·재개 기준

> [30-3-w3-skill-subgraphs.md](30-3-w3-skill-subgraphs.md) §11의 상세 문서.

## 1. 롤백 비용

W3은 **신규 파일 추가만** 한다. 기존 `app/workflows/`는 그대로 살아 있고 운영 경로도 바뀌지 않는다.
따라서 롤백 비용이 낮다.

| 산출물 | 롤백 방법 | 비용 |
| --- | --- | --- |
| `app/graph/skills/*` | 파일 삭제 또는 커밋 revert | 낮음 |
| `tests/test_graph_skill_*.py` | 동일 | 낮음 |
| 부작용 노드 목록 등 문서 | 문서 revert | 낮음 |

**주의:** W3-V11 검증 과정에서 테스트 DB에 데이터가 쌓인다. 롤백 후 재시도 시 이전 상태가 결과에
영향을 줄 수 있으므로(특히 `rank_priorities`의 `changes` 계산) 테스트 DB를 초기화한다.

## 2. Skill 단위 롤백

W3의 가장 큰 장점은 **Skill 단위로 되돌릴 수 있다**는 점이다.

| 롤백 단위 | 영향 | 남는 것 |
| --- | --- | --- |
| Skill 1개 | 그 Skill만 미완료 | 나머지 10개 유효 |
| `rank_priorities` | `daily_briefing`도 무효(의존) | 나머지 9개 유효 |
| `assistant_ask` | 그 Skill만 | 나머지 10개 유효 |
| W3-T0 설계 | 전부 재검토 가능성 | — |

`rank_priorities`와 `assistant_ask`가 의존 관계의 양 끝이다. 전자는 `daily_briefing`이 의존하고,
후자는 나머지 전부에 의존한다.

## 3. 중단 기준

### 3.1 즉시 중단 — 사용자 판단 필요

| 조건 | 사유 | 처리 |
| --- | --- | --- |
| **스냅샷 차이가 "의도적 변경"으로 판정됨** | W3에서 의도적 변경은 원칙적으로 없어야 한다 | 차이 내용과 근거를 보고하고 판단을 받는다 |
| **범위 밖 모듈 수정이 불가피** | 범위 확대 | [30-3-2](30-3-2-scope.md) §5의 절차 |
| **W3-D1(부작용 방침) 재검토 필요** | 설계 결정 변경 | 보고 후 판단 대기 |
| Domain 규칙을 바꿔야 결과가 맞음 | 결정적 규칙 변경은 별도 승인 대상 | 보고 |

### 3.2 자동 재작업 — 사용자 질문 없이 진행

| 조건 | 처리 |
| --- | --- |
| 이식 오류(값 유실, 노드 순서 오류) | 수정 후 재대조 |
| 스냅샷 정규화 누락 | W1 정규화 보완 + **이유 기록** |
| 테스트 Fixture 설정 오류 | 수정 후 재시도 |
| 실행 환경 문제(컨테이너·경로) | 보정 후 재시도 |
| `user_id` 조건 누락 | 즉시 수정 + 같은 패턴 전수 점검 |

다음은 해결 방법으로 인정하지 않는다(`AGENTS.md` 금지).

- 스냅샷 기대값을 새 구현에 맞춰 수정
- 실패한 테스트 삭제·우회
- 부분 실패 정책을 완화해 통과시키기
- **경고를 추가해 "조용히 무시" 케이스를 바꾸기** — 개선처럼 보이지만 동작 변경이다

### 3.3 Skill 단위 중단

| 조건 | 처리 |
| --- | --- |
| 같은 Skill의 스냅샷 대조가 **서로 다른 원인으로 3회 이상** 실패 | 그 Skill의 노드 분해 설계를 W3-T0으로 되돌려 재설계 |
| `assistant_ask`의 분할 단위에서 막힘 | 해당 노드만 기존 함수 호출로 임시 처리하고 나머지 완성. 단 그 상태로 W3 완료 금지 |

## 4. 재개 조건

| 중단 사유 | 재개 조건 |
| --- | --- |
| 의도적 변경 판정 | 사용자가 변경을 승인하고 스냅샷 갱신 방침을 확정 |
| 범위 확대 | 사용자 승인 |
| W3-D1 재검토 | 부작용 방침 확정 |
| 설계 재검토(3회 실패) | 새 노드 분해안 확정 |

재개 시 [30-3-3](30-3-3-entry-criteria.md)의 선행 조건을 다시 확인한다. 특히 W3-E1(스냅샷 PASS)은
중단 기간 중 W1 정규화를 건드렸다면 다시 검증해야 한다.

## 5. 에스컬레이션 경로

```
Skill 스냅샷 대조 FAIL
  │
  ├─ 이식 오류 / 정규화 누락
  │    → 자동 재작업 (사용자 질문 없음)
  │    → 재대조 PASS → 다음 Skill
  │    → 같은 Skill 3회 실패 → 설계 재검토(W3-T0)
  │
  ├─ 의도적 변경으로 보임
  │    → 중단, 사용자 보고
  │
  └─ 범위 밖 수정이 필요
       → 중단, 범위 변경 절차

W3-V3 (user_id) FAIL
  → 즉시 수정 + 같은 패턴 전수 점검
  → W3 전체를 미완료로 유지

W3-V11 (숨은 부작용) FAIL
  → W3-D1 재확인
  → 방침 변경이 필요하면 사용자 보고
```

## 6. 중단 시 기록 의무

`AGENTS.md`에 따라 사유를 남긴다. W3은 Skill 단위 진행이므로 **어디까지 됐는지**를 함께 기록한다.

```
## 9. 최종 판단
- 승인 여부: 보류
- 자동 진행 판정: 중단 / 보류
- 자동 진행 보류 사유: (구체적으로)
- 완료된 Skill: (목록)
- 미완료 Skill: (목록과 각각의 사유)
- 판정을 막은 검증: W3-Vx / Skill명
- 시도한 해결 방법: (후보별 결과)
- 필요한 조치·승인: (내용)
- 재개 조건: (조건)
- 다음 구현 백로그: W3-Tx
```

## 7. 롤백하지 않는 것

| 항목 | 이유 |
| --- | --- |
| W0 기준 Commit | 전환의 출발점 |
| W1 계약 스냅샷 | 옛 구현이 살아 있을 때만 만들 수 있다. 폐기하면 복구 불가 |
| W2 산출물(State·어댑터·Checkpointer·LLM) | W3 전체의 기반. 되돌리면 W3도 전부 무효 |
| **`app/workflows/`** | W7까지 비교 대상. W3에서 지우면 검증 수단이 사라진다 |
| 기존 440개 테스트 | 동상 |

## 8. W3 특유의 주의

### 8.1 "잘 되는 것처럼 보이는" 실패

W3에는 검증을 통과하면서도 틀린 상태가 두 가지 있다.

| 유형 | 왜 통과하나 | 잡는 방법 |
| --- | --- | --- |
| 숨은 부작용 소실 | 응답에 드러나지 않음 | W3-V11 (DB 직접 검증) |
| `user_id` 누락 | Fixture에 타 사용자 데이터가 없으면 통과 | W3-V3 (혼입 시나리오) |

둘 다 **전용 검증을 설계하지 않으면 영원히 통과한다.** 중단 기준에서 이 둘을 특별 취급하는 이유다.

### 8.2 부분 완료로 W4에 가지 않는다

Skill 11개 중 10개만 끝난 상태로 W4를 시작할 수 없다. Root Graph는 11개 전부를 라우팅 대상으로
가지므로, 하나가 없으면 라우팅 검증(W4-V1)이 성립하지 않는다.
