# W1-11 — 롤백·중단·재개 기준

> [30-1-w1-contract-snapshot.md](30-1-w1-contract-snapshot.md) §11의 상세 문서.

## 1. 롤백 비용

W1 산출물은 **`tests/` 아래 신규 파일뿐**이다. `app/`은 한 줄도 바뀌지 않는다(W1-R5). 전환 10단계 중
롤백 비용이 가장 낮다.

| 산출물 | 롤백 방법 | 비용 |
| --- | --- | --- |
| `tests/contracts/*` | 디렉터리 삭제 또는 커밋 revert | 매우 낮음 |
| 증빙 문서 | revert | 낮음 |

### 1.1 그러나 "다시 만들 수 있는 기한"이 있다

롤백 자체는 싸지만, **W7 이후에는 다시 만들 수 없다.**

```
W0 ─ W1 ─ W2 ─ W3 ─ W4 ─ W5 ─ W6 ─ W7(app/workflows 삭제) ─ W8 ─ W9
     └────────── 재작성 가능 구간 ──────────┘
```

따라서 W1을 롤백할 때는 "나중에 다시 하면 된다"가 아니라 "언제까지 다시 해야 하는가"를 함께 정한다.

## 2. 부분 롤백

케이스 단위로 되돌릴 수 있다.

| 롤백 단위 | 영향 | 남는 것 |
| --- | --- | --- |
| 케이스 1건 | 그 시나리오만 미검증 | 나머지 유효 |
| Skill 전체 케이스 | 그 Skill이 W3에서 무방비 | 나머지 Skill 유효 |
| 정규화 규칙 1종 | 해당 규칙을 쓰는 케이스가 간헐 실패 | — |
| 하네스 | **전부 무효** | — |

`_harness.py`가 단일 실패점이다. 그래서 W1-T3을 케이스 작성보다 먼저 하고, 충분히 검증한다.

## 3. 중단 기준

### 3.1 즉시 중단 — 사용자 판단 필요

| 조건 | 사유 | 처리 |
| --- | --- | --- |
| **W1-V6 FAIL (운영 코드 변경됨)** | W1의 전제 붕괴 | 변경 내용을 확인하고 되돌린다. 불가피했다면 이유를 보고 |
| **스냅샷 불가 Skill이 3개 초과** | 안전망의 1/4 이상이 빔 | 보고 후 판단([30-1-9](30-1-9-exit-criteria.md) §4.2) |
| 금지 목록 값이 비결정적 | 점수·순위가 실행마다 다르다면 그 자체가 문제 | 원인 조사 후 보고 |
| 기존 440건이 깨짐 | 하네스가 전역 상태를 오염 | 원인 제거. 해결 안 되면 보고 |

### 3.2 자동 재작업 — 사용자 질문 없이 진행

| 조건 | 처리 |
| --- | --- |
| 정규화 누락으로 간헐 실패 | 원인 필드 추가 + **이유 기록**. 최대 3회 |
| 케이스 Fixture 설정 오류 | 수정 후 재시도 |
| 실행 환경 문제(컨테이너·경로) | 보정 후 재시도 |
| 하네스 버그 | 수정 후 재시도 |
| 전역 상태 오염 | 격리·정리 보완 |

다음은 해결 방법으로 인정하지 않는다.

| 금지 | 이유 |
| --- | --- |
| **금지 목록 값을 정규화** | 점수·순위·`warnings.code` 등은 회귀로 잡아야 한다 |
| 실패하는 케이스를 삭제 | `AGENTS.md` 금지 |
| 정규화를 이유 없이 추가 | W1-V8 FAIL |
| `app/`을 고쳐 결정성 확보 | W1-R5 위반 |

### 3.3 Skill 단위 중단 — 조건부 완료

특정 Skill의 결정성을 3회 보완으로도 확보하지 못하면, 무리하지 않고 기록한다.

```
스냅샷 불가 Skill: <skill_id>
사유:              (어떤 값이 왜 결정적이지 않은가)
시도한 정규화:      (3회의 시도와 결과)
대체 검증:          W3에서 사람이 직접 비교 / 기존 테스트로 대체
영향:              W3-E1의 예외 항목
```

**3개를 넘으면 조건부 완료가 아니라 중단이다**(§3.1).

## 4. 재개 조건

| 중단 사유 | 재개 조건 |
| --- | --- |
| 운영 코드 변경 | 변경을 되돌리거나 사용자가 승인 |
| 스냅샷 불가 3개 초과 | 대체 검증 방침 확정 |
| 금지 목록 값 비결정 | 원인 해소 |
| 기존 테스트 깨짐 | 오염 제거 확인 |

재개 시 [30-1-3](30-1-3-entry-criteria.md)의 선행 조건을 다시 확인한다. 특히 W1-E1(기준 Commit)과
W1-E5(옛 구현 온전함)는 중단 기간 중 달라졌을 수 있다.

## 5. 에스컬레이션 경로

```
스냅샷 대조 FAIL
  │
  ├─ 정규화 누락 (실행마다 다름)
  │    → 원인 필드 추가 + 이유 기록
  │    → 3회 반복 → Skill 단위 조건부 완료
  │
  ├─ 케이스 Fixture 오류
  │    → 수정 후 재시도
  │
  └─ 금지 목록 값이 다름 (점수·순위 등)
       → 정규화 금지. 원인 조사
       → 원인이 환경이면 보정
       → 원인이 구현이면 **중단하고 보고** — 기준선 자체가 불안정하다는 뜻

W1-V6 FAIL (app/ 변경됨)
  → 즉시 중단, 변경 확인, 되돌리기
```

## 6. 중단 시 기록 의무

`AGENTS.md`에 따라 사유를 남긴다. W1은 케이스 단위 진행이므로 **어디까지 됐는지**를 함께 기록한다.

```
## 9. 최종 판단
- 승인 여부: 보류
- 자동 진행 판정: 중단 / 조건부 완료
- 자동 진행 보류 사유: (구체적으로)
- 완료된 케이스: N건 (Skill별 분포)
- 미완료 Skill: (목록과 각각의 사유)
- 시도한 해결 방법: (정규화 시도 3회의 내용과 결과)
- 필요한 조치·승인: (내용)
- 재개 조건: (조건)
- **재작성 기한: W7 착수 전**
- 다음 구현 백로그: W1-Tx
```

`재작성 기한`은 W1 고유 항목이다. 다른 단계에는 없다.

## 7. 롤백하지 않는 것

| 항목 | 이유 |
| --- | --- |
| W0 기준 Commit (`8043c1e`) | 전환의 출발점. 스냅샷이 이 Commit 기준으로 찍힌다 |
| `app/workflows/` | 스냅샷의 대상. 손상되면 W1 자체가 불가 |
| 기존 440개 테스트 | 시나리오의 출처이자 회귀 감시선 |

## 8. W1 특유의 주의

### 8.1 "실패를 없애는 것"이 목표가 아니다

W1에서 스냅샷이 실패하면 두 가지 반응이 가능하다.

| 반응 | 결과 |
| --- | --- |
| 정규화를 늘려 통과시킨다 | 쉽지만 검증력이 사라진다 |
| 왜 결정적이지 않은지 조사한다 | 느리지만 스냅샷이 의미를 갖는다 |

금지 목록(§3.2)이 이 선택을 강제한다. 점수가 실행마다 다르다면 그것은 정규화할 일이 아니라 조사할
일이다.

### 8.2 W1은 "완벽"보다 "존재"가 중요하다

케이스 27건을 다 못 만들더라도, **하네스 + Skill당 1건**만 있으면 W3에서 최소한의 대조가 된다.
반대로 케이스를 아무리 잘 만들어도 하네스가 없으면 쓸 수 없다.

시간이 부족하면 이 순서로 확보한다.

```
1. 하네스 + 정규화        (없으면 아무것도 못 한다)
2. Skill당 정상 케이스 1건 (11건)
3. 부분 실패 케이스        (실패 경로 보호)
4. 입력 오류 케이스
5. 추가 정상 케이스
```
