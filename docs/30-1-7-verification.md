## 2. 검증 케이스 상세

### W1-V1 — 스냅샷 대조

```
uv run python -m unittest tests.contracts.test_contract_snapshots -v
```

| 케이스 | 기대 |
| --- | --- |
| V1-1 | 모든 케이스가 PASS |
| V1-2 | 임의 케이스의 `expected`를 한 글자 바꾸면 FAIL — **대조가 실제로 동작하는지 확인** |
| V1-3 | 차이 보고가 경로 단위로 나온다 |

**V1-2가 중요하다.** 대조 로직에 버그가 있어 항상 통과하면, 전건 PASS가 아무 의미가 없다. 일부러
틀린 기대값을 넣어 FAIL이 나오는지 확인한다(확인 후 되돌린다).

### W1-V2 — 결정성

| 케이스 | 방법 | 기대 |
| --- | --- | --- |
| V2-1 | 전체 대조 2회 연속 실행 | 두 결과 동일 |
| V2-2 | 케이스 실행 순서를 바꿔 실행 | 동일 결과(저장소 격리 확인) |
| V2-3 | 시간이 지난 뒤 재실행(수 분 간격) | 동일 결과 |

**V2-2가 저장소 격리(W1-D4)의 검증이다.** `rank_priorities`가 Snapshot을 저장하므로, 격리가 없으면
실행 순서에 따라 `changes` 값이 달라진다.

**V2-3은 시각 관련 정규화의 검증이다.** `as_of`를 주입하지 않은 케이스가 있으면 몇 분 뒤 실행 시
날짜 경계를 넘어 결과가 달라질 수 있다.

### W1-V3 — Skill 커버리지

```python
{case["skill_id"] for case in all_cases} == set(APPROVED_SKILL_IDS)
```

| 기대 | 값 |
| --- | --- |
| Skill 수 | 11 |
| Skill당 최소 케이스 | 1 |

### W1-V4 — 부류 커버리지

| 부류 | 최소 | 확인 방법 |
| --- | --- | --- |
| 정상 | Skill당 1건 | `description` 또는 메타데이터 |
| 부분 실패 | 전체 3건 이상 | `expected.warnings`가 비어 있지 않은 케이스 |
| 입력 오류 | 전체 2건 이상 | `expected`가 예외를 표현하는 케이스 |

**입력 오류 케이스의 표현:** `ValueError`가 나는 경우 `expected`에 결과 대신 예외 타입과 메시지를
기록한다. 이 메시지는 422 응답의 `detail`이 되므로 공개 계약의 일부다.

```json
"expected": {
  "raises": {"type": "ValueError", "message": "meeting_id is required"}
}
```

### W1-V5 — 기존 테스트 무영향

```
WORKMATE_TEST_DATABASE_URL="postgresql://postgres:postgres@127.0.0.1:55432/workmate_test" \
  uv run python -m unittest discover -s tests -v
```

| 항목 | 기대 |
| --- | --- |
| 기존 440건 | 전부 통과 |
| W1 신규(스냅샷 대조) | 전부 통과 |
| SKIP | 0 |

**W1은 `app/`을 건드리지 않으므로 기존 테스트가 깨질 이유가 없다.** 깨진다면 하네스가 전역 상태
(환경변수·임시 파일)를 오염시키고 있다는 뜻이다.

### W1-V6 — 운영 코드 무변경

```
git diff --stat app/
```

기대: 출력 없음.

**이 검증이 W1의 성격을 정의한다.** 출력이 있다면 측정을 위해 대상을 바꾼 것이고, 스냅샷이 무엇을
기록했는지 불분명해진다.

### W1-V7 — Secret 비포함

| 케이스 | 패턴 | 대상 |
| --- | --- | --- |
| V7-1 | `sk-`, `Bearer `, `ya29.`, `AIza` | 케이스 파일 전체 |
| V7-2 | Presigned URL 형태(`X-Amz-Signature`, `Expires=`) | 동상 |
| V7-3 | 실제 이메일 주소·이름 | Fixture 값이 가짜인지 확인 |

**V7-3 주의:** 기존 테스트 Fixture는 이미 가짜 값을 쓴다
([`work_domain.py`](../workmate-agent/tests/fixtures/work_domain.py)의 UUID 형태 사용자 ID). 새로
만드는 Fixture도 같은 규칙을 따른다.

### W1-V8 — 정규화 목록 완전성

| 케이스 | 방법 | 기대 |
| --- | --- | --- |
| V8-1 | 모든 `normalized_fields` 항목 검사 | `path`·`rule`·`reason` 3개 필드 존재 |
| V8-2 | `reason`이 비어 있지 않음 | 빈 문자열 금지 |
| V8-3 | 금지 대상 정규화 검사 | 점수·순위·`source_refs`·`warnings.code`가 정규화되지 않음 |

**V8-3이 과도한 정규화를 막는 마지막 방어선이다.**
[30-1-5](30-1-5-design.md) §4.2의 금지 목록을 코드로 확인한다.

### W1-V9 — 기록 모드 보호

| 케이스 | 방법 | 기대 |
| --- | --- | --- |
| V9-1 | 환경변수 없이 `record()` 호출 | 거부(예외 또는 no-op) |
| V9-2 | 일반 unittest 실행 | 케이스 파일이 변경되지 않음(mtime 확인) |

## 3. 검증 실행 순서

```
W1-T3 (하네스) 완료 후:
  1. W1-V9  기록 모드 보호

케이스 그룹 완료마다:
  2. W1-V1  해당 그룹 대조

전체 케이스 완료 후:
  3. W1-V3, V4  커버리지
  4. W1-V8      정규화 목록
  5. W1-V2      결정성 (2회 연속)
  6. W1-V1-2    의도적 실패 확인
  7. W1-V5      전체 회귀
  8. W1-V6, V7  무변경·Secret
```

## 4. 검증 도구

| 검증 | 도구 |
| --- | --- |
| V1, V2, V5 | `unittest` |
| V3, V4, V8 | 케이스 파일 집계 스크립트(테스트로 구현) |
| V6 | `git diff --stat` |
| V7 | 정규식 패턴 검사(테스트로 구현) |
| V9 | 환경변수 조작 테스트 |

V3·V4·V7·V8을 **테스트로 구현**하는 이유: 수동 확인은 케이스가 늘어나면 누락된다. 스냅샷 자체의
품질을 검사하는 메타 테스트를 둔다.

## 5. 판정 규칙

- 검증은 **PASS / FAIL** 두 값
- W1-V1이 FAIL이면 그 케이스만 미완료. 다른 케이스는 진행 가능
- W1-V2(결정성) FAIL은 **전체 미완료** — 하나라도 간헐 실패하면 스냅샷 전체의 신뢰도가 떨어진다
- W1-V6(운영 코드 무변경) FAIL은 **즉시 중단** — W1의 전제가 깨진 것
