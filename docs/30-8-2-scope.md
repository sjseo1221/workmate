# W8-2 — 목적과 범위

> [30-8-w8-retry-observability.md](30-8-w8-retry-observability.md) §2의 상세 문서.

## 1. 목적

노드 단위 실패 격리와 재시도 정책을 Graph의 기능으로 정리하고, 실행을 들여다볼 수 있게 만든다.

### 1.1 왜 지금인가

| 시점 | 재시도의 상태 |
| --- | --- |
| W2 | 정책을 **정의**만 했다. 모델 객체의 라이브러리 재시도는 껐다 |
| W3 | Skill을 옮기면서 **기존 재시도 루프를 그대로 보존**했다 |
| W7 | 옛 코드가 사라지고 실행 경로가 하나가 됐다 |
| **W8** | **정책을 전 노드에 일관되게 적용**할 수 있다 |

W3에서 재시도를 정리하지 않은 이유: 그때는 "동작을 바꾸지 않는다"가 원칙이었다. 재시도 구조를 바꾸면
실패 시나리오의 결과가 달라질 수 있다.

### 1.2 W8이 만드는 차이

| 항목 | W7까지 | W8 이후 |
| --- | --- | --- |
| 재시도 위치 | 함수 내부 루프 | 노드 설정 |
| 재시도 범위 | 함수 전체 | 노드 하나 |
| 부작용 노드 | 구분 없음 | **재시도 제외** |
| 실패 관측 | 없음 | 노드별 로그 |
| 정책 일관성 | 지점마다 다름 | 두 정책으로 정리(통일은 아님) |

## 2. 범위 내 (In scope)

| ID | 항목 | 산출물 |
| --- | --- | --- |
| S1 | 오류 분류 정리 | `app/graph/llm.py` 확장 |
| S2 | 재시도 적용 대상 선정(부작용 노드 제외) | 적용표 |
| S3 | 노드 `RetryPolicy` 적용 | Skill Subgraph |
| S4 | 노드 내부 재시도 루프 제거 | 동상 |
| S5 | 실패 파급 규칙 검증 | 테스트 |
| S6 | 노드 단위 실행 로그 | `app/graph/observability.py` |
| S7 | 로그 민감정보 검사 | 검사 |

## 3. 범위 외 (Out of scope)

| 항목 | 이유 |
| --- | --- |
| **스트리밍(`astream`) 전환** | D5=A. 전환 완료 후 별건 |
| **LangSmith 등 외부 트레이싱** | API Key 필요. 별도 승인 |
| 새 Provider 추가 | 범위 밖 |
| **재시도 정책 통일** | 동작 변경. W9 후속 백로그 |
| HTTP 429 재시도 정책 변경 | 현재 동작 유지 |
| 성능 최적화 | 측정은 하되 최적화는 별건 |
| 범위 밖 LLM 호출 지점 | [30-2-5](30-2-5-design.md) §5.3 |

### 3.1 정책 통일을 하지 않는 이유

두 정책이 공존하는 것이 이상해 보이지만, 통일하면 **동작이 바뀐다.**

| 통일 방향 | 결과 |
| --- | --- |
| 전부 네트워크만 재시도 | `weekly_report`가 429·5xx에서 즉시 실패 → 부분 결과 빈도 증가 |
| 전부 Provider 오류 재시도 | `assistant_router`가 5xx를 3회 재시도 → 장애 시 지연 증폭(2026-08-19 회귀) |

둘 다 W1 스냅샷의 부분 실패 케이스를 깨뜨린다. 그 차이는 "의도한 변경"으로 설명해야 하는데, 이번
전환에서 의도한 적이 없다.

**W9에서 후속 백로그로 기록한다.**

### 3.2 LangSmith를 안 하는 이유

`AGENTS.md`상 API Key가 필요한 외부 서비스 도입은 별도 승인 대상이다. 또한 전환 검증과 무관한 변수를
하나 더 늘린다.

**표준 로깅으로 충분한 수준까지만 한다.**

## 4. W2와의 분담

재시도는 W2와 W8에 걸쳐 있다. 경계를 명확히 한다.

| 항목 | W2 | W8 |
| --- | --- | --- |
| 오류 분류 함수(`is_network_error`) | **정의** | 확장·적용 |
| `RetryPolicy` 객체 2종 | **정의** | **적용** |
| 라이브러리 기본 재시도 끄기 | **완료** | 확인 |
| 모델 객체 생성 | **완료** | — |
| 노드에 정책 붙이기 | — | **완료** |
| 노드 내부 루프 제거 | — | **완료** |
| 부작용 노드 제외 | — | **완료** |
| 실패 파급 규칙 | 문서화(W3) | **검증** |

**W2-V7이 정책 정의를 검증했고, W8-V1~V3이 적용을 검증한다.**

## 5. 관측의 범위

### 5.1 무엇을 남기나

```python
{"node": "fetch_gmail", "thread_id": "...", "user_id": "...",
 "elapsed_ms": 412, "status": "warning",
 "warning_code": "GOOGLE_PROVIDER_UNAVAILABLE", "retry_count": 1}
```

| 항목 | 남긴다 | 남기지 않는다 |
| --- | --- | --- |
| 노드명 | ✓ | |
| `thread_id`·`task_id` | ✓ | |
| `user_id` | ✓ | |
| 소요 시간 | ✓ | |
| 상태·경고 코드 | ✓ | |
| 재시도 횟수 | ✓ | |
| **메일 본문·회의 녹취** | | **✗** |
| **Token·API Key** | | **✗** |
| **Presigned URL** | | **✗** |
| LLM 프롬프트·응답 전문 | | ✗ |

### 5.2 왜 `user_id`는 남기나

장애 조사에 필요하다. `user_id`는 OIDC subject이며 그 자체로 개인정보가 아니다
([test_work_domain_migration.py](../workmate-agent/tests/test_work_domain_migration.py)가
"`users.user_id`는 raw OIDC subject를 담는다"고 명시).

단 메일 본문·회의 내용처럼 **사용자 데이터**는 남기지 않는다.

## 6. 범위 변경 절차

| 상황 | 처리 |
| --- | --- |
| 재시도가 필요해 보이는 노드 추가 | 부작용 여부 먼저 판정 |
| 정책을 통일하고 싶음 | **범위 밖.** 후속 백로그 |
| 로그 항목 추가 | 민감정보 여부 확인 후 범위 내 |
| 성능 문제 발견 | 기록만. 최적화는 별건 |
| 외부 트레이싱 도입 | 범위 밖. 승인 필요 |
