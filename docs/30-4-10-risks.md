## W4-K1 — 멱등성 동작 변경의 파급

**설명** [30-4-5](30-4-5-design.md) §3의 조사 결과, 현재 멱등성은 "충돌 감지"까지만 구현돼 있고
중복 요청은 재실행된다. W4-D1로 제대로 구현하면 동작이 바뀐다.

**예상 밖 파급이 생길 수 있는 곳**

| 곳 | 우려 |
| --- | --- |
| 기존 테스트 | 같은 `message_id`로 두 번 호출하는 테스트가 있으면 두 번째 결과가 달라진다 |
| 오케스트레이터 | HTTP 재시도 시 같은 `message_id`를 보낸다면 이제 재실행되지 않는다(의도한 동작이지만 응답 형태 확인 필요) |
| UI REST | `message_id`가 매번 달라 영향 없음 — 그래서 W5에서 다시 다뤄야 한다 |

**완화**
- W4-T0에서 기존 테스트 중 같은 `message_id` 재사용 케이스를 조사
- W4-V3 7케이스로 꼼꼼히 검증
- 증빙에 동작 변경으로 기록(W9 의도적 변경)

**대응 계획** 기존 테스트가 깨지면 그 테스트가 무엇을 검증하던 것인지 확인한다. "중복 요청이
재실행된다"를 검증하던 테스트라면 그것이 현재 동작을 고정한 것이므로, 변경 사실과 함께 테스트를
갱신한다(W3 이후 테스트 재작성 범위).

## W4-K2 — 새 Schema 검증의 거부

**설명** `validate_contract`는 운영 경로에 없던 검증이다. 지금까지 통과하던 결과가 실패할 수 있다.

**왜 발생하나** 테스트가 검증하는 Skill은 일부다.
[test_priority_workflow.py:70-85](../workmate-agent/tests/test_priority_workflow.py#L70)처럼 Schema
검증을 하는 테스트가 모든 Skill에 있지는 않다. 검증되지 않은 Skill의 결과가 Schema를 위반하고 있을
수 있다.

**영향** W4에서 정상 요청이 `FAILED`가 된다.

**완화**
- **W4-T0에서 스냅샷 27건의 `expected`를 Schema로 사전 검증**(W4-V5-1)
- 실패 케이스가 나오면 **Schema를 완화하지 않는다** — 현재 존재하는 계약 위반을 발견한 것이므로
  기록하고 보고한다

**대응 계획** 위반이 발견되면 두 경로가 있다.

| 선택 | 내용 |
| --- | --- |
| a | 구현을 고쳐 Schema를 만족시킨다 → 동작 변경, 스냅샷 갱신 |
| b | 그 Skill만 검증 예외로 두고 기록 → 계약 위반이 방치됨 |

**a를 기본으로 하되 사용자 보고 후 결정한다.** 이는 W4가 아니라 별도 수정일 수 있다.

## W4-K3 — 멱등성이 Checkpointer로 새어나감

**설명** Checkpointer에도 `thread_id`별 State가 있으니, 멱등성 판정을 그쪽에서 하고 싶어진다.

**왜 발생하기 쉬운가** 둘 다 "이미 처리했는가"를 알 수 있어 보인다. 특히 `thread_id = task_id`이므로
Checkpoint 존재만 확인하면 될 것 같다.

**왜 틀렸나**

| 저장소 | 알 수 있는 것 |
| --- | --- |
| Task Store | `message_id`로 "**이 요청**을 처리했는가" |
| Checkpointer | `thread_id`로 "이 **실행**이 어디까지 갔는가" |

`message_id`는 요청 식별자이고 `thread_id`는 실행 식별자다. 재시도로 같은 요청이 와도 새 `task_id`를
발급할 수 있으므로 둘은 다르다.

**영향** [96번 §10](96-workmate-langgraph-target-architecture.md) 경계 붕괴. 장애 복구 시 어느
저장소가 진실인지 판정 불가.

**완화**
- W4-V8-3에서 `idempotency_check`의 조회 대상이 Task Store인지 확인
- 96번 §10 경계표를 W4-T1 설계 검토 항목으로

## W4-K4 — 공통 노드가 결과를 덮어씀

**설명** `initialize_state`나 `build_artifact`가 Subgraph의 결과를 의도치 않게 바꾼다.

**구체적 위험 지점**

| 노드 | 위험 |
| --- | --- |
| `initialize_state` | `now`·`timezone`을 케이스의 `as_of`와 다르게 주입 → 날짜 계산이 달라짐 |
| `build_artifact` | Artifact 이름·설명을 Skill이 정한 값이 아니라 노드가 덮어씀 |
| `persist_result` | (결과에는 영향 없지만) 저장 내용이 달라짐 |

**완화**
- **W4-V6(Root 경유 스냅샷)** — W3 대조와 결과가 같은지 확인하는 것이 유일하고 확실한 방법
- `build_artifact`는 State의 `result`에 있는 값을 **읽어서** Part를 구성한다. 새로 만들지 않는다

## W4-K5 — path map 누락

**설명** `add_conditional_edges`에 path map을 주지 않거나 일부 Skill을 빠뜨린다.

**영향** 해당 Skill 호출 시에만 런타임 실패. 테스트에서 그 Skill을 호출하지 않으면 발견되지 않는다.

**완화**
- W4-V1에서 **11개 각각** 호출
- W4-V1-14에서 path map 키 집합이 공개 Skill 11개와 정확히 일치하는지 확인
- path map을 상수(`SKILL_NODE_NAMES`)로 두고 노드 등록에도 같은 상수를 쓴다

---

## W4-K6 — 순환 import

**설명** Root가 Skill을 import하고 Skill(`assistant_ask`)이 다른 Skill을 import하면 순환이 생긴다.

**완화**
- W3-V9에서 Skill 간 직접 import가 없음을 이미 확인(W4-E3)
- 주입은 `build_workmate_graph()` 한 곳에서만
- `assistant_ask`는 다른 Subgraph가 만들어진 뒤 생성

**대응 계획** 순환이 발생하면 import 시점이 아니라 호출 시점에 해결하는 구조(주입)가 지켜지지 않은
것이다. 지연 import로 우회하지 않는다 — 그것이 현재 코드의 문제다.

---

## W4-K7 — `build_artifact`의 text Part 누락 회귀

**설명** 구조화 `data`만 있는 결과에서 `text/plain` Part를 생략한다.

**왜 위험한가** **이미 한 번 발생한 문제다.** 2026-08-14 오케스트레이터 연동 중 발견됐다.

> `app/a2a/runtime.py`의 `_artifact_parts`가 구조화 `data`만 있는 결과에서 `text` Part를 생략해,
> `text`만 읽는 Orchestrator Client가 결과를 놓치는 것이었다. `markdown` 없는 구조화 결과에도
> `text/plain` Part를 함께 싣도록 고쳤다.
> — HANDOFF.md 2026-08-14 기록

`build_artifact`로 이관하면서 이 처리를 빠뜨리면 같은 문제가 재발한다. 게다가 **Task는
`COMPLETED`인데 응답이 비어 보이는** 형태라 발견이 어렵다.

**완화**
- [`_artifact_parts()`](../workmate-agent/app/a2a/runtime.py#L289)의 현재 구현을 그대로 이관
- W4-V6 스냅샷 대조에 Artifact Part 구성이 포함되도록
- W5에서 A2A 경로 실제 응답으로 재확인

---

## W4-K8 — Schema 파일 접근 실패

**설명** `validate_contract`가 Schema 파일을 찾지 못한다.

**왜 발생하나** 테스트는 `Path(__file__).parents[2] / "docs" / "schemas" / ...`로 저장소 구조에
의존한다. Docker 이미지에 `docs/`가 없으면 실패한다.

**이미 겪은 문제다** — 커밋 `62f38c5`: "vendor docs/schemas + bake into Docker image so
schema-validated skill chat works standalone".

**가장 나쁜 시나리오** 로딩 실패를 예외로 처리하지 않고 "검증 건너뛰기"로 폴백하면, 검증이 꺼진 채
배포되고 아무도 모른다.

**완화**
- W4-D2: 기존 [`_schema_validator()`](../workmate-agent/app/internal_chat.py#L59)의 로딩 방식 재사용
- **W4-V5-4: 로딩 실패 시 명시적 오류** — 조용한 폴백 금지
- W4-V5-5: 배포 환경 경로에서 로딩 확인

---

## W4-K9 — Root 노드에 업무 규칙이 스며듦

**설명** 공통 노드에 Skill별 분기나 Repository 호출이 들어간다.

**왜 발생하기 쉬운가** "이 Skill만 예외 처리"가 필요해 보이는 순간이 온다. 예: 특정 Skill의 Artifact
이름을 다르게 만들어야 하는 경우.

**영향** [96번 §10](96-workmate-langgraph-target-architecture.md)의 계층 경계 붕괴. Root가 Skill에
의존하면 Skill 추가 시마다 Root를 고쳐야 한다.

**완화**
- W4-R9를 요구사항으로 명시
- Skill별 차이는 **Subgraph가 State에 담아 보내고** Root는 그것을 읽기만 한다
- 코드 검토 항목
