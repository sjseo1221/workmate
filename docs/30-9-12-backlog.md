## 2. 항목 상세

### W9-B1 — 재시도 정책 통일

**현재 상태** 두 정책이 공존한다.

| 지점 | 시도 | 재시도 대상 |
| --- | --- | --- |
| `assistant_router` 계열 | 3회 | 네트워크만 |
| `weekly_report` 계열 | 2회 | 429·5xx 포함 |

**왜 안 했나** 통일하면 동작이 바뀌고 W1 스냅샷의 부분 실패 케이스가 깨진다. 그 차이는 "의도한
변경"으로 설명해야 하는데, 전환에서 의도한 적이 없다.

**어떻게 할 것인가** 어느 정책이 맞는지 먼저 판단해야 한다.

| 방향 | 결과 |
| --- | --- |
| 네트워크만으로 통일 | `weekly_report`의 부분 결과 빈도 증가 |
| Provider 오류 포함으로 통일 | `assistant_router`가 5xx를 3회 재시도(2026-08-19 회귀) |
| 429만 양쪽에 추가 | W9-B2와 함께 |

**우선순위 낮음** — 현재 동작에 문제가 없다.

---

### W9-B2 — HTTP 429 재시도

**현재 상태** `assistant_router` 계열이 429를 재시도하지 않는다.

```python
except error.HTTPError as exc:   # 429도 여기
    last_exc = exc
    break                         # 즉시 실패
```

**왜 안 했나** 현재 동작을 보존했다(W8-D6). 변경하면 스냅샷에 영향.

**왜 우선순위가 중간인가** 429는 **재시도하면 성공할 가능성이 높은** 오류다. rate limit이 풀리면
된다. 즉시 실패시키는 것은 사용자에게 불필요한 실패를 준다.

**어떻게 할 것인가**
- 429를 별도 분류로 추가
- `Retry-After` 헤더를 존중하는 backoff
- 다른 HTTP 오류는 계속 즉시 실패

---

### W9-B3 — `AUTH_REQUIRED` 상태 도입

**현재 상태** [96번 §7·§8](96-workmate-langgraph-target-architecture.md)에 설계돼 있지만 구현하지
않았다.

**왜 안 했나** 신규 Task 상태이므로 계약 영향이 있다. W6에서 이미 계약을 바꿨고, W8에서 또 바꾸면
"의도적 변경" 목록이 커진다(W8-D2).

**왜 우선순위가 중간인가** Google Provider의 토큰이 만료되면 지금은 그냥 실패한다. 사용자는 왜
실패했는지, 무엇을 해야 하는지 모른다.

**어떻게 할 것인가**
- W6의 `INPUT_REQUIRED`와 같은 패턴
- 인증 오류 → `AUTH_REQUIRED` → 사용자가 재인증 → resume
- UI가 재인증 안내를 표시
- 계약 문서 개정

---

### W9-B4 — LLM 환경변수 통일

**현재 상태** 두 계열이 공존한다.

| 모듈 | 환경변수 |
| --- | --- |
| `assistant_router`, `meeting_analysis`, `email_action_items` | `OPENAI_API_KEY`·`OPENAI_BASE_URL`·`OPENAI_MODEL` |
| `weekly_report`, `meeting_answer` | `LLM_API_KEY`·`LLM_BASE_URL`·`LLM_MODEL` |

**왜 안 했나** 통일하려면 **배포 환경변수 설정까지** 바꿔야 한다. 전환 검증과 무관한 변수를 늘린다.

**어떻게 할 것인가**
- 한쪽으로 통일하되 옛 이름도 당분간 읽는 호환 기간
- 배포 설정 갱신
- 문서 반영

---

### W9-B5 — 범위 밖 LLM 호출 지점 교체

**현재 상태** [email_action_items.py](../workmate-agent/app/email_action_items.py)의 LLM 호출 2곳이
`urllib` 직접 호출로 남아 있다.

**왜 안 했나** 이 모듈을 `daily_briefing`(전환 범위 내)과 `dev_gmail_sync_api`·`proposal_api`(범위
밖)가 공유한다. 교체하면 범위 밖 경로에 위험이 번진다(W2 §5.3).

**어떻게 할 것인가** 범위 밖 호출자의 테스트가 충분한지 먼저 확인하고 교체한다.

---

### W9-B6 — UI REST `message_id` 비대칭

**현재 상태**

| 경로 | 멱등성 |
| --- | --- |
| A2A | 동작함(W4-D1) |
| UI REST | **발동하지 않음** — `message_id = f"internal-{uuid4()}"` |

**왜 안 했나** 클라이언트가 `message_id`를 보내게 하려면 공개 계약이 바뀐다. W6의 범위와 겹쳐 함께
다루는 편이 나았으나, W6에서 확인 프로토콜만으로도 범위가 컸다(W5-D3).

**어떻게 할 것인가**
- 클라이언트가 `message_id`를 보내는 방식
- 또는 요청 내용 해시 — 단 정당한 중복 요청("같은 할 일 두 번 만들기")이 막히지 않게

---

### W9-B7 — `astream` 스트리밍 전환

**현재 상태** 폴링 유지(D5=A). `analyze_meeting` 같은 긴 작업의 진행 상황을 볼 수 없다.

**왜 안 했나** UI(SSE 수신)·Task 상태 매핑·A2A `message:stream` 계약이 한꺼번에 얽힌다. 전환 중에
넣으면 실패 원인 분리가 어렵다.

**어떻게 할 것인가** Graph가 제자리에 있으므로 `ainvoke` → `astream` 교체 + UI SSE 수신.

---

### W9-B8 — 외부 트레이싱

**현재 상태** 표준 로깅만(W8).

**왜 안 했나** API Key가 필요해 `AGENTS.md`상 별도 승인 대상이다. 전환 검증과 무관한 변수를 늘린다.

**어떻게 할 것인가** 필요성이 확인되면 승인 후 도입. LangSmith 외의 선택지도 검토.

---

### W9-B9 — 오케스트레이터 대응

**현재 상태** W6-T1의 판정에 따라 달라진다.

| 판정 | 후속 |
| --- | --- |
| 어댑터로 흡수 | 없음 |
| 흡수 불가 + 승인 | W6에서 수정 완료 |
| 흡수 불가 + 미승인 | **이 백로그** |

**왜 우선순위가 중간인가** 팀 통합 경로다. 끊기면 오케스트레이터에서 Workmate 기능을 쓸 수 없다.

**어떻게 할 것인가** 오케스트레이터 담당자와 협의 후 수정 승인.

---

### W9-B10 — 확인 대기 Task 만료

**현재 상태** 사용자가 확인도 거부도 하지 않으면 Task가 `INPUT_REQUIRED`로 무한히 남는다.

**왜 안 했나** 현재도 같은 상황이다 — 확인 버튼을 안 누르면 아무 일도 안 일어난다. 만료 정책은
전환이 만든 문제가 아니다.

**어떻게 할 것인가** TTL 설정 + 만료 시 `CANCELED` 전이. Checkpoint 정리도 함께.

| 항목 | 왜 중간인가 |

승인 절차가 필요하다.
