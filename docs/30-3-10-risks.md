## W3-K1 — `assistant_router` 규모

**설명** 937줄 구현 + 1,019줄 테스트. W3 전체 비중의 약 25%를 차지하며, 하위 Skill 10개에 모두
의존해 마지막에야 착수할 수 있다.

**징후** W3-T7 착수 후 진척이 정체, 스냅샷 대조가 여러 원인으로 반복 실패.

**영향** W3이 무기한 지연되고, 후행 단계 전체가 밀린다.

**완화**
- [30-3-6](30-3-6-wbs.md) §2의 T7-a~T7-f **6단계 분할 착수**
- 노드 경계는 [96번 §6](96-workmate-langgraph-target-architecture.md)을 그대로 따라 설계 시간을 줄인다
- 확인 흐름은 W3에서 바꾸지 않으므로(W3-R11) 그만큼 범위가 줄어 있다

**대응 계획** 분할 단위에서도 막히면 해당 노드만 기존 함수를 그대로 호출하는 임시 형태로 두고, 나머지
노드를 먼저 완성한다. 단 "기존 함수 그대로 호출"이 남은 채로 W3을 완료하지 않는다.

---

## W3-K2 — 중간 상태 유실

**설명** 함수 지역 변수로 흐르던 값을 노드로 쪼개면서 State에 싣지 않아, 뒤 노드에서 값이 비어 있다.

**왜 발생하기 쉬운가** 현재 `execute()`들은 지역 변수를 자유롭게 참조한다. 예를 들어
`daily_briefing`은 `message_summaries`·`provider_freshness`·`registered_task_ids`를 함수 전체에서
공유한다. 노드로 나누면 이 중 무엇을 State 채널로 올릴지 매번 판단해야 한다.

**영향** 스냅샷 대조 실패. 값이 `None`·빈 리스트로 나오는 형태라 조용히 지나칠 수도 있다.

**완화**
- Skill 완료 **즉시** 스냅샷 대조(W3-T8을 마지막에 몰지 않는다)
- 노드 Docstring에 "무엇을 읽고 무엇을 쓰는지" 명시(W3-R9)
- 스냅샷이 `WorkflowResult` **전 필드**를 비교하므로 빈 값도 검출된다

**대응 계획** 유실 발견 시 해당 값을 State 채널로 승격한다. 채널이 늘어나면 `source_data` namespace
사용을 검토한다.

---

## W3-K3 — 병렬 갱신 충돌

**설명** `daily_briefing`의 병렬 노드가 `warnings`를 동시에 갱신할 때 하나가 사라지거나, Reducer가
없어 `InvalidUpdateError`로 실행이 실패한다.

**영향** 부분 실패 정보 손실 — Provider 장애 시 사용자가 무엇이 안 됐는지 알 수 없다.

**완화**
- W2에서 정의한 `warnings` 누적 Reducer가 전제다(W2-V1)
- W3-V6-1에서 **Gmail·Calendar 동시 실패** 케이스로 확인
- `source_data`는 출처별 namespace로 분리해 키 충돌 자체를 방지

**대응 계획** 충돌 시 채널 설계를 재검토한다. 노드가 같은 키를 쓰는 것은 대개 분해 설계의 문제다.

---

## W3-K4 — Domain 규칙 재구현

**설명** 노드 안에서 점수·날짜·중복 제거를 다시 구현해 Domain 함수와 결과가 달라진다.

**왜 발생하기 쉬운가** 노드로 쪼개다 보면 "이 계산은 여기서 하는 게 자연스럽다"는 유혹이 생긴다.
특히 `rank_priorities`의 `score_breakdown` 조립이나 `weekly_report`의 분류가 그렇다.

**영향** 결정성 위반. `AGENTS.md`의 "우선순위 점수는 결정적으로 계산한다", "LLM이 Task 순위와 근거
ID를 생성하거나 변경하지 않도록 한다" 위반.

**완화**
- [30-3-2](30-3-2-scope.md) §4 원칙 2를 설계 검토 항목으로 고정
- W3-V7에서 경로 검사 — 점수 계산이 [`rank_tasks()`](../workmate-agent/app/domain/priority.py)
  호출로만 이뤄지는지
- W3-V7-3: LLM Fake가 분류 필드를 포함해 응답해도 결과가 바뀌지 않는지

**대응 계획** 재구현 발견 시 Domain 호출로 되돌린다. Domain 함수가 노드에 맞지 않는 시그니처라면
Domain을 바꾸는 것이 아니라 노드에서 변환한다.

---

## W3-K5 — State 스키마 변경

**설명** W3 중간에 State 필드나 Reducer 규칙이 바뀌어 이미 만든 Subgraph를 다시 손봐야 한다.

**영향** 최악의 경우 Skill 11개 전부 수정.

**완화**
- W2에서 96번 §3을 **그대로** 구현하고 임의 추가를 막는다(W2-K8)
- W3에서 변경이 필요하면 **한 Skill에서 먼저 검증**한 뒤 확산
- 이식 순서를 난이도 순으로 둬서, 어려운 Skill이 늦게 오도록 한다 — 스키마 문제는 대개 복잡한
  Skill에서 드러나는데, 그때는 이미 패턴이 검증돼 있어 수정 범위를 산정하기 쉽다

**대응 계획** 변경 시 영향받는 Subgraph 목록을 먼저 만들고, 변경 사유·범위를 증빙에 기록한다.

---

## W3-K6 — 숨은 부작용 소실

**설명** `daily_briefing`이 `rank_priorities`를 호출하며 우선순위 Snapshot을 저장하는 부작용을,
Domain 호출로 바꾸면서 잃는다.

**왜 위험한가** **스냅샷 대조로 검출되지 않는다.** `daily_briefing`의 응답에 부작용이 드러나지 않기
때문이다. W3-V1이 전건 PASS여도 이 문제는 남는다.

**영향** 사용자가 관찰하는 `rank_priorities`의 `changes` 값이 달라진다. 두 Skill이 저장소를 통해
결합돼 있던 관계가 끊긴다.

**완화**
- W3-D1 결정(부작용 유지)을 W3-T0에서 확정
- **W3-V11 전용 검증** — DB 상태를 직접 확인
- [30-3-5](30-3-5-design.md) §3.4의 부작용 목록을 W3-T0에서 전수 작성

**대응 계획** 부작용을 제거하는 것이 바람직하더라도 W3 범위가 아니다. 별도 백로그로 기록한다.

---

## W3-K7 — 범위 밖 모듈 수정

**설명** 보조 Skill 5종이 `app/action_item_api.py`·`app/proposal_api.py`·`app/task_api.py`의 함수를
호출하는데, Subgraph로 옮기면서 그 모듈을 고치고 싶어진다.

**왜 발생하기 쉬운가** 이 모듈들은 FastAPI 요청 객체나 Pydantic 모델을 다루는 부분이 있어, Graph
노드에서 부르기 어색할 수 있다.

**영향** [30-langgraph-migration-plan.md](30-langgraph-migration-plan.md) §2.2의 범위 이탈. UI REST
경로에 회귀가 생길 수 있고, 그쪽은 W3 검증 범위 밖이다.

**완화**
- [30-3-5](30-3-5-design.md) §2.2의 3노드 최소 분해 유지
- 호출이 어색하면 **노드 쪽에서 변환**하고 모듈은 그대로 둔다
- `git diff --stat`으로 범위 밖 파일 변경 감시

**대응 계획** 모듈 수정이 불가피하면 범위 변경으로 보고한다([30-3-2](30-3-2-scope.md) §5).

---

## W3-K8 — `user_id` 조건 누락 (보안)

**설명** 조회 코드를 노드로 옮기면서 `user_id` 조건이나 Soft Delete 제외가 빠진다.

**영향** **타 사용자 데이터 노출.** 가장 심각한 실패 유형이다.

**완화**
- 모든 Skill에 대해 W3-V3 수행 — 예외 없음
- 조회 노드가 `state["user_id"]`를 쓰는지 코드 검사(V3-3)
- `assistant_ask`가 하위 Skill에 `user_id`를 전달하는지 별도 확인(V3-4)
- 한 Skill에서 누락이 발견되면 **같은 패턴을 쓴 다른 Skill을 전수 재점검**

**대응 계획** 발견 즉시 수정하고, W3 전체를 미완료로 되돌린다([30-3-9](30-3-9-exit-criteria.md) §2.2).

---

## W3-K9 — 과분해

**설명** 노드를 지나치게 잘게 나눠 Checkpoint I/O와 State 왕복이 늘어난다.

**영향** 성능 저하. 특히 노드마다 State 전체를 저장하는 구조에서 체감된다.

**완화**
- [30-3-2](30-3-2-scope.md) §1.2의 분해 기준 적용
- "한 줄짜리 노드"가 생기면 분해 기준 재검토
- 얇은 래퍼 Skill은 3노드로 제한(W3-D4)

**대응 계획** W8의 노드 단위 로그에서 소요 시간을 보고 판단한다. W3에서 성능을 측정하지는 않는다.

---

## W3-K10 — 확인 흐름 조기 변경

**설명** W6을 앞당겨 W3에서 `interrupt`를 넣는다.

**영향** W1 스냅샷의 `assistant_ask.requires_confirmation` 케이스와 대조 불가. "이식 오류인지 계약
변경인지" 구분할 수 없게 된다.

**완화**
- W3-R11을 요구사항으로 명시
- W3-V1의 `assistant_ask.requires_confirmation` 케이스가 자동으로 잡는다
- 대신 **노드 경계는 W6 대비로 미리 나눈다**(W3-D5) — 하고 싶은 욕구를 경계 설계로 흡수
