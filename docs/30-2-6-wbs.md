## 2. 작업 상세

### W2-T1 — 의존성 추가·충돌 확인

**내용**

1. `uv add langgraph langgraph-checkpoint-sqlite langgraph-checkpoint-postgres langchain-openai`
2. `uv.lock` diff 검토 — **기존 고정 버전(`a2a-sdk==1.1.2`, `fastapi==0.116.1`, `psycopg[binary]==3.2.10`,
   `jsonschema==4.26.0`)이 변경되지 않았는지** 확인
3. 변경됐다면 `AGENTS.md`에 따라 M0.1 Contract Test 재실행
4. 전체 스위트 실행으로 기존 동작 무영향 확인
5. **부수 작업:** `/chat/completions` 호출 5개 모듈의 호출자를 재확인해 교체 대상 확정
   ([30-2-5](30-2-5-design.md) §5.3)

**왜 가장 먼저인가** 충돌이 나면 W2 전체가 막히고 D3 결정을 되돌려야 한다. 다른 작업에 시간을 쓰기
전에 판정한다.

**난이도** 낮음(성공 시) / 치명적(실패 시) — 실패는 중단 사유다

### W2-T2 — `state.py` 구현

**내용**

- `WarningState`·`WorkmateState` TypedDict 정의([30-2-5](30-2-5-design.md) §2.1)
- `warnings`에 `operator.add` Reducer
- `source_data`에 `merge_by_source` Reducer (키 충돌 시 예외)
- 모듈·공개 타입에 한글 Docstring

**주의** `WarningState` 필드는 현재
[`_warning()`](../workmate-agent/app/workflows/daily_briefing.py#L118)이 만드는 구조와 일치해야 한다.
W1 스냅샷이 이 모양을 기대값으로 갖는다.

**난이도** 낮음

---

### W2-T3 — 식별자 불변식 테스트

**내용**

- 두 노드가 각각 `warnings`를 추가했을 때 둘 다 보존되는지(W2-V1)
- 노드가 `user_id`를 바꾸려 하면 테스트가 검출하는지(W2-V2)
- `source_data` 키 충돌 시 예외가 나는지
- State 직렬화 결과에 Secret 패턴이 없는지(W2-V9)

**주의** W2-V2는 "우연히 안 바뀜"이 아니라 "바꾸려 하면 실패"를 확인해야 한다. 변경을 시도하는 노드를
실제로 만들어 검증한다.

**난이도** 낮음

---

### W2-T4 — `adapter.py` 구현

**내용**

- `state_from_request()` — 식별자·payload·`now`·`timezone` 주입
- `result_from_state()` — 8개 필드 산출([30-2-5](30-2-5-design.md) §3.2)
- `data`가 비고 `text`에만 구조화 결과가 실리는 조합을 만들지 않는다

**주의** `now`를 어댑터에서 주입하는 이유는 노드가 각자 `datetime.now()`를 부르면 같은 실행 안에서
시각이 어긋나기 때문이다. W1 스냅샷의 결정성과도 직결된다.

**난이도** 중간 — 현재 `WorkflowResult` 생성 지점들을 읽어 필드 의미를 정확히 옮겨야 한다

### W2-T7 — Checkpointer 테스트

**내용**

- 같은 `thread_id`로 2회 실행 시 이력 누적(W2-V4)
- `get_state_history()` 조회
- `DATABASE_URL` 유무에 따른 백엔드 선택(W2-V5) — **두 백엔드 모두 실제 저장·복원 확인**
- Task Store와 쓰기 경로가 겹치지 않음(W2-V4의 책임 분리 부분)

**주의** Postgres 경로는 테스트 컨테이너가 필요하다([30-2-3](30-2-3-entry-criteria.md) W2-E4).
SQLite만 확인하고 넘어가면 운영 백엔드가 미검증으로 남는다.

**난이도** 중간

### W2-T8 — `llm.py` 구현

**내용**

- `build_chat_model()` — `max_retries=0`, `temperature=0`, timeout 30초
- `is_network_error()` — 오류 분류
- `NETWORK_ONLY_RETRY`(3회) / `PROVIDER_ERROR_RETRY`(2회) 두 정책
  ([30-2-5](30-2-5-design.md) §5.2의 불일치 처리)
- 모델 식별자 변환 규칙 이관(`"openai/gpt-4.1-mini"` → `"gpt-4.1-mini"`)
- 구조화 출력 래퍼

**주의** 재시도 정책이 **두 종류**라는 점을 놓치지 않는다. 하나로 합치면 `weekly_report`의 동작이
바뀌고 W1 스냅샷이 깨진다.

**난이도** 높음 — D3=B의 위험이 집중된다

### W2-T10 — 재시도 정책 테스트

**내용**

| 케이스 | 주입 | 기대 |
| --- | --- | --- |
| 네트워크 오류 | DNS 실패류 | 3회 시도 후 실패 |
| HTTP 500 | 5xx 응답 | **1회 시도 후 즉시 실패** |

## 3. 병렬 실행 가능성

세 계열이 서로 독립이므로 W2-T1 이후 병렬로 진행할 수 있다.

```
W2-T1 (의존성)
  ├─ State 계열:      T2 → T3
  ├─ Checkpointer:    T6 → T7
  └─ LLM 계열:        T8 → T9, T10
                          ↓
  어댑터: T2 → T4 → T5
                          ↓
                       T11 (증빙)
```

단일 작업자가 진행한다면 **T1 → T8·T9·T10(LLM) → T2·T3·T4·T5(State·어댑터) → T6·T7(Checkpointer)**
순서를 권한다. LLM 계열을 먼저 하는 이유는 실패 확률이 가장 높고, 실패 시 D3 재검토가 필요해
빨리 알수록 손실이 적기 때문이다.
