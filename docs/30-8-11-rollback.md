# W8-11 — 롤백·중단·재개 기준

> [30-8-w8-retry-observability.md](30-8-w8-retry-observability.md) §11의 상세 문서.

## 1. 롤백 비용 — 낮다

W8은 **정책 설정과 로깅 추가**가 전부다. 구조를 바꾸지 않는다.

| 산출물 | 롤백 방법 | 비용 |
| --- | --- | --- |
| `RetryPolicy` 적용 | `retry=` 인자 제거 | 낮음 |
| 내부 루프 제거 | revert(루프 복원) | 낮음 |
| 노드 로그 | 파일 삭제 | 낮음 |
| 적용표 문서 | revert | 낮음 |

**비가역 작업이 없다.** W7과 대조적이다.

### 1.1 그래도 주의할 것

W8-T4(내부 루프 제거)를 revert하면 루프가 돌아오는데, `RetryPolicy`도 함께 제거해야 한다. 안 그러면
**이중 재시도**가 된다(W8-K1).

**W8-T3과 W8-T4를 인접 커밋으로 두고 함께 revert한다.**

## 2. 부분 롤백

| 롤백 단위 | 영향 | 남는 것 |
| --- | --- | --- |
| 로그만(W8-T6) | 관측 없음 | 재시도는 유효 |
| 특정 Skill의 정책만 | 그 Skill만 옛 동작 | 나머지 유효 |
| 재시도 전체(T3+T4) | W7 상태로 복귀 | 로그는 유효 |
| 전체 | W7 상태 | — |

### 2.1 Skill 단위 롤백이 가능하다

`RetryPolicy`는 노드별 설정이므로 Skill 하나만 되돌릴 수 있다.

```
weekly_report만 문제 → 그 Skill의 정책만 제거 + 루프 복원
나머지 Skill은 W8 상태 유지
```

단 **일관성이 깨진 상태**이므로 오래 두지 않는다.

## 3. 중단 기준

### 3.1 즉시 중단 — 사용자 판단 필요

| 조건 | 사유 | 처리 |
| --- | --- | --- |
| **W8-V2(HTTP 비재시도) FAIL이고 해결 불가** | 완료 기준 미충족 | 원인과 시도한 방법을 보고 |
| **W8-V7(부작용 노드) FAIL이고 구조적** | 데이터 손상 위험 | 보고 |
| W8-K7(예외 타입) 해결 불가 | W5 오류 매핑 붕괴 | 보고 |
| `AUTH_REQUIRED` 도입이 필요하다고 판단 | 계약 변경 | **승인 요청** |
| 정책을 바꿔야 문제가 해결됨 | 동작 변경 | 보고 |

### 3.2 자동 재작업 — 사용자 질문 없이 진행

| 조건 | 처리 |
| --- | --- |
| 호출 횟수가 정책보다 많음 | 라이브러리 재시도 끄기, Provider Client 재시도 제거 |
| 오류 분류 누락 | `is_network_error()` 보완 |
| 부작용 노드에 재시도가 붙음 | 제거 |
| 부분 실패가 전체 실패로 승격 | 예외 처리 보완 |
| 로그에 민감정보 | 항목 제거 |
| 예외 타입 변화 | 재시도 대상에서 제외하거나 원 예외 추적 |

다음은 해결 방법으로 인정하지 않는다.

| 금지 | 이유 |
| --- | --- |
| **정책 통일로 문제 회피** | W8-R10. 동작 변경 |
| **429·5xx를 재시도 대상에 추가** | W8-D6. 현재 동작 유지 |
| 재시도가 없던 곳에 추가 | W8-D3 |
| 부작용 노드에 재시도를 붙이고 "중복은 무시" | 데이터 손상 |
| 로그를 끄는 것으로 민감정보 문제 회피 | W8-R6 |
| 스냅샷 기대값 수정 | `AGENTS.md` |

### 3.3 조건부 진행

| 조건 | 처리 |
| --- | --- |
| W8-V6(인증 분류)만 FAIL | 분류가 불명확하면 기록하고 후속으로. W9 진행 가능 |
| 로그 일부 항목 누락 | 보완 후 진행 |
| 특정 Skill의 정책 적용 실패 | 그 Skill만 보류하고 기록 |

**W8-V2와 W8-V7은 조건부 진행 대상이 아니다.** 둘 다 필수다.

## 4. 재개 조건

| 중단 사유 | 재개 조건 |
| --- | --- |
| HTTP 재시도 | 호출 계측에서 1회 확인 |
| 부작용 노드 | 제외 확인 + 중복 생성 없음 확인 |
| 예외 타입 | 422/503 매핑 복원 |
| `AUTH_REQUIRED` | 도입 여부 승인 |

## 5. 에스컬레이션 경로

```
W8-V3 (호출 횟수) 초과
  ├─ 라이브러리 재시도 → max_retries=0 재확인 (자동 재작업)
  ├─ Provider Client 재시도 → 제거 (자동 재작업)
  ├─ 노드 내부 루프 잔존 → 제거 (자동 재작업)
  └─ 원인 불명 → 중단, 보고

W8-V2 (HTTP 비재시도) FAIL
  ├─ is_network_error()가 HTTPError를 True로 판정 → 수정
  ├─ 라이브러리가 자체 재시도 → §위 경로
  └─ 해결 불가 → **중단, 보고** (완료 기준 미충족)

W8-V7 (부작용 노드) FAIL
  → 적용표 재검토
  → retry= 인자 제거
  → 중복 생성 확인
  → 구조적으로 불가피하면 중단, 보고

W8-V9 (스냅샷) 부분 실패 케이스 차이
  → 재시도가 실패 시점을 바꿨다
  → 실패 파급 규칙 확인
  → 정책 통일 유혹을 경계 (금지)
```

## 6. 중단 시 기록 의무

```
## 9. 최종 판단
- 승인 여부: 보류
- 자동 진행 판정: 중단 / 조건부 진행
- 자동 진행 보류 사유: (구체적으로)
- 판정을 막은 검증: W8-Vx
- 적용 상태: Skill별 정책 적용 여부
- 호출 횟수 계측: (수치)
- 시도한 해결 방법: (후보별 결과)
- 필요한 조치·승인: (내용)
- 재개 조건: (조건)
- 다음 구현 백로그: W8-Tx
```

**"호출 횟수 계측"을 수치로 남긴다.** W8의 대부분 문제가 이 숫자로 드러난다.

## 7. 롤백하지 않는 것

| 항목 | 이유 |
| --- | --- |
| W0~W7 산출물 | W8이 딛고 선 기반 |
| **`app/workflows/`** | **이미 삭제됨(W7).** 복원은 최후 수단 |
| 2026-08-19 재시도 구분 | W8-R1의 대상 |
| 실패 파급 규칙표 | W8이 보존하는 계약 |
| 부작용 노드 목록 | W8-R9의 근거 |

## 8. W8 특유의 주의

### 8.1 "더 안전하게"가 위험을 만든다

W8의 위험 다수가 **과도한 안정화**에서 온다([30-8-10](30-8-10-risks.md) §3.1).

| 생각 | 결과 |
| --- | --- |
| "모든 노드에 재시도를 붙이면 안정적" | 부작용 노드 중복 실행 |
| "여러 계층에서 재시도하면 더 안전" | 지연 증폭 |
| "정책을 통일하면 일관적" | 동작 변경 |
| "실패를 막으려면 더 시도해야" | 전체 실패 승격 |

**적절한 곳에만 붙이는 것이 W8의 요점이다.**

### 8.2 계측 없이 판단하지 않는다

| 질문 | 계측 없이는 |
| --- | --- |
| 재시도가 몇 번 도나 | 설정만 보고 추측 |
| 부작용 노드가 중복 실행되나 | 코드만 보고 추측 |
| 로그에 민감정보가 있나 | 일부만 보고 추측 |

**W8-V3·V7·V8이 전부 계측 기반인 이유다.**

### 8.3 후속 백로그를 정직하게 남긴다

W8에서 의도적으로 하지 않는 것이 셋 있다.

| 항목 | 이유 |
| --- | --- |
| 정책 통일 | 동작 변경 |
| 429 재시도 | 동상 |
| `AUTH_REQUIRED` | 계약 영향 |

**"안 했다"를 숨기지 않는다.** W9의 후속 백로그에 이유와 함께 기록한다.
