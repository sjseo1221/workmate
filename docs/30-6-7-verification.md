## 2. 검증 케이스 상세

### W6-V1 — interrupt 중단

확인 대상 4종 각각에 대해 수행한다.

| 케이스 | 입력 | 기대 |
| --- | --- | --- |
| V1-1 | "그 Task 지워줘" (`manage_tasks.delete`) | `INPUT_REQUIRED`, Task 미삭제 |
| V1-2 | Action Item 거절 요청 | `INPUT_REQUIRED`, 상태 불변 |
| V1-3 | 제안 무시 요청 | `INPUT_REQUIRED`, 상태 불변 |
| V1-4 | 회의 분석 요청 | `INPUT_REQUIRED`, 분석 미실행 |
| V1-5 | 확인 불필요한 요청(`manage_tasks.list`) | 바로 실행, `COMPLETED` |
| V1-6 | Checkpoint 내용 | `skill_id`·`arguments`·대화 컨텍스트 보존 |
| V1-7 | 판정 규칙 | 4종 조건이 W3 이전과 동일 |

V1-5가 중요하다. **확인이 필요 없는 동작까지 멈추면** 모든 요청이 사용자 확인을 요구하게 된다.

### W6-V2 — 외부 상태 불변 (최우선)

각 확인 대상에 대해 **중단 상태에서 DB를 직접 조회**한다.

| 케이스 | 확인 | 기대 |
| --- | --- | --- |
| V2-1 | `manage_tasks.delete` 중단 시 Task 조회 | **Task가 존재한다** |
| V2-2 | `review_proposal.ignore` 중단 시 제안 상태 | 변경 없음 |
| V2-3 | `review_action_items.reject` 중단 시 승인 상태 | 변경 없음 |
| V2-4 | `analyze_meeting` 중단 시 분석·transcript | 생성되지 않음 |
| V2-5 | 취소 후 | 여전히 변경 없음 |
| V2-6 | `validate_skill_and_arguments` 노드의 호출 계측 | Repository 쓰기 0회 |

**이 검증이 확인 절차의 존재 이유를 지킨다.** 사용자가 "아니오"를 눌렀는데 이미 삭제됐다면 확인을
물어본 의미가 없다.

### W6-V3 — resume 재개

| 케이스 | 방법 | 기대 |

### 2.7.1 V7-7이 이 전환의 핵심 증명이다

다른 케이스는 "확인 기능이 동작한다"를 본다. V7-7만 **"프로세스 메모리에 의존하지 않는다"** 를
증명한다.

```
1. "그 할 일 지워줘" 입력      → Task가 INPUT_REQUIRED로 멈춤
2. DB 조회                     → Task가 아직 살아 있음 (W6-V2)
3. **서버 프로세스 재시작**     ← 여기가 핵심
4. UI에서 확인 버튼 클릭        → resume
5. 결과 확인                   → 멈춘 지점부터 실행, Task 삭제됨
```

**3번 없이는 재요청 방식과 구분되지 않는다.** 현재 구조(`pending_action` 반환)도 1·2·4·5는 통과한다
— 프론트가 상태를 들고 있기 때문이다. 서버가 죽었다 살아난 뒤에도 재개되는 것은 Checkpointer가
있어야만 가능하다.

**기록할 것**

| 항목 | 내용 |
| --- | --- |
| 재시작 전 Task 상태 | `INPUT_REQUIRED` |
| 재시작 전 Checkpoint | `get_state_history()` 출력 |
| 재시작 후 resume 결과 | 실행된 `skill_id`, LLM 호출 횟수(0) |
| 소요 | 재개가 처음부터 다시 하지 않았음을 보이는 근거 |

이 기록이 [W9](30-9-w9-docs-evidence.md)의 전환 결과 보고에서 "LangGraph를 썼다"의 실물 증거가 된다.

**V7-4가 UI 변경의 핵심 검증이다.** 현재 폴링 루프는 `INPUT_REQUIRED`를 모르므로 5분 후 "시간 내에
끝나지 않았습니다"를 띄운다.

**V7-6은 W6-T6에서 동작을 정해야 한다.** 확인 대기 중 사용자가 다른 말을 하면?

## 3. 검증 실행 순서

```
W6-T2 완료:
  1. W6-V2  외부 상태 불변  ← 가장 먼저
  2. W6-V1  interrupt 중단

W6-T4·T5 완료:
  3. W6-V3, V4, V5  resume
  4. W6-V6          취소

W6-T6 완료:
  5. W6-V7  UI 육안 검수  ← 사용자 판정

W6-T7~T9 완료:
  6. W6-V8, V9
  7. W6-V10 스냅샷 (변경 전 → 갱신 → 갱신 후)
  8. W6-V11 전체 회귀
```

**W6-V2를 가장 먼저 하는 이유:** 이것이 깨진 채 나머지를 만들면, 확인 기능 전체가 무의미한 상태로
완성된다.

## 4. 판정 규칙

- **W6-V2(외부 상태 불변) FAIL이면 W6 전체 미완료.** 다른 검증이 전부 통과해도 확인 절차의 의미가
  없다
- **W6-V7(육안 검수)은 사용자 판정.** 자동 승인 불가
- W6-V10-2(3건 이상 FAIL)는 의도하지 않은 변경이므로 **중단하고 원인 조사**
- W6-V8은 W6-T1 판정에 따라 범위가 달라진다
