## 2. 단계 성격 — 운영 품질 단계

W8은 기능을 추가하지 않는다. 이미 동작하는 것을 **운영할 수 있게** 만든다.

| 항목 | W7까지 | W8 이후 |
| --- | --- | --- |
| 재시도 | 노드 내부 루프(W3에서 그대로 옮김) | 노드 `RetryPolicy` |
| 재시도 정책 | 지점마다 다름 | 정의된 두 정책 |
| 실행 관측 | 없음 | 노드 단위 로그 |
| 실패 격리 | Skill별 구현 | 노드 단위 |

### 2.1 W2에서 정의하고 W8에서 적용한다

재시도는 두 단계에 걸쳐 있다([30-2-2](30-2-2-scope.md) §3.1).

| 단계 | 하는 일 |
| --- | --- |
| **W2** | 오류 분류 함수와 `RetryPolicy` 객체를 **정의**. 모델 객체의 라이브러리 기본 재시도를 끔 |
| **W8** | 정의된 정책을 **전 노드에 적용**. 노드 내부 루프 제거. 부작용 노드 제외 |

W2에서 정책을 정의하지 않았다면 W3의 LLM Skill들이 각자 재시도를 구현했을 것이고, W8에서 11곳을
되돌려야 했다.

### 2.2 W8이 다루는 핵심 문제

**재시도 정책이 하나가 아니다.** W2 조사에서 발견한 사실이다([30-2-5](30-2-5-design.md) §5.2).

| 지점 | 시도 | 재시도 대상 |
| --- | --- | --- |
| `assistant_router` 계열 | 3회 | 네트워크 오류만. **HTTP 4xx/5xx 제외** |
| `weekly_report` 계열 | 2회 | `LLMProviderError` — timeout·429·5xx·Schema **포함** |

W8은 이 둘을 **통일하지 않고 각각 보존**한다. 통일은 동작 변경이므로 전환 범위 밖이다.

## 5. 용어

| 용어 | 정의 | 주의 |
| --- | --- | --- |
| **`RetryPolicy`** | LangGraph가 노드 단위로 재시도를 관리하는 설정 | 함수 내부 `for attempt in range(...)`와 다르다 |
| **재시도 계층** | HTTP 요청 / 노드 / Provider Client의 3계층 | 각 계층의 주체가 다르다(96번 §8) |
| **부작용 노드** | 외부 상태를 바꾸는 노드 | **재시도를 붙이면 안 된다** |
| **멱등 노드** | 재실행해도 결과가 같은 노드 | 재시도 안전 |
| **핵심/보조 소스** | 실패 시 전체 실패 / 부분 결과 | Skill마다 다르다 |
| **`NETWORK_ONLY_RETRY`** | 3회, 네트워크 오류만 | `assistant_router` 계열 |
| **`PROVIDER_ERROR_RETRY`** | 2회, Provider 오류 포함 | `weekly_report` 계열 |

## 6. 재시도 계층 (96번 §8)

혼동하지 않는 것이 W8의 요점이다.

| 계층 | 주체 | 재시도 대상 | 멱등성 근거 |
| --- | --- | --- | --- |
| HTTP 요청 전체 | **Orchestrator** | 요청 실패 | 같은 `message_id` |
| 노드 | **LangGraph `RetryPolicy`** | 노드 내 Provider 호출 | 노드 재실행이 안전해야 함 |
| Provider Client | **없음** | — | 클라이언트 내부 재시도를 두지 않는다 |

**W4-D1(멱등성 구현)이 첫 번째 계층을 성립시켰다.** 이제 Orchestrator가 재시도해도 중복 실행되지
않는다.
