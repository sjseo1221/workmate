## W5-K1 — Graph가 예외를 감싸 오류 매핑 붕괴

**설명** Graph를 거친 `ValueError`·`RuntimeError`가 다른 타입으로 바뀌어
`except (ValueError, RuntimeError)`에 안 걸린다.

**결과** 예외가 `ServerErrorMiddleware`까지 올라가 **CORS 헤더 없는 500**이 된다. 브라우저는
`TypeError: Failed to fetch`만 본다.

**이것은 이미 일어난 적이 있다** — 2026-08-15, `analyze_meeting`에서 재현.
[internal_chat.py:402-425](../workmate-agent/app/internal_chat.py#L402)의 주석이 전말을 기록한다.

**왜 재발하기 쉬운가**

| 경로 | 위험 |
| --- | --- |
| Subgraph 경계 | 하위 Graph의 예외를 상위가 감쌀 수 있다 |
| `RetryPolicy`(W8) | 재시도 소진 시 원 예외가 유지되는지 |
| Root 노드의 방어적 `try/except` | 좋은 의도로 감싸면 매핑이 깨진다 |

**완화**
- 설계 결정 W5-D2: 노드는 예외를 그대로 올린다
- Root 노드에서 광범위한 `except Exception` 금지
- **W5-V5-6 단위 검증** — `ainvoke`가 `ValueError`를 그대로 raise하는지
- **W5-T9 로컬 HTTP 확인** — CORS 헤더 존재
- W5-V5 FAIL이면 W6 진행 금지

**대응 계획** 감싸진다면 진입점에서 원 예외를 꺼내 매핑한다(`exc.__cause__` 추적). 단 그것이
필요하다는 것 자체가 Graph 설계를 다시 볼 신호다.

## W5-K2 — 이벤트 순서·내용 변화

**설명** A2A 이벤트가 순서대로 오지 않거나, 순서는 맞는데 Artifact 내용이 빈다.

**이미 일어난 적이 있다** — 2026-08-14. HANDOFF 기록:

> `search_meetings`·`analyze_meeting`이 실제로는 `TASK_STATE_COMPLETED`인데 응답이 비어 있는 별도
> 결함을 발견했다. 원인은 `app/a2a/runtime.py`의 `_artifact_parts`가 구조화 `data`만 있는 결과에서
> `text` Part를 생략해, `text`만 읽는 Orchestrator Client가 결과를 놓치는 것이었다.

**W5에서 재발하는 경로**

| 경로 | 위험 |
| --- | --- |
| `build_artifact` 노드로 이관 | `_artifact_parts()`의 text Part 처리를 빠뜨림 |
| 이벤트 발행 순서 조정 | "더 자연스럽게" 바꾸고 싶은 유혹 |
| Graph 실행 위치 변경 | `start_work()` 호출 시점 |

**완화**
- W4-K7에서 이미 `build_artifact` 이관을 경계했다
- W5-V2-3에서 **Artifact Part 내용**까지 확인
- W5-D5: `start_work()` 호출 위치 유지
- W5-T9에서 실제 응답 확인

## W5-K3 — `save_checkpoint` 제거의 파급

**설명** 제거하면서 Task 저장이나 `record_message`까지 건드려 FK 참조가 깨진다.

**배경** [runtime.py:214-215](../workmate-agent/app/a2a/runtime.py#L214) 주석:

> Message·Checkpoint·Artifact가 FK로 Task Snapshot을 참조하므로 SDK EventQueue보다 먼저 최소
> Task를 영속화한다.

**완화**
- 제거 대상은 `save_checkpoint(...)` **호출 한 덩어리**뿐
- `task_store.save(submitted, ...)`와 `record_message(...)`는 남긴다
- 메서드 자체(`PersistentTaskStore.save_checkpoint`)는 W7에서 제거

## W5-K4 — 백그라운드 예외 삼킴

**설명** Graph 실행 중 예외가 `_run_skill_in_background()`의 `except`에 안 걸려, Task가 `WORKING`에
영원히 남는다.

**결과** UI는 5분 폴링 후 "시간 내에 끝나지 않았습니다" 타임아웃. 실제 원인은 보이지 않는다.

**현재 방어** 코드에 이미 방어가 있다.

```python
except Exception as exc:  # pragma: no cover - Task를 WORKING에 영원히 묶어두지 않기 위한 방어
    await _save_task_status(task_id, FAILED, user_id, message_text=f"unexpected error: {exc}")
```

**완화**
- 이 `except Exception`을 **반드시 유지**한다
- W5-V4-6에서 예상치 못한 예외를 주입해 확인
- Graph가 예외를 비동기 컨텍스트에서 삼키지 않는지 확인(`asyncio` Task 예외 처리)

**특히 주의** `background_tasks`로 실행되므로 예외가 어디로 가는지 추적이 어렵다. 명시적 검증이
유일한 수단이다.

## W5-K5 — Windows Event Loop 충돌

**설명** 비동기 Checkpointer를 앱 lifespan에 결합하면서 Selector Event Loop 정책과 충돌한다.

**배경** [main.py](../workmate-agent/app/main.py)의 Event Loop·IPv4 설정은 실사용 대응이다.
`_ipv4_only_getaddrinfo`는 2026-08-19 DNS 문제와도 관련이 있다.

**완화**
- W2-V4·W4-V7에서 Checkpointer 동작을 이미 확인
- W5-V9-4에서 Windows 환경 확인
- 충돌 시 **Checkpointer 쪽을 조정**한다. Event Loop 설정은 건드리지 않는다

## W5-K6 — `warnings` metadata 유실

**설명** `_persist_task()`가 하던 Artifact metadata의 `warnings` 저장을 `persist_result`가 안 하면,
비동기 Skill의 부분 실패 경고가 사라진다.

**배경** [internal_chat.py:252-258](../workmate-agent/app/internal_chat.py#L252) 주석:

> `warnings`도 여기 함께 싣는다 — Task Store Snapshot(Polling으로 조회하는 값)엔 원래 Artifact만
> 남고 동기 응답의 `warnings` 필드는 저장되지 않았다. (…) `_ASYNC_SKILLS`는 결과를 Polling으로만
> 받으므로 여기 없으면 부분 실패 경고가 조용히 사라진다.

**왜 눈에 안 띄나** 동기 Skill은 응답 바디에 `warnings`가 있어 정상으로 보인다. 비동기 Skill만
영향받고, 그것도 부분 실패가 발생했을 때만 드러난다.

**완화**
- 설계 결정 W5-D1
- **W5-V4-3에서 비동기 Skill의 Task metadata 확인**
- W1 케이스에 비동기 Skill의 부분 실패가 있는지 확인

## W5-K7 — 기준선 없이 교체

**설명** 교체 전에 현재 동작을 고정하는 테스트가 없어, 교체 후 "원래 이랬나?"를 확인할 수 없다.

**영향** 회귀가 생겨도 발견되지 않거나, 발견해도 "원래 그랬던 것 같다"고 넘어간다.

**완화**
- **W5-T0을 가장 먼저** 수행
- 부족한 계약(이벤트 순서·오류 매핑·CORS·비동기 실패)에 대해 교체 전에 테스트 추가
- 스냅샷(W1)이 응답 값은 커버하지만, **전송 계층 계약은 커버하지 않는다** — 그래서 별도 기준선이
  필요하다

**스냅샷이 못 잡는 것**

| 계약 | 왜 스냅샷 밖인가 |
| --- | --- |
| 이벤트 순서 | Workflow 결과가 아니라 전송 동작 |
| HTTP 상태 코드 | 동상 |
| CORS 헤더 | 동상 |
| Route allowlist | 동상 |

---

## W5-K8 — 멱등성 변경의 외부 영향

**설명** W4-D1로 같은 `message_id` 재전송이 재실행되지 않게 되는데, 오케스트레이터가 HTTP 재시도 시
같은 `message_id`를 보낸다면 동작이 달라진다.

**판단** 이는 **의도한 개선**이다. 96번 §8도 "HTTP 계층 재시도는 Orchestrator가 같은 `message_id`로
담당한다"고 규정한다. 즉 재시도 시 기존 결과를 받는 것이 설계 의도다.

**그러나 확인이 필요하다**

| 확인 | 방법 |
| --- | --- |
| 재전송 시 응답 형태 | W5-T9 로컬 HTTP |
| 오케스트레이터가 그 응답을 처리할 수 있는지 | W6 어댑터 검토에서 |

**완화**
- W5-T9에서 재전송 응답을 기록
- W6의 어댑터 검토 항목으로 전달
- 증빙에 사용자 관찰 가능 변경으로 명시

---

## W5-K9 — Checkpointer 연결 누수

**설명** 요청마다 Checkpointer를 만들거나 종료 시 정리하지 않아 연결이 쌓인다.

**완화**
- 프로세스 단위 싱글턴(W5-R10)
- lifespan에서 정리
- W5-V9-2에서 요청 반복 후 연결 수 확인
