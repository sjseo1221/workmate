## 2. 작업 상세

### W4-T0 — 설계 결정 확정

**내용**

1. **W4-D1 멱등성 방침 확정** — 현재 `record_message()` 반환값이 무시되고 있고, 96번 설계대로
   구현하면 동작이 바뀐다([30-4-5](30-4-5-design.md) §3). B안(설계대로 구현)이 기본이지만 착수 전
   재확인한다
2. **W4-D5 진행 중 중복 정책 확정** — 같은 `message_id`가 아직 실행 중일 때의 동작. 현재 코드에
   정의돼 있지 않다. a안(진행 중 Task Snapshot 반환)이 기본
3. W4-D2 Schema 로딩 경로 확인 — [internal_chat.py:59-73](../workmate-agent/app/internal_chat.py#L59)의
   `_schema_validator()` 방식 재사용
4. W4-D3 `runtime_bootstrap` 처리 — 기존 테스트가 쓰는지 확인
5. **스냅샷 27건을 Schema로 사전 검증** — [30-4-5](30-4-5-design.md) §5.4

**5번이 특히 중요하다.** `validate_contract`는 운영 경로에 없던 검증을 새로 넣는 것이므로, 기존
결과가 통과하는지 먼저 확인해야 한다. 실패하는 케이스가 있으면 **현재 존재하는 계약 위반**이므로
기록하고 보고한다.

**난이도** 중간 / **비중** 15%

### W4-T1 — 멱등성 노드

**내용**

```
idempotency_check(state)
  → Task Store에서 message_id 조회
  → 결과에 따라 state["idempotent_hit"] 설정

restore_result(state)
  → 저장된 응답을 state["result"]로 복원
```

**주의**
- 멱등성 원장은 **Task Store**다. Checkpointer를 쓰지 않는다(W4-R5)
- `persist_result`가 `response=`를 넘겨 복원할 응답을 저장해야 한다 — 현재 A2A 경로는 안 넘긴다
- `restore_result` 경로에서도 식별자가 보존돼야 한다(W4-R4)
- 진행 중 중복 정책(W4-D5)을 여기서 구현

**난이도** 중간 — 동작 변경이 포함되므로 검증이 중요

---

### W4-T2 — Schema 검증 노드

**내용**

```
validate_contract(state)
  → 승인 Schema로 result 검증
  → 통과: task_state 전이 허용
  → 실패: task_state=FAILED, 정의된 오류
```

**주의**
- Schema 로딩 실패를 **조용히 넘기지 않는다** — 검증이 꺼진 채 배포되면 계약 위반이 방치된다
- 기존 `_schema_validator()`의 로딩 방식 재사용(W4-D2)
- W4-T0의 사전 검증에서 실패한 케이스가 있으면 그 사실을 반영

**난이도** 중간

### W4-T3 — 나머지 공통 노드

**내용**

| 노드 | 핵심 |
| --- | --- |
| `initialize_state` | 식별자 5종 + `now`·`timezone` 주입, `task_state=WORKING`. **`now`를 여기서 확정**해야 노드마다 시각이 어긋나지 않는다 |
| `build_artifact` | [`_artifact_parts()`](../workmate-agent/app/a2a/runtime.py#L289)의 로직 이관. `markdown` 있으면 우선, 없으면 `text/plain` JSON |
| `persist_result` | Task Store에 상태·Artifact 저장. `record_message(response=...)` 포함 |

**`build_artifact` 주의:** 2026-08-14에 고친 버그가 있다 — 구조화 `data`만 있는 결과에서 `text` Part를
생략해 Orchestrator가 결과를 놓쳤다. `markdown` 없는 구조화 결과에도 `text/plain` Part를 함께 싣는
동작을 유지한다.

**난이도** 중간

### W4-T8 — Root 경유 스냅샷 재대조

**내용** W1 케이스 27건을 **Root Graph를 통해** 실행해 대조한다.

```
W3: Subgraph 직접 호출 → 대조
W4: Root Graph 경유    → 대조   ← 여기
W5: 운영 경로 경유     → 대조
```

**왜 다시 대조하는가** W4가 추가한 공통 노드 6종이 결과를 바꿀 수 있다. 특히

| 노드 | 바꿀 수 있는 것 |
| --- | --- |
| `initialize_state` | `now`·`timezone` 주입 방식이 다르면 날짜 계산이 달라진다 |
| `validate_contract` | 통과하지 못하면 `COMPLETED`에 도달 못 함 |
| `build_artifact` | Artifact 이름·설명·Part 구성 |
| `persist_result` | (결과에는 영향 없지만) 저장 내용 |

**차이 발견 시 판정**

```
1. 공통 노드가 값을 덮어썼는가?  → 노드 수정
2. Schema 검증이 거부했는가?     → W4-T0의 사전 검증 결과와 대조
3. 멱등성 경로를 탔는가?         → 케이스 격리 확인
```

**난이도** 중간
