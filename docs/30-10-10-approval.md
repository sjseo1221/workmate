# W10-10 — 승인 경계

> [30-10-w10-react-agent.md](30-10-w10-react-agent.md) §10의 상세 문서.

W10은 **착수 전·계약 확정·완료 시** 세 번의 승인이 필요하다. 이 문서는 각 승인의 대상과 판단 근거를
모아 둔다.

## 1. 승인 지점 정리

| 시점 | 대상 | 작업 | 미승인 시 |
| --- | --- | --- | --- |
| **착수 전** | 결정 D7-1~D7-7 | W10-T1 | **착수 금지** |
| **착수 전** | 05번 문서 §1 개정안 | W10-T1 | **착수 금지** |
| 계약 확정 | `executed_skill_ids` 설계안 | W10-T8 | 구현 보류 |
| 완료 시 | UI 육안 검수 + 비용 수용 | W10-T11 | 완료 보류 |

### 1.1 지금 확정하지 않는다

**D7은 W10 착수 시점에 확정한다.** W10은 W9 완료 후이므로 여덟 단계 뒤다.

| 결정 | W2~W6을 거치면 달라질 수 있는 근거 |
| --- | --- |
| D7-2 (커스텀 StateGraph) | W2~W4에서 Graph를 실제로 만들어 본 경험 |
| D7-6 (`executed_skill_ids`) | W6에서 계약을 한 번 바꿔 본 비용 |
| D7-3 (도구 집합) | W3에서 Skill Subgraph 10개의 경계가 드러남 |
| D7-4 (확인 지점) | W6의 `interrupt` 구현 경험 |

**미리 정하면 경험 없이 정한 것을 되돌리는 절차가 하나 더 생긴다.** 이 문서의 권장안은 근거와 함께
남겨 두고, 착수 시점에 이 표를 놓고 판단한다.

05번 개정도 같다. 지금 고치면 **W1~W9 동안 문서가 구현보다 앞서 나간다** — W9가 없애려는 문제와 같은
종류다.

## 2. 결정 D7-1 ~ D7-7

| ID | 결정할 것 | 선택지 | 권장 |
| --- | --- | --- | --- |
| **D7-1** | 적용 범위 | (A) `assistant_ask`만 (B) A2A 공개 경로까지 | **A** |
| **D7-2** | 구현 방식 | (A) `create_react_agent` prebuilt (B) 커스텀 StateGraph | **B** |
| **D7-3** | 도구 집합 | (A) Skill 10개 그대로 (B) 읽기/쓰기 분리 재설계 | **A로 시작** |
| **D7-4** | 확인 지점 | (A) 파괴적 도구 호출 직전 interrupt (B) 계획 전체를 먼저 승인 | **A** |
| **D7-5** | 루프 예산 | 반복 상한·토큰 상한·시각 상한 | **반복 6회 + 시간 상한** |
| **D7-6** | 공개 계약 | (A) `executed_skill_id` 배열로 확장 (B) 단수 유지(마지막 도구) | **A** |
| **D7-7** | 시점 | (A) W9 완료 후 별도 (B) W3·W6에 접어 넣기 | **A** |

### 2.1 D7-1 — `assistant_ask`만

나머지 10개 Skill은 진입점이 명확한 결정적 작업이다.

```
"이번 주 주간보고 써줘"  → weekly_report   (판단할 게 없다)
"오늘 브리핑"            → daily_briefing  (동상)
```

**Agent가 필요한 곳은 "무엇을 해야 할지 모르는" 요청뿐이고, 그건 `assistant_ask`다.** 다른 Skill을
ReAct로 감싸면 비용과 불확실성만 늘고 얻는 게 없다.

### 2.2 D7-2 — prebuilt를 권하지 않는 이유

LangGraph의 `create_react_agent`는 빠르지만 우리 요구를 다 못 담는다.

| 우리 요구 | prebuilt |
| --- | --- |
| 파괴적 도구 직전 `interrupt` | 커스터마이즈 필요 |
| 도구별 확인 규칙 4종 | 동상 |
| 루프 예산과 중단 사유 기록 | 제한적 |
| 결정적 규칙 보존 검증 | 직접 만들어야 |
| `user_id` 전파 | 직접 |

**커스텀 StateGraph로 ReAct 루프를 짜되 구조는 표준 패턴을 따른다**([30-10-5](30-10-5-design.md) §1).

**부수 효과** 직접 짜면 Graph 구조가 코드에 드러나 `draw_mermaid()` 출력이 설계 문서와 대조 가능해진다
(W4-R11과 같은 성격).

### 2.3 D7-3 — Skill 10개로 시작

읽기/쓰기를 분리해 도구를 재설계하는 안(B)이 더 깔끔할 수 있다. 하지만

| | A (Skill 10개) | B (재설계) |
| --- | --- | --- |
| W3 Subgraph 재사용 | 그대로 | 다시 나눠야 |
| 규칙 회귀 대조 | Skill 단위로 1:1 | 대응이 흐려짐 |
| 확인 대상 4종 | 그대로 | 다시 판정 |

**A로 시작해 실제 사용에서 도구 경계가 불편하면 그때 재설계한다.** 규칙 회귀 검증이 Skill 단위로
1:1 대조되는 것이 A의 결정적 장점이다.

### 2.4 D7-4 — 도구 호출 직전 확인

계획 전체를 먼저 승인받는 안(B)은 "3단계로 진행할까요?"를 묻는 방식이다.

| | A (도구 직전) | B (계획 승인) |
| --- | --- | --- |
| 사용자가 보는 것 | "이 회의를 분석할까요?" | "회의 검색 → 분석 → 등록을 할까요?" |
| W6 재사용 | 그대로 | 새 프로토콜 |
| 재계획 | 자연스럽다 | 계획이 틀리면 처음부터 |
| 확인 대상 4종 | 그대로 적용 | 재정의 필요 |

**A를 권한다.** W6의 확인 UI와 계약을 그대로 쓸 수 있고, 확인 대상 4종의 의미가 유지된다.

### 2.5 D7-5 — 반복 6회

| 회수 | 커버하는 시나리오 |
| --- | --- |
| 1~2 | 단일 도구 (현재 구조와 동등) |
| 3~4 | 조회 → 실행 |
| 5~6 | 조회 → 실행 → 재조회 → 확인 |
| 7+ | **대부분 헤매는 중이다** |

토큰·시간·중복 호출 상한도 함께 둔다([30-10-5](30-10-5-design.md) §7).

### 2.6 D7-6 — 계약이 또 바뀐다

현재 `assistant_ask` 응답은 `executed_skill_id`가 **단수**다.

```json
{"type": "assistant_reply",
 "data": {"reply": "...", "executed_skill_id": "manage_tasks", "pending_action": null}}
```

ReAct는 한 요청에서 도구를 여러 번 부를 수 있으므로 단수로는 표현이 안 된다.

**W6에서 이미 한 번 바꾼 계약을 또 바꾸는 것**이다. UI·어댑터·02번 문서가 다시 영향받는다.

| 영향 | 내용 |
| --- | --- |
| `workmate-ui` | 응답 파싱 |
| 오케스트레이터 어댑터 | **타 저장소.** 영향 확인 후 보고, 수정은 승인 필요 |
| [02번 문서](02-a2a-interface.md) | 계약 기술 |
| W1 스냅샷 `assistant_ask` 4건 | 재작성 |

**B안(단수 유지, 마지막 도구만)도 가능하다.** 계약은 안 바뀌지만 다단계 실행이 외부에서 보이지 않는다.
**감사 관점에서 좋지 않다** — 무엇이 실행됐는지 기록이 남지 않는다.

## 3. 05번 문서 §1 개정안

### 3.1 현재 표

| LLM | 코드 |
| --- | --- |
| 요약과 자연어 표현 | 날짜 범위 계산 |
| 통합 회의 분석 Text와 Action Item 후보 추출 | 인증과 접근권한 |
| 보고서 문장 작성 | 중복 제거와 상태 전이 |
| 검색 문맥 기반 답변 | 우선순위 점수와 출력 검증 |

**"도구를 고르고 실행 순서를 정한다"가 LLM 칸에 없다.**

### 3.2 개정안

| LLM | 코드 |
| --- | --- |
| 요약과 자연어 표현 | 날짜 범위 계산 |
| 통합 회의 분석 Text와 Action Item 후보 추출 | 인증과 접근권한 |
| 보고서 문장 작성 | 중복 제거와 상태 전이 |
| 검색 문맥 기반 답변 | 우선순위 점수와 출력 검증 |
| **도구 선택과 호출 순서 (`assistant_ask` 한정)** | **도구가 반환한 값의 소유** |

**원칙에 추가할 문장**

```
- assistant_ask에서 LLM은 도구 선택과 호출 순서를 정한다. 그 범위는 "어떤 도구를
  부를지"에 한정하며, 도구가 반환한 값을 바꾸지 않는다.
- 날짜 범위는 LLM이 계산하지 않는다. 상대 표현(예: 지난주)만 전달하고 코드가 날짜로
  변환한다.
- 도구 인자에 user_id·task_id·thread_id를 포함하지 않는다. 인증된 요청에서 코드가
  주입한다.
- 루프 실행에는 상한을 두고, 초과 시 부분 결과와 warnings를 반환한다.
```

### 3.3 개정이 "넓히기"만은 아니다

| 방향 | 항목 |
| --- | --- |
| **넓힘** | 도구 선택과 호출 순서 |
| **좁힘** | 날짜 계산을 LLM에서 코드로 되돌림 (W10-D1) |
| **명문화** | "Agent는 도구 반환값을 바꾸지 않는다" |

**두 번째 줄이 중요하다.** 지금은 프롬프트가 "오늘-7일" 계산을 LLM에 지시하고 있어, 05번 문서의 "날짜
범위 계산은 코드"와 이미 어긋나 있다. W10은 이 어긋남을 **바로잡으면서** 도구 선택 권한을 넓힌다.

### 3.4 `AGENTS.md`와 충돌하지 않는다

| `AGENTS.md` 규칙 | W10 이후 |
| --- | --- |
| 우선순위 점수는 결정적으로 계산한다 | 유지. Domain 소유 |
| LLM이 Task 순위와 근거 ID를 생성·변경하지 않는다 | 유지. W10-V5가 강제 |
| 모든 조회에 `user_id` 조건을 적용한다 | 유지. W10-V6이 강제 |

**따라서 `AGENTS.md` 수정 제안은 없다.** 충돌 지점을 찾지 못했다.

## 4. 대안 — W3·W6에 접어 넣기 (D7-7의 B안)

| | A안(W10 별도) | B안(전환에 포함) |
| --- | --- | --- |
| W9 완료 판정 | 깨끗함 | **설명 불가 차이가 섞임** |
| 원인 분리 | 가능 | **불가** |
| 총 기간 | 길다 | 짧다 |
| 승인 횟수 | 3회(W6·W9·W10) | 2회 |
| UI 작업 | 두 번(W6·W10) | 한 번 |
| 롤백 | ReAct만 되돌림 | 전환 전체가 얽힘 |

### 4.1 A안을 권한다

전환의 완료 기준이 **"의도적으로 바꾼 것 외에는 안 바뀌었다"**인데, ReAct를 섞으면 그 판정이
불가능해진다.

```
[B안에서 스냅샷 차이가 나왔을 때]

assistant_ask 응답이 다르다
  → Graph 전환 때문인가?
  → ReAct 때문인가?
  → 둘 다인가?
판정 불가. 원인 추적에 드는 시간이 아낀 기간보다 크다.
```

### 4.2 B안의 유일한 장점 — UI 작업 한 번

W6에서 확인 프로토콜을, W10에서 `executed_skill_ids`를 각각 UI에 반영해야 한다. B안이면 한 번이다.

**그래도 A안을 권한다.** UI 작업 한 번을 아끼려고 전환 판정을 포기하는 거래다.

### 4.3 B안을 택한다면

```
[ ] W3의 assistant_ask Subgraph를 처음부터 ReAct로 만든다
[ ] W1 스냅샷의 assistant_ask 4건을 "의도적 변경"으로 미리 분류
[ ] W6의 계약 변경에 ReAct 계약(executed_skill_ids)을 함께 담는다
[ ] 05번 개정을 W1 이전에 승인받는다
[ ] W9의 "설명 불가 차이 0" 기준에서 assistant_ask를 제외하고, 제외 사유를 기록
```

**마지막 항목이 대가다.** 27건 중 4건에 대해 "설명 불가 차이 0"을 포기한다.

## 5. 승인 요청 형식

### 5.1 착수 전 (W10-T1)

```
[결정 요청]
D7-1 적용 범위        권장 A (assistant_ask만)
D7-2 구현 방식        권장 B (커스텀 StateGraph)
D7-3 도구 집합        권장 A (Skill 10개 그대로 시작)
D7-4 확인 지점        권장 A (도구 호출 직전)
D7-5 루프 예산        권장 반복 6회 + 토큰·시간·중복 상한
D7-6 공개 계약        권장 A (executed_skill_ids 복수)
D7-7 시점             권장 A (W9 완료 후 별도)

[문서 개정 승인 요청]
05번 §1 — LLM 칸에 "도구 선택과 호출 순서(assistant_ask 한정)" 추가,
          원칙 4개 문장 추가, 날짜 계산을 코드로 명시

[예고]
공개 계약 변경 (executed_skill_id 단수 → 복수). 설계안은 W10-T8에서 별도 승인 요청
```

### 5.2 완료 시 (W10-T11)

```
[육안 검수 요청]
- 다단계 요청의 확인 배너가 각 도구마다 뜨는지
- 확인 거부 후 대안 제시가 자연스러운지
- 예산 초과 시 부분 결과 안내가 이해되는지

[수용 판단 요청]
- 선택 안정성: N/10
- 토큰 사용량: 현재의 N배
- 응답 지연: 현재의 N배
→ 수용하시겠습니까?
```
