## 2. 문서 개정 승인

### 2.1 왜 승인이 필요한가

계획서 §5 W9의 초판 서술: "이 단계의 문서 수정은 사용자 승인을 받고 진행한다."

문서는 **프로젝트의 공식 기록**이다. 특히 96·97번은 설계 기준 문서이고, 잘못 고치면 이후 작업이
틀린 전제로 진행된다.

### 2.2 승인 요청 형식

W9-T6에서 다음을 제시한다.

```
[문서 개정안]

97번 (큼)
  - §1 "현재/목표 대조표" → "전환 이력"으로 성격 변경 (W9-D1)
  - 표현 지침 정정: "LangGraph로 구현 완료가 아니라…" → 구현 완료 서술
  - §3·§4 Registry 기반 도식 → Root Graph 기반

96번 (중간)
  - 문서 성격: "가정형 목표 아키텍처" → "구현 기준 아키텍처"
  - 상단 인용구 정정
  - §5·§6 노드 구성을 실제 구현과 대조해 반영
  - §11 불변식 유지

07번 (중간)
  - Workflow Runtime 전제 서술 → Graph 기준

02·06번 (확인)
  - W6·W7에서 이미 개정됨. 정합성 확인 결과 첨부

[별도 제안 — 반영하지 않음]
AGENTS.md: "M0.1은 (…) Checkpoint의 최소 인프라 Migration을 소유한다"
  → W7에서 a2a_checkpoints를 DROP했으므로 소유 범위가 줄었다. 수정 필요 여부 판단 요청.
```

### 2.3 개정안을 먼저 보여주는 이유

문서를 고친 뒤 승인을 요청하면, 반려 시 되돌릴 범위가 크다. 특히 97번은 구조 자체가 바뀐다.

**"개정안 → 승인 → 반영" 순서를 지킨다.**

## 3. `AGENTS.md` — 제안만 한다

### 3.1 왜 고치지 않나

`AGENTS.md`는 **개발 규칙 문서**다. 저장소에서 구현·검수 작업을 수행하는 개발자와 AI Agent가 공통으로
따르는 기준이다.

전환 작업이 그 규칙을 임의로 고치면, 규칙의 권위가 사라진다.

### 3.2 제안 대상

| 항목 | 현재 서술 | W7 이후의 사실 |
| --- | --- | --- |
| M0.1의 소유 범위 | "A2A Task·Message 멱등성·Artifact·`task_id ↔ thread_id`·**Checkpoint**의 최소 인프라 Migration을 소유" | `a2a_checkpoints`가 DROP됨 |

**제안 형식**

```
[AGENTS.md 수정 제안]
위치: "구현 규칙" 절의 M0.1 소유 범위
현재: "…Checkpoint의 최소 인프라 Migration을 소유하고"
사실: W7(D6=B)에서 a2a_checkpoints를 DROP했다. Checkpoint는 이제 LangGraph
      Checkpointer가 담당하며 M0.1 Migration의 소유가 아니다.
제안: 해당 서술에서 Checkpoint를 제외하거나, "007에서 폐기됨"을 병기
판단: 사용자
```

### 3.3 다른 후보

전환 중 `AGENTS.md`와 충돌하거나 갱신이 필요해 보이는 항목이 더 있으면 함께 제안한다.

| 후보 | 확인 |
| --- | --- |
| "`workmate-agent`의 Python 의존성 원장은 `pyproject.toml`과 `uv.lock`" | 유효 |
| "공개 A2A 응답과 테스트 Fixture는 승인된 Artifact·Skill Schema를 통과해야" | 유효(W4에서 강화됨) |
| Route allowlist 규칙 | 유효 |

## 4. Merge·Push 승인

### 4.1 규칙

`AGENTS.md` 커밋·Push 규칙:

> 백로그 완료 시에는 구현·테스트·증빙을 로컬 커밋으로만 남기고 원격 Push하지 않는다. **하위
> 마일스톤의 모든 백로그와 통합 완료 기준이 승인된 시점에 관련 로컬 커밋을 한 번에 Push한다.**

> 마일스톤 완료와 Merge는 명시 승인 또는 완료 규칙에 따른 묵시 승인으로 `latest_approved_run_id`가
> 확정된 뒤에만 수행한다.

> Push 승인 질문도 **실제 Push 조건에 도달했을 때 한 번만** 한다.

### 4.2 Push 전 체크리스트

`AGENTS.md`가 요구하는 항목이다.

```
[ ] 변경 범위의 테스트          → W9-V8
[ ] git diff --check            → W9-V7
[ ] Schema·Contract Test 확인   → W9-V1 (완료 기준 2)
[ ] Secret 검사                 → W9-V6
[ ] 증빙 경로와 HANDOFF.md 갱신 → W9-T7, T9
```

### 4.3 승인 요청 형식

```
[Merge·Push 승인 요청]

전환 완료 상태
  기준 Commit: workmate-agent@8043c1e
  최종 Commit: {SHA}
  완료 기준: 9개 전항 충족
  스냅샷 diff: 동일 25 / 의도적 변경 2 / 설명 불가 0

Push 전 체크리스트: 5개 항목 완료

브랜치: feat/lg-rewrite
Merge 대상: main (또는 기준 브랜치)

후속 백로그: 10건 (별도 계획)
```

### 4.4 한 번만 묻는다

승인 요청을 잘게 쪼개지 않는다. W9에서 승인은 **두 번**이다.

```
W9-T6  문서 개정안
W9-T10 Merge·Push
```

**`AGENTS.md`의 "Push 승인 질문도 실제 Push 조건에 도달했을 때 한 번만 한다"를 따른다.**

## 5. 승인 대기 중 할 수 있는 것

### 5.1 문서 개정 승인 대기 중

| 가능 | 불가 |
| --- | --- |
| 증빙 작성(W9-T7) | 문서 반영 |
| diff 분류(W9-T1) | |
| 단계 문서 상태 갱신(W9-T8) | |
| Push 전 체크리스트 준비 | |

### 5.2 Merge·Push 승인 대기 중

| 가능 | 불가 |
| --- | --- |
| 로컬 커밋 정리 | **원격 Push** |
| 증빙 보완 | **Merge** |
| 후속 백로그 정리 | |

**로컬 커밋은 승인 없이 계속 쌓을 수 있다.** 금지되는 것은 원격 Push다.

## 6. 승인 경계 요약

전환 10단계 중 승인이 필요한 단계는 둘이다.

| 단계 | 승인 항목 | 횟수 |
| --- | --- | --- |
| W0~W5, W7, W8 | 없음(자동 승인) | 0 |
| **W6** | 계약안 C1~C5, UI 육안 검수 | 2 |
| **W9** | 문서 개정, Merge·Push | 2 |

**W6과 W9가 전환의 두 관문이다.** 하나는 공개 계약을 바꾸는 지점, 하나는 완료를 선언하는 지점이다.
