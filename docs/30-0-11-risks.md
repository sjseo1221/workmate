## W0-K1 — 작업 트리 불안정 (발생 → 해소)

**예상** 측정 시점의 트리에 정체불명의 변경이 있으면 기준선이 흔들린다.

**실제** 미커밋 변경 5개 파일이 있었다.

```
 M app/meeting_answer.py
 M app/workflows/assistant_router.py
 M app/workflows/meetings.py
 M tests/test_assistant_router.py
 M tests/test_meeting_answer.py
```

**왜 위험했나** 이 변경들이 **공개 응답 값에 영향을 준다.**

| 변경 | 영향 |
| --- | --- |
| `proposal_id` 추가 | `assistant_ask` 컨텍스트 |
| warning 분류 | `search_meetings` 결과 |

나중에 누가 되돌리면 W1 스냅샷이 어긋난다.

**조치** 사용자 질문 → "로컬 커밋으로 고정" → 2개 커밋.

**결과** 기준 Commit `8043c1e` 확정. 트리 clean.

## W0-K2 — 미검증 경로 (발생 → 해소)

**예상** 일부 경로가 SKIP된 채 전환에 들어가면 그 경로는 끝까지 미검증으로 남는다.

**실제** 12건 SKIP. 전부 `WORKMATE_TEST_DATABASE_URL` 미설정.

**왜 위험했나** 전환 범위 안의 테스트가 3건 포함돼 있었다.

| 테스트 | 검증 대상 |
| --- | --- |
| `test_m1_5_integration` (2건) | `daily_briefing`·`rank_priorities`의 Postgres 경계 |
| `test_postgres_integration` | Task Snapshot·Message 멱등성 |

또한 D6=B(`a2a_checkpoints` DROP)가 Postgres 경로에 영향을 준다.

**조치** 사용자 질문 → "지금 구성해서 기준선에 포함" → pgvector 컨테이너.

**결과** SKIP 0.

## W0-K3 — 환경 복구가 결과 계약을 바꿈 (발생 → 해소)

**예상** 환경을 고치다가 의존성 버전이 달라지면 기준선이 다른 환경의 것이 된다.

**실제** venv가 깨져 있어 복구가 불가피했다.

**어떻게 막았나**

| 조치 | 이유 |
| --- | --- |
| `uv sync` 사용 | `uv.lock`의 버전을 그대로 설치 |
| `uv python install 3.12` | 프로젝트 제약(`>=3.12,<3.13`) 준수 |
| 버전 변경 없음 | `pyproject.toml` 무수정 |

**결과** 3.12.4 → 3.12.13(패치 버전만 다름), 의존성 동일.

**남는 의문** 3.12.4와 3.12.13이 완전히 같은 결과를 내는가? 패치 버전 차이이므로 실용적으로 문제
없다고 판단했다. 기록해 둔다.

## W0-K4 — 기준선이 깨진 상태 (미발생)

**예상** 테스트가 실패하는 상태에서 전환을 시작하면 회귀를 판정할 수 없다.

**실제** 440건 전부 통과. 문제없었다.

**만약 실패가 있었다면** [30-0-12](30-0-12-rollback.md) §3에 따라 **전환 자체를 착수하지 않는다.**

## W0-K5 — 검증 명령 실패를 성공으로 오판 (예상 못 함, 발생)

**예상하지 못한 위험이다.**

**실제** 첫 테스트 실행에서 `| tail -60` 파이프를 썼더니 exit code 0이 나왔다.

```
error: Querying Python at ... failed with exit status exit code: 103
[stderr] No Python at '"C:\Python312\python.exe'

[exited with code 0]     ← 파이프라인의 마지막 명령(tail)의 코드
```

**만약 출력을 안 봤다면** "테스트가 통과했다"고 오판했을 것이다.

**조치** 출력을 파일로 리디렉션하고 `echo "exit=$?"`로 확인.

```bash
... > {log} 2>&1; echo "exit=$?"; tail -25 {log}
```

**교훈** **검증 명령의 결과를 신뢰하려면 그 명령이 제대로 실행됐는지부터 확인해야 한다.**

이 교훈은 이후 단계에도 적용된다 — 검증 결과를 파이프로 가리지 않는다.

## W0-K6 — 측정을 위해 코드를 고침 (미발생)

**예상** 테스트가 실패하면 "이것만 고치면 되는데" 하고 코드를 건드리게 된다.

**실제** 발생하지 않았다. 테스트가 전부 통과했기 때문이다.

**만약 실패가 있었다면** 고치지 않고 기록했을 것이다. 고치면 "무엇을 측정했는지" 불분명해진다.

## W0-K7 — 발견 사항 미기록 (미발생)

**예상** 조사 중 알게 된 사실을 "나중에 쓰겠지" 하고 넘어간다.

**실제** 3건을 기록했다(W0-F1~F3).

**기록하지 않았다면**

| 발견 | 기록 안 했을 때 |
| --- | --- |
| W0-F1 (`save_checkpoint` 미사용) | D6 결정에서 "마이그레이션이 필요한가" 고민 |

| W0-F3 (pgvector 필요) | 표준 postgres로 시도 → 실패 → 원인 추적에 시간 |

## 2. 예상하지 못한 것들

W0를 "그냥 테스트 한 번 돌리는 단계"로 생각했다면 전부 예상 밖이다.

| 사건 | 예상 |
| --- | --- |
| venv가 깨져 있었다 | 없음 |
| 미커밋 변경이 있었다 | 없음 |
| Docker 엔진이 꺼져 있었다 | 없음 |
| pgvector 이미지가 필요했다 | 없음 |
| 파이프가 exit code를 가렸다 | 없음 |
| `uv venv`가 `--clear`를 요구했다 | 없음 |

### 2.1 기준선 만들기가 생각보다 손이 많이 간다

작업 7개 중 4개가 "예상 밖 문제 해결"이었다.

```
W0-T1 트리 확인      → 미커밋 변경 발견
W0-T2 환경 점검      → 복구 필요
W0-T3 1차 실행       → 파이프 문제로 재실행
W0-T5 테스트 DB      → Docker 기동 + 이미지 선택
```

**이 기록이 다른 프로젝트에서도 참고가 될 것이다.**

## 3. 잔여 위험

| 위험 | 잔여 이유 | 처리 |
| --- | --- | --- |
| Python 3.12.4 vs 3.12.13 | 패치 버전 차이 | 실용적으로 무시. 기록함 |
| 테스트 DB가 로컬 컨테이너 | 운영 환경과 다를 수 있다 | 운영 중이 아니므로 수용 |

| --- | --- |
| 오랜 기간 후 재개 | 재측정하고 차이를 기록 |
| 환경이 바뀜 | 동상 |

## 4. 위험 대응에서 배운 것

### 4.1 두 번의 질문이 옳았다

| 상황 | 질문했다 | 질문 안 했다면 |
| --- | --- | --- |
| 미커밋 변경 | 사용자가 "커밋" 선택 | 임의 커밋 또는 무시 — 둘 다 위험 |
| SKIP 12건 | 사용자가 "구성" 선택 | 방치 → Postgres 경로 미검증 |

**판단이 갈리는 지점에서 물어본 것이 기준선을 완전하게 만들었다.**

### 4.2 자동으로 해도 되는 것과 물어야 하는 것

| 구분 | 예 | 기준 |
| --- | --- | --- |
| 자동 | venv 복구 | 결과 계약을 바꾸지 않는다 |
| 질문 | 미커밋 변경 커밋 | 다른 작업자의 의도, 기준선 확정 |
| 질문 | 외부 환경 구성 | 사용자 환경에 영향 |

`AGENTS.md`의 자동 재시도 범위가 이 판단의 기준이었다.
