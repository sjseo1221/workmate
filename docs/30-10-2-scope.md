# W10-2 — 목적과 범위

> [30-10-w10-react-agent.md](30-10-w10-react-agent.md) §2의 상세 문서.

## 1. 목적

`assistant_ask`의 **단발 분류 라우팅**을 **ReAct Agent 루프**로 바꾼다.

```
[현재]
LLM ①  Context 참조 해소       (_resolve_context_reference)
LLM ②  action + skill_id + arguments  ← 단 한 번의 결정
코드    allowlist 검증 → 확인 판정 → Skill 1개 실행
LLM ③  결과를 문장으로

[ReAct 이후]
LLM    생각 → 도구 호출 → 결과 관찰 → 생각 → 도구 호출 → … → 최종 답변
       (호출 횟수 가변, 도구 여러 개 연쇄 가능)
```

### 1.1 현재 구조의 실제 모습

[assistant_router.py](../workmate-agent/app/workflows/assistant_router.py)의 `route()`가 한 번의
LLM 호출로 세 값을 동시에 결정한다.

| 반환값 | 의미 |
| --- | --- |
| `action` | `answer`(바로 답변) 또는 `call_skill`(Skill 실행) |
| `skill_id` | 실행할 Skill 하나 |
| `arguments` | 그 Skill의 인자 (평평한 15필드 중 해당 항목) |

**한 번 정하면 되돌릴 수 없다.** 결과를 보고 "아 이게 아니었네"라고 판단하는 경로가 없다.

## 2. 무엇이 좋아지는가

| 현재의 한계 | ReAct가 해결하는 것 |
| --- | --- |
| **Skill 1개만 실행** | "지난주 회의 찾아서 그 액션아이템 승인해줘" 같은 다단계 요청 |
| 정보가 부족하면 되묻기만 | 도구로 먼저 조회한 뒤 판단 |
| **평평한 인자 Schema 15필드** | 도구별 개별 Schema ([30-10-5](30-10-5-design.md) §4) |
| 134줄 단일 프롬프트에 모든 규칙 | 도구별 설명으로 분산 |
| 결과를 보고 다시 판단 못 함 | 관찰 후 재계획 |

### 2.1 가장 확실한 이득 — 평평한 Schema 해소

`_ARGUMENTS_SCHEMA`가 15개 필드를 평평하게 갖고 전부 `required`다. OpenAI strict 모드의 제약이며,
그래서 코드가 `null`을 걸러낸다([assistant_router.py:691](../workmate-agent/app/workflows/assistant_router.py#L691)).

| | 현재 | ReAct |
| --- | --- | --- |
| Schema 수 | 1개(15필드 평평) | 10개(각 2~4필드) |
| `null` 필터링 | 필요 | 불필요 |
| 인자 오배치 | 가능 — `meeting_id`를 `manage_tasks`에 줄 수 있다 | **구조적으로 불가** |

**이것은 LLM 품질과 무관한 구조적 개선이다.** 다른 이득은 "LLM이 잘해 주면"이라는 조건이 붙지만 이건
아니다.

### 2.2 다단계 요청 — 지금은 왜 안 되는가

```
사용자: "지난주 회의 찾아서 그 액션아이템 승인해줘"

[현재]
route() → skill_id 하나를 골라야 한다
  search_meetings?   → 회의만 찾고 끝. 승인은 못 함
  review_action_items? → 어느 회의인지 모름

결과: 되묻기 ("어느 회의인가요?") 또는 절반만 수행
```

ReAct는 `search_meetings` → 결과 관찰 → `review_action_items`로 이어 갈 수 있다.

## 3. 무엇이 나빠지는가

| 항목 | 현재 | ReAct |
| --- | --- | --- |
| LLM 호출 횟수 | 최대 3회 고정 | **가변** (예산 상한 필요) |
| 응답 지연 | 예측 가능 | 가변 |
| 비용 | 예측 가능 | 가변. **도구 결과가 컨텍스트에 누적** |
| 재현성 | 높음(`temperature=0` 단발) | **낮음** — 같은 입력에 다른 경로 |
| 스냅샷 대조 | 성립 | **성립하기 어려움**([30-10-11](30-10-11-risks.md) §3) |
| 확인 시점 | 실행 전 1회 | 루프 중 여러 번 발생 가능 |
| 디버깅 | 로그 한 줄 | 루프 전체를 따라가야 함 |

### 3.1 비용이 선형으로 늘지 않는다

ReAct는 매 반복마다 **누적된 대화 전체**를 보낸다.

```
반복 1  입력: 시스템 + 사용자 질문
반복 2  입력: 시스템 + 질문 + 도구 호출 + 도구 결과①
반복 3  입력: 시스템 + 질문 + 호출① + 결과① + 호출② + 결과②
...
```

**도구 결과가 크면 폭주한다.** `search_meetings`가 회의 20건을 반환하면 그게 다음 호출부터 계속
따라간다. 예산 설계([30-10-5](30-10-5-design.md) §7)에 토큰 상한이 있는 이유다.

## 4. 범위

### 4.1 범위 내

| ID | 항목 | 관련 요구사항 |
| --- | --- | --- |
| S1 | `assistant_ask`를 ReAct Agent Subgraph로 재작성 | W10-R1 |
| S2 | Skill 10개를 도구로 래핑, 도구별 Schema 정의 | W10-R2 |
| S3 | 134줄 카탈로그 규칙을 도구 설명·도구 동작으로 이전 | W10-R4 |
| S4 | 파괴적 도구 호출 전 `interrupt` | W10-R7 |

| S9 | 스냅샷 `assistant_ask` 4건 재작성 | W10-R13 |

### 4.2 범위 외

| 항목 | 이유 |
| --- | --- |
| **나머지 10개 Skill 내부를 Agent로** | Skill 내부는 결정적 Workflow로 유지([30-10-5](30-10-5-design.md) §6) |
| 결정적 규칙을 LLM에 이관 | `AGENTS.md` 금지. **절대** |
| 도구 자동 발견·동적 등록 | 범위 밖. 도구 집합은 코드에 고정 |
| 멀티 에이전트(Supervisor·Swarm) | 범위 밖 |
| A2A 공개 경로의 다른 Skill을 ReAct로 | D7-1=A. `assistant_ask`만 |
| 도구 실행 병렬화 | 확인 게이트와 순서 보장이 얽힌다. 별건 |

### 4.3 범위를 좁게 잡는 이유

`assistant_ask` **하나만** 바꾼다. 나머지 10개 Skill은 진입점이 명확한 결정적 작업이다.

```
"이번 주 주간보고 써줘"  → weekly_report  (판단할 게 없다)
"오늘 브리핑"            → daily_briefing (동상)
```

**Agent가 필요한 곳은 "무엇을 해야 할지 모르는" 요청뿐이고, 그건 `assistant_ask`다.** 다른 Skill을
ReAct로 감싸면 비용과 불확실성만 늘고 얻는 게 없다.

## 5. 후속 백로그와의 관계

[W9-12](30-9-12-backlog.md)의 항목 중 W10과 겹치는 것이 있다.

| 백로그 | W10에서 |
| --- | --- |
| W9-B7 `astream` 스트리밍 | **함께 하는 편이 낫다** — 루프가 길어 진행 표시가 중요해진다 |
| W9-B8 LangSmith 등 트레이싱 | **함께 하는 편이 낫다** — 루프 추적이 어려워 가치가 올라간다 |
| W9-B3 `AUTH_REQUIRED` | 독립 |
| W9-B2 429 재시도 | 독립. 단 루프 중 429가 반복되면 체감이 커진다 |
| W9-B6 `message_id` 비대칭 | 독립 |

**ReAct는 관측의 필요성을 크게 높인다.** 단발 호출은 로그 한 줄로 충분하지만, 6단계 루프는 어디서
잘못됐는지 추적이 필요하다.

### 5.1 함께 할지는 W10 착수 시 판단한다

지금 묶지 않는다. W9-B8은 API Key가 필요해 별도 승인 대상이고([AGENTS.md]), 스트리밍은 UI SSE까지
얽힌다. **W10의 범위를 먼저 통제하고, 루프 디버깅이 실제로 어려운지 확인한 뒤 결정한다.**
