## W1-K1 — 정규화 불완전

**설명** 비결정 값을 놓쳐 스냅샷이 실행할 때마다 실패한다.

**놓치기 쉬운 값**

| 값 | 어디서 |
| --- | --- |
| `calculated_at` | `rank_priorities` — `datetime.now(timezone.utc)` |
| `text` 안의 타임스탬프 | 위 값이 JSON 문자열로도 들어간다 |
| `priority_snapshot_id` | `uuid4()` |
| 날짜 경계 | `as_of`를 주입하지 않으면 자정 넘어 결과가 달라진다 |
| `last_synced_at` | 동기화 상태 |
| 임시 디렉터리 경로 | Fixture 세팅 |

**영향** 간헐 실패하는 스냅샷은 신뢰를 잃고, 곧 "또 그거네" 하고 무시된다. 안전망이 있는데 아무도 안
보는 상태가 가장 나쁘다.

**완화**
- W1-V2에서 2회 연속 실행 + 실행 순서 변경 + 시간 간격 두고 재실행
- 주입 우선 원칙([30-1-5](30-1-5-design.md) §4.1) — `as_of`·`timezone`을 케이스에 명시
- 실패 시 원인 필드를 추가하되 **이유를 기록**

**대응 계획** 3회 보완으로도 안 되면 해당 Skill을 "스냅샷 불가"로 기록하고 대체 검증을 정한다
([30-1-9](30-1-9-exit-criteria.md) §4).

## W1-K2 — 과도한 정규화

**설명** 실패를 없애려고 정규화를 늘리다가, 정작 검증해야 할 값까지 비교 대상에서 빠진다.

**왜 발생하기 쉬운가** 정규화는 실패를 즉시 없애준다. "일단 빼고 나중에 보자"가 쌓이면 스냅샷이
껍데기가 된다. 극단적으로는 `expected`가 전부 `<normalized>`인 상태도 통과한다.

**영향** W1-K1보다 나쁘다. 간헐 실패는 눈에 띄지만, 과도한 정규화는 **조용히 통과**한다.

**완화**
- **금지 목록**([30-1-5](30-1-5-design.md) §4.2) — 점수·순위·`source_refs`·`warnings.code`·
  `artifact_name`·근거 문장은 정규화 금지
- W1-V8-3에서 금지 목록 침범을 코드로 검사
- `normalized_fields`에 **이유 필수**(W1-D2) — 쓰기 귀찮게 만들어 남용을 억제
- 필드 제외 금지, 치환만 허용(W1-D5) — 존재 여부와 형식은 항상 검증

**대응 계획** 금지 목록의 값이 비결정적이면 그것 자체가 문제다. 왜 결정적이지 않은지 먼저 조사한다.

## W1-K3 — 케이스 대표성 부족

**설명** 케이스가 실제 사용 경로를 대표하지 못해, 커버되지 않은 경로에서 회귀가 발생한다.

**영향** W3에서 스냅샷 전건 PASS인데 실제로는 동작이 바뀌어 있다.

**완화**
- W1-T1에서 **기존 테스트를 전수 조사**해 시나리오를 뽑는다. 즉흥 작성 금지
- 기존 테스트는 실사용 중 발견된 문제를 담고 있어 대표성이 높다 — 주석의 날짜·배경이 단서
- `origin` 기록(W1-D1)으로 출처를 추적 가능하게
- 부류 커버리지 검증(W1-V4)

**잔여 위험** 기존 테스트가 다루지 않는 경로는 여전히 비어 있다. 이는 W3의 단위 테스트가 보완한다.

---

## W1-K4 — `assistant_ask` 연쇄 의존

**설명** `assistant_ask`는 내부에서 다른 Skill을 호출하므로, 하위 Skill의 스냅샷이 불안정하면 연쇄로
깨진다.

**영향** 하나의 원인으로 여러 케이스가 동시에 실패해 원인 추적이 어려워진다.

**완화**
- W1-T8을 **마지막에** 배치(하위 Skill 케이스가 안정된 뒤)
- `assistant_ask` 케이스에서 하위 Skill 호출을 Fake로 고정할지, 실제 호출할지 결정
  - 실제 호출: 통합 검증이 되지만 연쇄 취약
  - Fake: 격리되지만 Meta Skill의 본질(다른 Skill 호출)을 검증하지 못함
  - **권장:** `routes_to_skill` 케이스는 실제 호출, 나머지는 필요에 따라

**대응 계획** 연쇄 실패 시 하위 Skill 케이스부터 확인한다.

---

## W1-K5 — 기록 모드 오작동

**설명** 기록 모드가 의도치 않게 실행돼 `expected`가 현재(잘못된) 결과로 덮어써진다.

**왜 치명적인가** **회귀를 정답으로 고정**한다. 이후 모든 대조가 잘못된 기준으로 통과한다. 게다가
조용히 일어나면 알아차리기 어렵다.

**완화**
- 환경변수 가드 `WORKMATE_SNAPSHOT_RECORD=1`(W1-R9)
- 일반 unittest 실행에서는 절대 기록되지 않음(W1-V9-2에서 mtime 확인)
- **기대값 변경은 반드시 커밋 diff로 검토** — 케이스 파일이 변경된 커밋은 이유가 명시돼야 한다

**대응 계획** 덮어써진 것이 의심되면 git 이력에서 이전 버전을 확인한다. 이것이 스냅샷을 저장소에
커밋하는 또 하나의 이유다.

---

## W1-K6 — 측정을 위한 운영 코드 수정

**설명** Fake 주입이 어려워 `app/`에 테스트용 훅을 추가하고 싶어진다.

**왜 발생하기 쉬운가** 일부 Skill은 모듈 수준에서 Provider를 만든다. 주입 지점이 없으면 `patch`가
지저분해진다.

**영향** W1의 전제가 깨진다. "무엇의 스냅샷인가"가 불분명해지고, 추가한 훅이 W3 이후에도 남는다.

**완화**
- 대부분의 Workflow 빌더에 **이미 주입 파라미터가 있다**([30-1-5](30-1-5-design.md) §5.1) —
  `provider_factory`·`repositories`·`analyzer`·`embedding_provider`·`answer_service`
- 없으면 `patch`로 처리
- W1-V6(`git diff --stat app/`)으로 강제

**대응 계획** 주입도 patch도 불가한 Skill이 있으면 그 사실을 기록하고, 해당 Skill을 "스냅샷 불가"로
처리한다. 운영 코드를 고치지 않는다.

---

## W1-K7 — Fixture에 Secret 혼입

**설명** 실제 토큰·이메일 주소·회의 내용이 Fixture에 들어가 저장소에 커밋된다.

**영향** `AGENTS.md` 금지 사항 위반. 저장소 이력에 남아 제거가 어렵다.

**완화**
- 기존 Fixture의 가짜 값 사용 — [`work_domain.py`](../workmate-agent/tests/fixtures/work_domain.py)의
  `OWNER_USER_ID`(UUID 형태) 등
- W1-V7 패턴 검사(`sk-`, `Bearer `, `ya29.`, `AIza`, Presigned URL 형태)
- 커밋 전 검사

**대응 계획** 혼입 발견 시 커밋 전이면 수정, 커밋 후면 이력 처리를 사용자에게 보고한다.

---

## W1-K8 — 하네스의 전역 상태 오염

**설명** 하네스가 환경변수나 임시 파일을 정리하지 않아 다른 테스트에 영향을 준다.

**징후** W1-V5(기존 440건)가 실패한다. W1은 `app/`을 안 고치므로 다른 이유가 없다.

**구체적 위험 지점**

| 지점 | 문제 |
| --- | --- |
| `os.environ["WORKMATE_TASK_DB_PATH"]` | 기존 테스트도 같은 변수를 쓴다 |
| 임시 디렉터리 | 정리 누락 시 누적 |
| 모듈 수준 캐시 | Repository 싱글턴 등 |

**완화**
- 케이스마다 격리(W1-D4)와 정리
- 환경변수는 컨텍스트 매니저로 복원
- W1-V5로 검출

---

## W1-K9 — W1을 건너뛰려는 압력

**설명** "일단 W2부터 하고 스냅샷은 나중에" 또는 "케이스 몇 개만 만들고 넘어가자"는 판단.

**왜 위험한가** **W1은 되돌릴 수 없는 시한이 있다.** W7에서 `app/workflows/`가 삭제되면 스냅샷을
만들 수 없다. 그때 "W1을 제대로 할 걸" 해도 방법이 없다.

**영향** 전환 전체의 회귀 감지 능력 상실. W9에서 "설명 불가 차이 0"을 증명할 수 없어 완료 판정이
불가능해진다.

**완화**
- 계획서 §1-4에 "W1 없이 W3을 시작하지 않는다"를 원칙으로 명시
- [W2-E1](30-2-3-entry-criteria.md)·[W3-E1](30-3-3-entry-criteria.md)에 선행 조건으로 고정
- 이 문서(§2 W1-K9)에 위험으로 기록

**대응 계획** 시간 압박이 있으면 케이스 수를 줄이더라도 **하네스와 Skill 11개 각 1건**은 확보한다.
하네스가 있으면 나중에 케이스를 추가할 수 있지만(W7 전까지), 하네스가 없으면 아무것도 못 한다.
