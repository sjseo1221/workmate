## 2. 요구사항 상세

### W10-R1 — 다단계 실행

**무엇** 한 요청에서 도구를 순차로 여러 번 호출할 수 있다.

```
"지난주 회의 찾아서 액션아이템 승인해줘"
  → search_meetings(relative="last_week")
  → (결과 관찰: 회의 1건)
  → review_action_items(meeting_id=..., decisions=[...])
  → 최종 답변
```

**왜** 현재는 Skill 1개만 실행하고 끝난다. 다단계 요청은 되묻기로 처리되거나 절반만 수행된다.

**경계** 도구 호출은 **순차**다. 병렬 호출은 범위 밖 — 확인 게이트와 순서 보장이 얽힌다.

---

### W10-R2 — 도구별 Schema

**무엇** 도구 10개가 각자의 Schema를 갖는다. 현재의 평평한 15필드 단일 Schema를 대체한다.

| 도구 | 인자 |
| --- | --- |
| `weekly_report` | `relative` 또는 `week_of` |
| `manage_tasks` | `action`, `title`, `due_at`, `task_id` |
| `search_meetings` | `query`, `date_from`, `date_to` |
| `get_meeting_analysis` | `meeting_id` |
| … | (도구별) |

**왜** 인자 오배치가 구조적으로 불가능해진다. `null` 필터링도 필요 없다.

**경계** 도구 집합은 **코드에 고정**한다. 자동 발견·동적 등록은 범위 밖.

---

### W10-R3 — 권한 인자는 LLM이 채우지 않는다

**무엇** `user_id`·`task_id`·`thread_id`를 도구 Schema에서 제외한다. 도구 래퍼가 State에서 읽어
주입한다.

**왜** **보안 요구사항이다.** LLM이 `user_id`를 채울 수 있으면 프롬프트 주입으로 남의 데이터를 조회할
수 있다. `AGENTS.md`의 "모든 조회에 요청된 `user_id` 조건을 적용한다"가 깨진다.

**검증** W10-V6 — 도구 Schema에 `user_id`가 없음을 코드로 단정하고, 주입 경로를 테스트한다.

---

### W10-R4 — 카탈로그 규칙 전수 보존 (최우선)

**무엇** `_SKILL_CATALOG` 134줄의 모든 규칙이 아래 넷 중 하나로 이전되고, 각각 회귀 케이스를 갖는다.

| 이전처 | 예 |
| --- | --- |
| 도구 `description` | "이미 분석된 회의에는 쓰지 마라" |
| Schema 필드 `description` | "상대 표현은 `relative`로 전달" |
| **코드** (도구 내부 기본값) | `week_of` 계산 |
| Agent 시스템 프롬프트 | "특정 안 되면 목록으로 되묻기" |

**왜** 134줄은 실사용 피드백으로 한 줄씩 쌓인 규칙이다. 흩어지면서 조용히 사라진다
([30-10-11](30-10-11-risks.md) W10-K1).

**판정** 규칙표 전항 PASS가 아니면 **W10을 완료하지 않는다.**

---

### W10-R5 — 계산은 코드로

**무엇** LLM은 `relative="last_week"` 같은 **의도**만 전달하고, 날짜는 도구 내부 코드가 계산한다.

| 현재 | W10 |
| --- | --- |
| 프롬프트에 "오늘-7일" 규칙 → LLM이 `week_of="2026-09-15"` 계산 | LLM은 `relative="last_week"`, 도구가 계산 |

**왜** 05번 문서 §1의 "날짜 범위 계산은 코드"와 일치한다. 프롬프트로 계산을 지시하면 "지난 주에 7일을
두 번 빼는" 실사용 오류가 재발한다.

**설계** [30-10-5](30-10-5-design.md) W10-D1.

---

### W10-R6 — 결정적 규칙 불변

**무엇** 아래는 W10 전후로 **한 글자도 달라지지 않는다.**

| 항목 | 소유 |
| --- | --- |
| 우선순위 점수·순위·`score_breakdown` | `app/domain/priority.py` |
| 근거 ID(`source_refs`) | Domain·Repository |
| 날짜 경계 계산 | 도구 내부 코드 |
| `user_id` 범위 | Repository |
| 중복 제거·상태 전이 | 코드 |
| 결과 Schema 검증 | `validate_contract` 노드 |

**Agent는 "어떤 도구를 부를지"만 정하고 도구가 반환한 값을 바꾸지 않는다.**

**왜** `AGENTS.md` — "우선순위 점수는 결정적으로 계산한다", "LLM이 Task 순위와 근거 ID를 생성하거나
변경하지 않도록 한다".

**검증** W10-V5. FAIL이면 **즉시 중단**이다(규칙 위반).

---

### W10-R7 — 확인 게이트 우회 불가

**무엇** 확인 대상 4종은 도구 호출 직전 `interrupt`를 거친다.

```python
TOOL_REQUIRES_CONFIRMATION = {
    "analyze_meeting": lambda args: True,
    "review_action_items": lambda args: any(d.get("decision") == "reject" for d in args.get("decisions", [])),
    "review_proposal": lambda args: args.get("decision") == "ignore",
    "manage_tasks": lambda args: args.get("action") == "delete",
}
```

**왜 구조로 강제하는가** 프롬프트로 "확인받아라"라고 지시하면 LLM이 건너뛸 수 있다. **Graph의 분기로
두면 건너뛸 경로가 없다.**

**경계** 확인 대상은 **W6-R10과 동일한 4종**이다. W10에서 늘리거나 줄이지 않는다.

---

### W10-R8 — 거부 후 재계획

**무엇** 사용자가 거부하면 Agent에게 "거부됨"을 전달하고 루프를 계속한다.

```
interrupt → 거부 → record_rejection → agent
                                       └ 다른 방법 시도 또는 사용자에게 설명
```

**왜 W6과 다른가** W6은 거부 시 Task를 종료한다. ReAct에서는 "그건 하지 마"가 대화의 일부이므로 Agent가
대응할 수 있어야 한다.

**경계** 거부된 도구를 **같은 인자로 다시 호출하면 안 된다.** 예산의 "같은 도구 연속 호출" 상한이
이 경우도 막는다.

---

### W10-R9 — 루프 예산

**무엇** 4종 예산을 두고 초과 시 조용히 끊지 않는다.

| 예산 | 값(D7-5) |
| --- | --- |
| 반복 횟수 | 6 |
| 누적 토큰 | 모델 컨텍스트의 70% |
| 경과 시간 | 60초(비동기 경로는 더 길게) |
| 같은 도구 연속 호출 | 2회 |

**초과 시** `warnings`에 사유를 남기고 **부분 결과를 반환**한다. `AGENTS.md`의 "외부 Provider 장애 시
정의된 부분 결과와 `warnings`를 반환한다"와 같은 원칙이다.

---

### W10-R10 — 공개 계약

**무엇** 한 요청에서 실행한 도구 이력을 응답에 표현한다.

```json
// 현재
{"reply": "...", "executed_skill_id": "manage_tasks", "pending_action": null}

// W10 (D7-6=A)
{"reply": "...", "executed_skill_ids": ["search_meetings", "review_action_items"], ...}
```

**왜** 단수로는 다단계 실행을 표현할 수 없다.

**주의** **W6에서 이미 한 번 바꾼 계약을 또 바꾸는 것**이다. UI·어댑터·02번 문서가 다시 영향받는다.
승인 절차는 [30-10-10](30-10-10-approval.md) §2.

---

### W10-R11 — 05번 문서 개정

**무엇** §1의 LLM·코드 책임 표에 "도구 선택과 호출 순서(assistant_ask 한정)"를 추가하고, 유지되는
코드 경계를 명시한다.

**왜** 현재 문서가 LLM을 텍스트 생성으로 한정하고 있어, 개정 없이 구현하면 **설계 기준과 구현이
충돌한다.** W9가 없애려던 문제와 같은 종류다.

**착수 전 승인 대상이다**(W10-E4).

---

### W10-R12 — 측정값 기록

**무엇** 아래를 증빙에 남긴다.

| 항목 | 측정 |
| --- | --- |
| 선택 안정성 | 같은 입력 10회 → 같은 도구 시퀀스 비율 |
| LLM 호출 횟수 | 케이스별 평균·최대 |
| 토큰 사용량 | 현재 대비 배수 |
| 응답 지연 | 현재 대비 |

**왜** ReAct의 대가를 수치로 남겨야 수용 판단을 할 수 있다. "느려진 것 같다"로는 판단할 수 없다.

---

### W10-R13 — 스냅샷 재작성 범위

**무엇** W1 스냅샷 27건 중 `assistant_ask` 4건만 재작성한다. **나머지 23건은 그대로 PASS해야 한다.**

**왜** W10의 범위가 `assistant_ask`뿐임을 기계적으로 증명하는 장치다. 23건 중 하나라도 깨지면 범위가
새어 나간 것이다.

## 3. 요구사항 간 충돌

### 3.1 R1(다단계)과 R9(예산)

다단계를 허용할수록 예산을 넘기 쉽다. **예산이 우선한다** — 초과 시 부분 결과.

### 3.2 R4(규칙 보존)와 R2(Schema 분산)

규칙을 도구별로 흩으면 보존 확인이 어려워진다. **R4가 우선한다** — 규칙표가 흩어진 위치를 추적한다.

### 3.3 R5(코드 계산)와 R1(LLM 판단)

"지난주"를 코드가 계산하면 LLM이 특이한 기간 지정("8월 첫째 주부터 셋째 주까지")을 표현하기 어렵다.

**해법** `relative`와 `date_from`/`date_to`를 **둘 다** 받는다. 상대 표현은 `relative`로, 명시적 범위는
직접 받는다. 단 `relative`가 있으면 코드 계산이 우선한다.
