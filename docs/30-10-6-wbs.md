### W10-T2 — 카탈로그 규칙 목록화 (성패를 가르는 작업)

**내용** 134줄 프롬프트의 규칙을 **하나씩 목록으로 만들고 각각에 회귀 테스트를 붙인다.**

**규칙표 형식**

| # | 규칙 | 출처 | 이전처 | 회귀 케이스 | 기대 |
| --- | --- | --- | --- | --- | --- |
| 1 | `week_of` 기본값은 오늘-7일 | 2026-08-17 | **코드**(W10-D1) | "주간보고" | `relative="this_week"` → 도구가 계산 |
| 2 | "지난 주"에 7일 두 번 빼지 않기 | 실사용 오류 | **코드** | "지난주 보고" | 오늘-7일. 오늘-14일 아님 |
| 3 | `[분석 완료]` 회의는 `get_meeting_analysis` | 비용 | 도구 description | 분석된 회의 + "분석해줘" | `get_meeting_analysis` 호출 |
| 4 | 회의 특정 안 되면 목록으로 되묻기 | 오분석 방지 | 시스템 프롬프트 | 후보 2개 상황 | 도구 호출 없이 되묻기 |
| 5 | `call_skill`일 때도 `reply` 채우기 | UX | 계약 설계 | 확인 대상 요청 | `reply` 비어 있지 않음 |
| … | (전수) | | | | |

**절차**

```
1. _SKILL_CATALOG를 줄 단위로 읽는다
2. 각 줄을 분류
   ├ 규칙성 문장   → 표에 추가, 이전처 지정
   └ 설명·예시     → "규칙 아님"으로 기록  ← 판단을 남긴다
3. 이전처가 "코드"인 규칙은 도구 기본값 설계를 함께 적는다
4. 각 규칙에 회귀 케이스 작성 (입력 → 기대 도구·인자)
5. 16번 문서(프롬프트 원문)와 대조해 누락 확인
```

**왜 이 작업이 성패를 가르나** 이 목록 없이 구현하면 무엇이 빠졌는지 알 수 없다. ReAct는 대부분 잘
동작할 것이고, 빠진 규칙은 **사용자 신고로 발견된다.**

**난이도** 중간 / **비중 20%** / **W10에서 가장 중요**

### W10-T3 — 도구 Schema 정의

**내용** Skill 10개의 도구 Schema를 작성한다.

**체크리스트**

```
[ ] 각 도구가 실제로 쓰는 인자만 포함
[ ] user_id·task_id·thread_id 제외          ← W10-D5
[ ] 필드 description에 "의도 표현 방법" 기재
[ ] 계산 규칙은 넣지 않는다 (코드로 — W10-D1)
[ ] 규칙표의 "Schema 필드 description" 항목 전부 반영
```

**산출물 예**

```python
class WeeklyReportArgs(BaseModel):
    """주간 업무보고 인자.

    relative가 주어지면 코드가 날짜를 계산하며 week_of는 무시한다.
    """
    relative: Literal["this_week", "last_week"] | None = None
    week_of: str | None = None
```

**난이도** 중간 / **비중 10%**

### W10-T4 — 계산 규칙을 코드로 이전

**내용** 규칙표에서 이전처가 "코드"인 항목을 도구 내부 기본값 계산으로 구현한다.

**대상(예상)**

| 규칙 | 구현 |
| --- | --- |
| `week_of` 상대 표현 계산 | `relative` → 날짜 변환 함수 |
| "지난 주" 중복 차감 방지 | 위 함수 하나로 통일 → 구조적으로 불가 |
| 기본 날짜 범위 | 도구별 기본값 |

**왜 따로 두나** W10-T3(Schema)과 섞으면 "Schema에 설명을 썼으니 됐다"로 넘어가기 쉽다. **계산이
코드로 내려왔는지를 별도 작업으로 확인한다.**

**난이도** 중간 / **비중 10%**

### W10-T5 — ReAct Graph 구현

**내용** [30-10-5](30-10-5-design.md) §1의 Graph를 구현한다.

**구성**

```
[ ] load_context 노드            (기존 Context 조회 재사용)
[ ] agent 노드                   (bind_tools, temperature=0)
[ ] tool_node                    (Skill Subgraph 래핑)
[ ] route_after_agent            (결정적 판정 함수)
[ ] final_answer 노드
[ ] State 확장 (messages·tool_calls_made·iteration)
```

**주의** `agent` 노드가 **유일하게 라우팅 판단을 하는 지점**이다. 다른 노드에 판단을 흘리지 않는다.

**난이도** 높음 / **비중 15%**

### W10-T6 — 확인 게이트 + interrupt

**내용** `confirm_required?` 게이트와 `interrupt`, 거부 후 재계획 경로를 구현한다.

```
[ ] TOOL_REQUIRES_CONFIRMATION 4종
[ ] confirm_required? 조건 분기   ← Graph 구조로 (W10-D2)
[ ] interrupt(pending_tool_call)
[ ] record_rejection → agent 복귀 (W10-D3)
[ ] 같은 도구 재호출 차단 (무한 확인 루프 방지)
```

**W6과의 관계** W6의 `interrupt` 구현을 재사용하되 **위치가 다르다** — W6은 Skill 실행 전 1회,
W10은 루프 안에서 여러 번.

**난이도** 높음 / **비중 15%**

## 3. 작업 의존 그래프

```
W10-T1 (결정·개정안 승인)   ← 사용자
   ↓
W10-T2 (규칙 목록화)         ← 성패를 가른다
   ↓
W10-T3 (도구 Schema)
   ├→ W10-T4 (계산 코드 이전)
   └→ W10-T5 (ReAct Graph)
         ├→ W10-T6 (확인 게이트)
         │     └→ W10-T8 (계약·UI)
         └→ W10-T7 (예산)
                ↓
         W10-T9 (회귀 검증)  ← T4·T6·T7 전부 선행
                ↓
         W10-T10 (측정) → W10-T11 (증빙·승인)
```

**W10-T4와 W10-T5는 병렬 가능하다.** T6·T7도 서로 독립이다.
