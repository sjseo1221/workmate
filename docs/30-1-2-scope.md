# W1-2 — 목적과 범위

> [30-1-w1-contract-snapshot.md](30-1-w1-contract-snapshot.md) §2의 상세 문서.

## 1. 목적

전환 후 결과가 전환 전과 같은지 판정할 **기계 판독 가능한 기준(oracle)** 을 만든다.

### 1.1 왜 기존 테스트로는 안 되는가

현재 440개 테스트는 **부분 단언(partial assertion)** 만 한다. 대표 사례를 보자.

[test_priority_workflow.py:41-44](../workmate-agent/tests/test_priority_workflow.py#L41-L44)가
`rank_priorities`에 대해 확인하는 것:

```python
self.assertEqual([item["task_id"] for item in data["data"]["priorities"]], ["a"])
self.assertEqual(data["data"]["source_refs"], ["a"])
self.assertEqual(data["data"]["changes"][0]["change_type"], "entered")
```

확인되지 **않는** 것:

| 필드 | 값의 예 | 바뀌어도 통과 |
| --- | --- | --- |
| `priorities[].score` | 8.5 | ✓ |
| `priorities[].score_breakdown` | 5개 하위 필드 | ✓ |
| `priorities[].reasons` | 근거 문자열 배열 | ✓ |
| `calculated_at` | ISO-8601 문자열 | ✓ |
| `artifact_name`·`artifact_description` | | ✓ |
| `markdown` | 렌더링 결과 전체 | ✓ |
| `warnings` | 빈 배열 | ✓ |

즉 새 Graph가 점수를 다르게 계산하거나 근거 문장을 바꾸거나 Artifact 설명을 고쳐도 **이 테스트는
그대로 통과한다.**

### 1.2 D1=B가 상황을 악화시켰다

초판 계획은 `test_contract.py`(399줄)를 "기대값을 한 줄도 안 고치고 통과시키는" 회귀 감시선으로 쓸
생각이었다. D1=B(공개 계약까지 개편)로 그 계획이 성립하지 않는다.

| | 초판 계획 | D1=B 확정 후 |
| --- | --- | --- |
| `test_contract.py` | 기대값 무변경 감시선 | resume 프로토콜 기준으로 재작성 대상 |
| 회귀 감지 수단 | 기존 테스트 + 스냅샷 | **스냅샷뿐** |

게다가 D2=A와 무관하게, 구현과 테스트를 **동시에** 재작성하므로 새 테스트는 새 구현에 맞춰 작성된다.
둘 다 틀려도 초록색이다.

### 1.3 스냅샷이 메우는 빈틈

```
기존 테스트:  "중요한 몇 개 필드가 맞는가"     → 설계 의도 검증
계약 스냅샷:  "결과 전체가 예전과 같은가"      → 회귀 검출
```

둘은 대체 관계가 아니라 보완 관계다. W3에서 기존 테스트를 재작성하더라도 스냅샷은 그대로 남는다.

| ID | 항목 | 산출물 |

| S2 | 비결정 값 정규화 | `_normalize.py` |

## 3. 범위 외 (Out of scope)

| 항목 | 이유 |
| --- | --- |
| `app/` 운영 코드 수정 | W1은 **읽기 전용 측정**이다 |
| 기존 테스트 수정·삭제 | W3의 일이고, W1 시점에는 비교 기준이다 |
| 실제 외부 Provider 호출 | 비용·결정성 문제. Fake로 고정 |
| 성능 측정 | W8의 관측 범위 |
| 발견한 버그 수정 | 스냅샷은 **현재 동작을 기록**한다. 버그도 기록한다(§4) |
| 커버리지 100% | 대표 시나리오면 충분(§5) |

### 3.1 "버그도 기록한다"

스냅샷을 만들다 보면 현재 동작이 이상해 보이는 지점이 나올 수 있다. W1에서는 **고치지 않고 그대로
기록**한다.

| 이유 | 설명 |
| --- | --- |
| 비교 기준의 무결성 | 고치면 "전환 전"이 무엇인지 흔들린다 |
| 원인 분리 | 전환 후 값이 다를 때 "전환 때문인가 버그 수정 때문인가"를 구분할 수 없게 된다 |
| 범위 | 버그 수정은 별도 백로그다 |

발견한 이상은 증빙에 "관찰된 현재 동작"으로 기록하고, 필요하면 후속 백로그로 넘긴다.

## 4. 스냅샷이 보장하지 않는 것

이것을 명시하지 않으면 스냅샷을 과신하게 된다.

| 보장하지 않음 | 이유 | 보완 |
| --- | --- | --- |
| LLM 응답 품질 변화 | Fake 고정 응답 기준 | [W2-V6](30-2-7-verification.md) 구조화 출력 동등성 |
| 프롬프트 변경의 영향 | 동상 | 별도 평가(범위 밖) |
| 성능 변화 | 측정하지 않음 | W8 노드 로그 |
| **숨은 부작용** | 응답에 드러나지 않음 | **[W3-V11](30-3-7-verification.md)** |
| 케이스에 없는 입력 조합 | 대표 시나리오만 | 기존 테스트 + W3 단위 테스트 |
| 동시성 문제 | 단일 실행 기준 | 범위 밖 |

**숨은 부작용이 특히 중요하다.** [30-3-5](30-3-5-design.md) §3에서 발견한 대로 `daily_briefing`은
`rank_priorities`를 호출해 우선순위 Snapshot을 저장하는데, 이 동작은 응답에 나타나지 않아 스냅샷으로
잡히지 않는다. W3에 전용 검증(W3-V11)이 있는 이유다.

## 5. 커버리지 방침

### 5.1 목표

| 기준 | 목표 |
| --- | --- |
| Skill | 11개 전부, 각 1건 이상 |
| 시나리오 부류 | 정상 / 부분 실패 / 입력 오류 — 전체에서 각 1건 이상 |
| 총 케이스 | 25~30건 |

### 5.2 완전 커버리지를 추구하지 않는 이유

모든 입력 조합을 스냅샷으로 덮으면 케이스가 수백 개가 되고, W3에서 하나를 고칠 때마다 수십 개가
깨진다. 스냅샷은 **회귀 감지 그물**이지 명세가 아니다.

대신 **기존 테스트가 이미 다루는 시나리오를 재활용**한다(W1-T1). 기존 테스트는 실사용 중 발견된
문제들을 담고 있어 대표성이 높다.

### 5.3 우선순위

케이스를 고를 때 이 순서로 가치를 매긴다.

1. **실사용 중 발견된 문제의 시나리오** — 주석에 날짜와 배경이 있는 것
2. 부분 실패 경로 — Provider 장애 시 동작
3. 정상 경로 — 가장 흔한 입력
4. 입력 오류 — `ValueError` 경로
5. 경계 조건 — 빈 결과, 단일 항목

## 6. 범위 변경 절차

| 상황 | 처리 |
| --- | --- |
| 케이스 추가 | 구현자 판단. 많을수록 좋지만 유지 비용을 고려 |
| 정규화 범위 확대 | **이유를 기록**하고 진행. 과도하면 검증력이 사라진다([30-1-10](30-1-10-risks.md) W1-K2) |
| 스냅샷 불가 Skill 발생 | [30-1-11](30-1-11-rollback.md) §3의 중단 기준 |
| `app/` 수정이 필요해 보임 | **범위 이탈.** 측정을 위해 운영 코드를 고치지 않는다 |
