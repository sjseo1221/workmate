# W8-10 — 위험 등록부

> [30-8-w8-retry-observability.md](30-8-w8-retry-observability.md) §10의 상세 문서.

확률·영향은 상/중/하 3단계. **노출도** = 확률 × 영향.

## W8-K1 — 이중 재시도

**설명** `ChatOpenAI`의 기본 재시도를 못 껐거나, Provider Client에 재시도가 남아 있어 곱해진다.

**영향** 정책은 3회인데 실제로는 9회, 12회가 된다. 장애 시 지연이 증폭되고 Provider rate limit에
걸린다.

**왜 발생하기 쉬운가** 설정값만 보고 "껐다"고 판단하기 쉽다. `httpx`·OpenAI SDK 계층에 별도 재시도가
있을 수 있다.

**완화**
- W2에서 `max_retries=0` 설정(W2-V7-10에서 이미 계측)
- **W8-V3-1에서 실제 HTTP 호출 횟수 계측** — 설정 확인이 아니라 호출 계측이 유일한 검증
- W8-T1에서 Provider Client 재시도 조사
- W8-V3-5에서 라이브러리 설정 재확인

**대응 계획** 라이브러리에서 끌 수 없으면 커스텀 HTTP 클라이언트를 주입해 끈다.

---

## W8-K2 — 부작용 노드 재시도

**설명** 외부 상태를 바꾸는 노드에 `RetryPolicy`를 붙인다.

**결과**

| 노드 | 중복 실행 시 |
| --- | --- |
| `manage_tasks.create` | **Task가 3개 생성** |
| `manage_tasks.delete` | 이미 없는 Task 삭제 시도(오류 가능) |
| `review_proposal` | **제안 중복 처리, Task 중복 생성** |
| `review_action_items` | **승인 중복 처리** |
| `rank_priorities.save_snapshot` | Snapshot 중복 |
| `analyze_meeting.save_*` | 분석·transcript 중복 |

**왜 발생하기 쉬운가** "모든 노드에 재시도를 붙이면 안정적이겠지"가 자연스러운 생각이다. 특히 일괄
적용 코드를 쓰면 전부 붙는다.

**완화**
- **W8-T2 적용표를 구현보다 먼저** 만든다
- 부작용 노드를 "없음(제외)"로 명시하고 **이유를 주석에**(W8-D4)
- **W8-V7-3에서 실제로 오류를 주입해 Task 수를 확인**
- 일괄 적용 코드를 쓰지 않는다 — 노드별로 명시

**대응 계획** 발견 즉시 제거. 이미 중복 데이터가 생겼으면 테스트 DB이므로 초기화한다.

## W8-K3 — 오류 분류 유실

**설명** 내부 재시도 루프를 제거하면서 그 안의 오류 분류 로직을 잃는다.

**현재 루프의 구조**

```python
for attempt in range(_CHAT_COMPLETION_MAX_ATTEMPTS):
    try:
        ...
    except error.HTTPError as exc:      # ← 이 분류가 핵심
        last_exc = exc
        break                            # 재시도 안 함
    except (error.URLError, TimeoutError, json.JSONDecodeError) as exc:
        last_exc = exc
        if attempt + 1 < _CHAT_COMPLETION_MAX_ATTEMPTS:
            continue                     # 재시도
```

루프를 지우면 `except` 구조도 함께 사라진다. **분류 로직을 `is_network_error()`로 옮겨야 한다.**

**영향** 전부 재시도하거나 전부 재시도 안 하게 된다. W8-R1 위반.

**완화**
- W8-T4에서 루프를 지우기 전에 분류 로직을 먼저 `is_network_error()`로 옮긴다
- W8-V1·V2에서 각 오류 유형별로 검증
- W2에서 이미 `is_network_error()`를 정의했으므로 참조

---

## W8-K4 — 부분 실패의 전체 실패 승격

**설명** 재시도 소진 후 예외가 전파돼 보조 소스 실패가 전체 실패가 된다.

**예** `daily_briefing`의 Gmail 조회에 재시도를 붙였는데, 3회 소진 후 예외가 그대로 올라가 Workflow
전체가 실패한다. 원래는 경고만 남기고 진행해야 한다.

**완화**
- [30-3-5](30-3-5-design.md) §7의 실패 파급 규칙표를 W8-T5에서 검증
- **W8-V4에서 8케이스 확인**
- 보조 소스 노드는 재시도 후에도 예외를 잡아 `warnings`로 변환

**주의** 재시도와 실패 파급은 순서가 있다.

```
Provider 호출 실패 → RetryPolicy 재시도 → 소진 → 실패 파급 규칙
```

재시도가 파급 규칙을 건너뛰게 하면 안 된다.

---

## W8-K5 — 로그 민감정보 유출

**설명** 노드 실행 로그에 메일 본문·회의 녹취·Token이 들어간다.

**왜 발생하기 쉬운가** 디버깅을 쉽게 하려고 State를 통째로 로그에 남기고 싶어진다.

```python
logger.info("node=%s state=%s", node, state)   # ← 위험
```

State에는 `source_data`(메일·일정 내용)가 들어 있다.

**영향** `AGENTS.md` 금지 사항 위반. 로그가 저장·전송되면 유출 경로가 된다.

**완화**
- 로그 항목을 **명시적으로 나열**([30-8-5](30-8-5-design.md) §7.1). State 통째로 남기지 않는다
- **W8-V8 전수 검사** — 테스트 실행 중 로그를 캡처해 패턴 검사
- `user_id`만 예외(OIDC subject, 장애 조사에 필요)

## W8-K6 — 정책 통일 유혹

**설명** 두 정책이 공존하는 것이 이상해 보여 하나로 합친다.

**왜 발생하기 쉬운가** 코드 리뷰에서 "왜 여기만 2회지?"라는 질문이 나온다. 통일이 깔끔해 보인다.

**영향**

| 통일 방향 | 결과 |
| --- | --- |
| 네트워크만 | `weekly_report`가 429·5xx에서 즉시 실패 → 부분 결과 빈도 증가 |
| Provider 오류 포함 | `assistant_router`가 5xx를 3회 재시도 → **2026-08-19 회귀** |

둘 다 W1 스냅샷의 부분 실패 케이스를 깨뜨린다.

**완화**
- W8-R10을 요구사항으로 명시
- W8-D1 설계 결정
- 적용표에 **각 정책의 근거를 적는다**
- W8-V9에서 스냅샷으로 검출

**대응 계획** 통일이 바람직하더라도 **후속 백로그**로 기록한다. 전환과 분리해야 실패 시 원인이
명확하다.

---

## W8-K7 — 예외 타입 변화

**설명** `RetryPolicy`가 재시도를 소진하면서 원 예외를 자체 예외로 감싼다.

**영향** [W5-R6](30-5-4-requirements.md)의 오류 매핑이 깨진다.

```
노드에서 ValueError
  → RetryPolicy 소진
  → LangGraph가 RetryError로 감쌈
  → internal_chat의 except (ValueError, RuntimeError)가 안 걸림
  → CORS 헤더 없는 500  ← 2026-08-15 회귀
```

**완화**
- **W8-V5-7에서 예외 타입 확인** — 재시도 후에도 422/503 매핑이 유지되는지
- W5에서 매핑을 확인해 두었으므로 비교 가능
- 감싸진다면 진입점에서 `exc.__cause__`를 추적하거나, 재시도 대상이 아닌 예외는 `RetryPolicy`를
  통과하도록 설정

**주의** `ValueError`는 입력 오류이므로 **애초에 재시도 대상이 아니다.** `is_network_error()`가
`False`를 반환하면 즉시 전파돼야 한다.

---

## W8-K8 — 로그 성능 영향

**설명** 노드마다 로그를 남기면 I/O가 늘어난다.

**영향** 크지 않다. 구조화 로그 한 줄은 밀리초 단위다.

**완화**
- 동기 로깅이 병목이면 비동기 핸들러 검토
- 로그 레벨로 제어 가능하게

**측정** W8에서 성능을 측정하지는 않는다. 노드 로그의 `elapsed_ms`가 나중에 판단 근거가 된다.

---

## W8-K9 — `AUTH_REQUIRED` 도입의 계약 영향

**설명** W8-T1에서 `AUTH_REQUIRED` 도입으로 판단하면 신규 Task 상태가 생기고 계약이 또 바뀐다.

**영향**

| 항목 | 영향 |
| --- | --- |
| 공개 계약 | Task 상태 추가 |
| UI | 새 상태 처리 필요 |
| 승인 | 자동 승인 대상에서 벗어남 |
| W9 | "의도적 변경" 목록이 커짐 |

**완화**
- **W8-D2 기본값을 미도입으로** 둔다
- 인증 오류 **분류**까지만 하고 상태 도입은 후속
- 도입이 필요하다고 판단되면 W6처럼 승인 절차를 밟는다

## 3. W8의 위험 구조

### 3.1 "안정성을 높이려다 망가뜨리는" 유형

W8은 안정성을 높이는 단계인데, 위험의 다수가 **과도한 안정화**에서 온다.

| 위험 | 과도한 안정화의 형태 |
| --- | --- |
| K1 | 여러 계층에서 재시도 |
| K2 | 모든 노드에 재시도 |
| K4 | 실패를 막으려다 전체 실패로 |
| K6 | 정책을 "일관되게" 통일 |

**W8의 요점은 "적절한 곳에만" 재시도를 붙이는 것이다.**

### 3.2 계측이 유일한 검증 수단인 것들

| 위험 | 왜 계측이 필요한가 |
| --- | --- |
| K1 | 설정을 봐서는 실제 호출 횟수를 모른다 |
| K2 | 코드를 봐서는 중복 생성을 모른다 |
| K5 | 로그를 봐서는 모든 경로를 모른다 |

**W8-V3·V7·V8이 전부 계측 기반이다.**

## 4. 잔여 위험

| 위험 | 잔여 이유 | 후행 단계 처리 |
| --- | --- | --- |
| 정책 불일치 | W8-D1으로 유지 | W9 후속 백로그 |
| 429 재시도 없음 | W8-D6으로 유지 | W9 후속 백로그 |
| `AUTH_REQUIRED` 미도입 | W8-D2 | W9 후속 백로그 |
| 실제 장애 시 동작 | 오류 주입으로만 검증 | 운영 시 관찰 |
| 성능 | 측정 안 함 | 노드 로그로 간접 |
