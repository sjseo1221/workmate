### 1.1 97번 — 가장 큰 변화

현재 문서의 구조 자체가 "목표 vs 현재"다.

**개정 방향 선택지**

| | 방식 | 평가 |
| --- | --- | --- |
| a | 대조표를 지우고 구현 서술만 | 전환 이력이 사라진다 |
| **b** | **대조표를 "전환 이력"으로 성격 변경 + 구현 서술 추가** | **채택** |
| c | 문서 자체를 폐기 | 구조 도식의 가치가 있다 |

**설계 결정 W9-D1: b.** 대조표는 "2026-09 이전 구조 → 현재 구조"로 바꿔 역사적 기록으로 남긴다.
전환이 무엇을 바꿨는지 보여주는 자료가 된다.

**정정 대상 인용구**

```
현재: 발표나 문서에서는 "LangGraph로 구현 완료"가 아니라 "LangGraph형 Workflow 구조로 설계했고,
      현재는 A2A Registry 기반 경량 Runtime으로 구현했다"고 표현한다.

개정: LangGraph StateGraph로 구현했다(2026-09 전환). 전환 이전 구조와의 대조는 §N에 남긴다.
```

### 1.2 96번 — 성격 전환

| 항목 | 현재 | 개정 |
| --- | --- | --- |
| 문서 성격 | "가정형 목표 아키텍처" | "구현 기준 아키텍처" |
| 상단 인용구 | "이 문서는 현재 구현 상태를 설명하지 않는다" | **삭제 또는 정정** |
| §4 의사 코드 | "구조를 설명하기 위한 의사 코드" | 실제 구현 참조 링크 추가 |
| §5·§6 노드 구성 | 목표 | **구현과 대조해 차이 반영** |
| §11 불변식 | 목표 | **유지** |

**§5·§6이 실제 구현과 다를 수 있다.** W3에서 노드 분해를 하면서 96번과 다르게 만든 부분이 있으면
문서를 고친다([30-9-2](30-9-2-scope.md) §1.1).

**예외: §11 불변식.** 이것은 설계 원칙이므로 구현을 맞춘다. 다르면 해당 단계로 복귀한다.

### 1.3 `AGENTS.md` — 제안만

한 항목이 W7 결과와 충돌한다.

> M0.1은 A2A Task·Message 멱등성·Artifact·`task_id ↔ thread_id`·**Checkpoint**의 최소 인프라
> Migration을 소유하고…

W7에서 `a2a_checkpoints`를 DROP했으므로 M0.1의 소유 범위가 줄었다.

**`AGENTS.md`는 프로젝트 규칙 문서다.** W9에서 임의로 고치지 않고 **제안만** 한다.

## 3. 스냅샷 diff 분류 (핵심 산출물)

### 3.1 분류 정의

| 분류 | 정의 | 판정 근거 |
| --- | --- | --- |
| **동일** | 전환 전후 결과가 같음 | 대조 PASS |
| **의도적 변경** | 계획된 변경으로 설명됨 | 결정 ID(C1~C5 등) |
| **미검증** | 스냅샷이 애초에 다루지 않는 영역 | W1 `normalized_fields`·한계 6종 |
| **설명 불가 차이** | 위 셋에 속하지 않는 차이 | — |

### 3.2 기대 분포

| 분류 | 건수 | 내역 |
| --- | --- | --- |
| 동일 | 25 | `assistant_ask` 2건 외 전부 |
| 의도적 변경 | 2 | `assistant_ask.requires_confirmation`, `.confirmed_execution` |
| 미검증 | (목록) | 정규화 필드, 한계 6종 |
| **설명 불가** | **0** | — |

### 3.3 판정 절차

```
for 케이스 in 27건:
    if 대조 PASS:
        분류 = 동일
    elif 의도적 변경 목록에 있음:
        분류 = 의도적 변경
        변경 전후 기록
    elif 차이가 normalized_fields 안:
        분류 = 미검증 (원래 비교 대상이 아님)
    else:
        분류 = 설명 불가 차이   ← 여기가 0이어야 한다
```

### 3.4 "미검증"의 구성

스냅샷이 애초에 검증하지 않는 영역이다. **정직하게 나열한다.**

| 미검증 항목 | 출처 | 보완 |
| --- | --- | --- |
| 정규화된 필드의 값 | W1 `normalized_fields` 전체 | — |
| LLM 응답 품질 변화 | W1 한계 1 | W2-V6(구조화 출력 동등성) |
| 프롬프트 변경의 영향 | W1 한계 2 | 없음 |
| 숨은 부작용 | W1 한계 3 | **W3-V11** |
| 성능 변화 | W1 한계 4 | W8 노드 로그(간접) |
| 케이스에 없는 입력 | W1 한계 5 | W3 단위 테스트 |
| 오케스트레이터 실제 동작 | W6 | 통합 확인 |
| 고부하 시 동작 | W5 | 없음 |
| 실제 장애 시 재시도 | W8 | 오류 주입으로만 |

### 3.5 설명 불가 차이가 나오면

**완료 판정을 중단한다.**

```
1. 차이의 경로와 값을 기록
2. 어느 단계에서 생겼는지 추적 (W3? W4? W5?)
3. 해당 단계로 복귀해 수정
4. 또는 "의도적 변경"으로 승격 — 단 사용자 승인 필요
```

**3번이 기본이다.** 4번은 "지금 와서 보니 이게 맞다"는 경우인데, 그렇다면 왜 계획에 없었는지 설명이
필요하다.

## 4. 의도적 변경 전체 목록

스냅샷으로 검출되는 것은 2건뿐이므로, 나머지는 별도 기록이 필요하다.

| # | 변경 | 단계 | 결정 | 외부 관찰 | 검증 |
| --- | --- | --- | --- | --- | --- |
| 1 | 멱등성 실제 구현 — 중복 요청이 재실행되지 않음 | W4 | W4-D1 | **예**(W5부터) | W4-V3 |
| 2 | `runtime_bootstrap`이 미등록 Skill로 처리 | W4 | W4-D3 | 예 | W4-V2-3 |
| 3 | 진행 중 중복 요청의 동작 정의 | W4 | W4-D5 | 예 | W4-V3-6 |
| 4 | 확인 프로토콜 개편 | W6 | C1~C5 | **예** | W6-V1~V6 |
| 5 | UI REST 멱등성 비대칭 유지 | W5 | W5-D3 | 아니오 | 기록만 |

### 4.1 "외부 관찰 가능"의 의미

사용자·오케스트레이터가 알아챌 수 있는 변경이다. 4건이 해당한다.

**이 4건이 W9 보고의 핵심이다.** 나머지는 내부 구조 변경이다.

### 4.2 변경 4가 가장 크다

W6의 확인 프로토콜 개편은 agent·UI·어댑터·문서가 모두 바뀌었다. 별도 절(증빙 §6)로 상세 기록한다.
