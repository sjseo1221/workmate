## 2. W2로 넘기는 것

W2는 스냅샷을 **선행 조건으로만** 쓴다. 직접 소비하지는 않는다.

| 항목 | 용도 |
| --- | --- |
| W1-V1 전건 PASS | [W2-E1](30-2-3-entry-criteria.md) 착수 조건 |

**왜 W2가 스냅샷을 직접 안 쓰는가** W2는 State·어댑터·Checkpointer·LLM 경계를 만들 뿐 Skill을
실행하지 않는다. 다만 의존성 추가로 기존 경로가 영향받을 수 있으므로, W2-T1 직후 전체 스위트를
실행할 때 스냅샷도 함께 돈다.

## 3. W3으로 넘기는 것 — 가장 중요

W3은 스냅샷의 **1차 소비자**다.

| 항목 | 용도 | 대응 |
| --- | --- | --- |
| 케이스 27건 | Subgraph 재작성의 수용 기준 | [W3-R2](30-3-4-requirements.md) |
| Skill별 케이스 | Skill 완료 즉시 대조 | [W3-T8](30-3-6-wbs.md) |
| 정규화 목록 | 결정성 검증의 기준 | [W3-V4](30-3-7-verification.md) |
| 부분 실패 케이스 6건 | 실패 파급 규칙 검증 | [W3-V5](30-3-7-verification.md) |
| `daily_briefing.both_providers_down` | **병렬 Reducer 검증의 핵심** | [W3-V6](30-3-7-verification.md) |
| `origin` 정보 | 시나리오의 배경 추적 | W3 단위 테스트 설계 |
| 스냅샷 불가 Skill(있다면) | W3-E1의 예외 처리 | [W3-E1](30-3-3-entry-criteria.md) |

### 3.1 W3에서의 사용 규칙

```
Skill 하나 완료
  → 해당 스냅샷 대조
  → 차이 발견 시:
      1. 이식 오류인가?        → 구현 수정
      2. 정규화 누락인가?      → W1 정규화 보완 (이유 기록)
      3. 의도적 변경인가?      → W3에서는 원칙적으로 없어야 한다
```

**W3에서 스냅샷 기대값을 고치는 것은 금지다.** 3번에 해당하면 중단하고 보고한다.

### 3.2 W3이 스냅샷으로 못 잡는 것

| 숨은 부작용(우선순위 Snapshot 저장 등) | [W3-V11](30-3-7-verification.md) DB 직접 검증 |
| `user_id` 조건 누락 | [W3-V3](30-3-7-verification.md) 혼입 시나리오 |
| 노드 단위 동작 | [W3-V2](30-3-7-verification.md) 단위 테스트 |

## 5. W6으로 넘기는 것 — 의도적 변경

W6은 스냅샷을 **깨뜨리는 유일한 단계**다.

| 케이스 | W3~W5 | W6 |
| --- | --- | --- |
| `assistant_ask.requires_confirmation` | PASS 유지 | **의도적으로 변경** |
| `assistant_ask.confirmed_execution` | PASS 유지 | **의도적으로 변경** |
| 나머지 25건 | PASS 유지 | PASS 유지 |

### 5.1 W6에서의 처리 절차

```
1. 변경 전 대조 실행 → 2건 FAIL 확인 (예상된 실패)
2. 차이를 경로 단위로 기록 → "공개 계약 변경 내역"
3. 새 동작으로 스냅샷 갱신 (기록 모드, 커밋 diff로 검토)
4. 변경 전후를 증빙에 나란히 기록
```

**3번이 W1-R9(기록 모드 보호)의 유일한 정당한 사용이다.** 그 외의 기록 모드 실행은 사고다.

### 5.2 케이스 파일에 미리 표시

W1에서 이 2건의 `description`에 다음을 적어 둔다.

```json
"description": "확인이 필요한 동작에서 pending_action을 반환한다.
                W6(D1=B)에서 interrupt 기반으로 의도적으로 변경될 예정."
```

W3~W5에서 이 케이스가 실패하면 "아직 W6이 아닌데 왜 바뀌었나"를 즉시 알 수 있다.

## 6. W7·W8로 넘기는 것

| 단계 | 사용 방식 |
| --- | --- |
| [W7](30-7-w7-legacy-removal.md) | 레거시 삭제 후 재대조(W7-V9). 삭제가 동작을 바꾸지 않았음을 확인 |
| [W8](30-8-w8-retry-observability.md) | RetryPolicy 적용 후 재대조(W8-V9). 재시도 정책 변경이 결과를 바꾸지 않았음을 확인 |

**W7의 대조가 특히 중요하다.** `app/workflows/` 삭제 후에도 스냅샷이 PASS하면, 새 구현이 옛 구현을
온전히 대체했다는 증거가 된다. 이 시점 이후 스냅샷은 **재작성 불가**가 된다.

## 7. W9로 넘기는 것 — 최종 보고의 근거

[W9](30-9-w9-docs-evidence.md)의 핵심 산출물인 **스냅샷 diff 분류표**가 W1 자료로 만들어진다.

| 분류 | 근거 | 기대 |
| --- | --- | --- |
| 동일 | 대조 PASS | 25건 |
| 의도적 변경 | W6에서 기록한 변경 내역 | 2건 |
| 미검증 | W1의 `normalized_fields` + 한계 6종 + 스냅샷 불가 Skill | 목록 |
| **설명 불가 차이** | 위 셋에 속하지 않는 차이 | **0** |

### 7.1 "미검증" 분류의 구성

W9에서 정직한 보고를 하려면 W1이 무엇을 검증하지 않았는지가 정확해야 한다.

| 미검증 항목 | W1 출처 |
| --- | --- |
| 정규화된 필드의 값 | `normalized_fields` 목록 전체 |
| LLM 응답 품질 | 한계 6종 중 1 |
| 프롬프트 변경 영향 | 한계 6종 중 2 |
| 성능 | 한계 6종 중 4 |
| 케이스에 없는 입력 | 한계 6종 중 5 |
| 스냅샷 불가 Skill | 조건부 완료 기록 |

### 7.2 관찰된 이상 동작

W1에서 "고치지 않고 기록만" 한 항목들(W1-R10)이 W9의 후속 백로그가 된다.
